## 1. 优化主题一：生成性能与稳定性

### 1.1 FP 子批并发生成（docs/22，v3.5.5）

**背景**：自举验证实测生成阶段 ~50min 全串行（FP1 LLM 14.5min + 批内去重 3.7min + FP2 14min + Review 10min + 空隙 8min），而 FP 之间无数据依赖（各生成各的，汇合点统一三道去重）。

**可行性验证（10-08 实测）**：
- 数据依赖审计：`resolved_cases` / `checkpoint_groups` / `degraded_flags` / `fp_subtasks` / `_gen_queue` / GenAgent 实例逐项确认并发安全；
- LLM 供应商并发实测：N=3 / 5 / 8 全部成功，无 429，无限流；
- checkpoint 全量覆盖写天然收敛，无需加锁。

**实施**（`orchestrator.py` `_gen_node`）：串行 `for fp in fp_list` → `_gen_one_fp(fp)` + `asyncio.gather` + `Semaphore(并发度)`；并发度从 `kb_settings` KV（`generation_fp_concurrency`）动态读取，`<=1` 或单 FP 走串行回退（行为与 v3.5.4 一致）。新增 `GEN_FP_CONCURRENCY: int = 3`（0/1 = 串行回退）。前端设置页新增「生成性能」卡片（下拉 1-5）。

**守卫测试挖出的真实回归（已修）**：初版 `_gen_one_fp` 完成回调无条件执行，单分片 FP 失败后仍写 checkpoint + 发 done → 失败 FP 被记成"完成 0 条"→ 续跑时被 `completed_fps` 跳过 → **永不重试**。修复：`single_shard_failed` 标记 + 完成回调入口提前 return。

**验证**：`test_fp_concurrency.py` 8/8 全绿；相邻单测 56 passed；phase4 186/186、phase5 112/112；`tsc --noEmit` + build 零错误。

### 1.2 LLM 供应商禁用机制改造 + 等待重试（docs/23，v3.5.6）

**起因**：10-09 自举 E2E 实证「需求文档混合上传」FP 5 个子批全部 0 条产出，根因 = 三家供应商同时落入内存禁用窗口（软失败累积 3 次 → 600s 禁用）。

**旧机制问题**：软失败跨调用禁用、禁用状态在内存（重启失效/多进程不一致）、全禁用即零重试失败、运维不可见、硬失败 600s 后自动恢复又去撞。

**新机制**：
- **失败分类**：软失败（超时/5xx）→ 仅本次 call 内让位，全部失败则等待重试；硬失败（401/403/额度耗尽/模型不存在）→ 持久化禁用（DB `enabled=false`）+ 管理员通知 + 主标记让位，需人工启用。
- **等待重试**：第 1 轮首响应超时 180s → 全败等待 60s（含 5s 分片倒计时）→ 第 2/3 轮收紧 60s → 全败写通知 + 抛出。单次 call 最坏 11-15 分钟。
- **数据模型**：`llm_config` 新增 4 列（`enabled` / `disabled_reason` / `disabled_by` / `disabled_at`）；新表 `admin_notifications`。
- **前端**：设置页启停开关 + 禁用原因；新建通知页 + 导航铃铛未读角标（60s 轮询）；生成页等待重试红色提示条。

**排查记录（重要）**：改常量 `DEFAULT_CALL_TOTAL_BUDGET`（240→0）时，`call_vision`（多模态）用 `or self.DEFAULT_CALL_TOTAL_BUDGET` 取预算 → `deadline = 开始时间 + 0` → 多模态调用全部秒挂。**教训：改"声明常量"必须全量 grep 消费方。**

**验证**：`test_provider_disable_retry.py` 9/9；守卫子集 117 passed；phase4 186/186、phase5 112/112；前端构建零错误。

## 3. 优化主题三：语义去重性能优化

### 3.1 性能排查（docs/26，10-12）

**现象**：复验轮执行期间日志静默、任务进度条停在 70% 长达 35 分钟，用户怀疑"卡死"。

**结论先行**：**系统无故障、无死锁**。慢的根因是 v3.4.5 新增的「跨子轮语义去重」在 CPU 上对全量用例做 bge-large embedding。

**证据链**：
- 静默窗口与 `dedup_semantic` 日志精确对齐；静默期 API 容器 CPU 379%~392%（8 核占约 4 核），典型本地推理特征；
- 吞吐实测：约 3~4 秒/条（整例 JSON 文本较长），v1.0-r2 全程 ~100min 中 ~60min 是两轮语义去重等待（占 60%）。

**根因（三因素叠加）**：① 模型过重（bge-large 335M，CPU）；② 全量重算（三个对称执行点每次对全部用例重新 embedding，无增量缓存）；③ 串行在主链路（编排必须等它算完才能进 review）。

### 3.2 优化方案与定标（docs/27，10-12）

**方案组合**：D 进度可观测 + E 语义字段序列化 + A 去重专用小模型 + B 进程内向量缓存。

**定标 gate（附录 A，1055 条真实用例三档对照）**：

| 档 | 模型 × 口径 | 判重对 | 单条 embed | 结论（原文） |
|---|---|---|---|---|
| T0（基线） | large × 整例 JSON | 586 | 3.810s | — |
| T1（E） | large × 语义字段 | 119 | — | 漏判 469 → E_FAIL |
| T2（A） | small × 语义字段 | 152 | — | 漏判 441、多判 7 |
| T3 | small × 整例 JSON | 979 | — | 过判（不同场景也 ≥0.92） |
| T4 | base × 整例 JSON | 415 | 0.815s | 漏判召回 53% |

**原文结论**：A（换轻量模型）与 E（语义字段瘦身）全线否决，0.92 阈值与 bge-large×整例JSON 分布深度绑定。

> ⚠️ **该结论已被 docs/29 推翻**（见下节），E 与 A 实际是「未验证」而非「已否决」。

### 3.3 定标 gate 复核 + 生产误删缺陷（docs/29，10-12）

**三处方法学缺陷（致命）**：
1. **评测域 ≠ 生产域**：定标语料把 6 个需求 1055 条汇成一张两两矩阵，跨 req 对占 66.3%；而生产里 `dedup_semantic` 只在单次生成任务的用例集上跑（同 req），跨 req 对永不被比较。实测证据对 90% 是跨 req（T1 lost 6/54、T2 lost 5/55、T4 divergent 5/35）→ **E_FAIL / T3 FAIL / T4 FAIL 三个 verdict 都不成立**。
2. **无正样本标签**：`pos_pairs_matched=0` → gate 退化成"与 T0 一致"，结构上不可能发现 T0 判错；公式不含 `lost_vs_base`（不对称）；归档报告缺 `high_conf_lost` 字段 → verdict 不可复现。
3. **`divergent`（标题 3-gram<0.45）不是误删信号**：T4 同 req 的 5 条 divergent 全部是真重复；T2 的 7 条 extra 里 6 条是真重复。

**新发现生产正确性缺陷（比性能更重要）**：`_calib_pairs.json` 32 条真实去重留痕（sim 0.9217~0.9827）里，标题级可判读的**误删 ≥9 条（28%）**：

| sim | removed ≈ kept | 判读 |
|---|---|---|
| 0.9455 | 管理员**编辑**项目信息成功 ≈ 管理员**创建**项目成功 | 误删（不同操作） |
| 0.9274 | 创建归属产品的**模块**成功 ≈ 管理员创建合法名称的**产品**成功 | 误删（不同实体） |
| 0.9273 / 0.9217 / 0.9298 | **产品** vs **项目** | 误删（不同实体） |
| 0.9475 | 为角色分配**空**菜单权限 ≈ 为只读角色分配菜单权限**成功** | 误删（边界 vs 正常） |
| 0.9223 | 质量门禁**未通过** ≈ 质量门禁**通过** | 误删（相反分支） |
| 0.9484 | 上传 **.docx** ≈ 上传 **.markdown** | 误删（不同扩展名） |
| 0.9327 / 0.9559 | 跨文档矛盾检测 / 无整理版检索 | 误删（不同场景） |

**关键定量**：同 req 内，真重复的 sim 可低至 **0.8933**（漏判），不同用例的 sim 可高至 **0.9455**（误删）——**两个分布在 0.89-0.95 区间重叠，单阈值救不了。**

**连带缺陷**：
- 数字护栏对小数失效（`_numbers("9.9MB") = {"9"}`，`re.findall(r"\d+")` 吃掉小数）；
- 误删不可审计（`semantic_dedup_removed` 只进日志/SSE，`review_reports` 无该字段）；
- 生产可见度为零（日志只打 3 条示例，`docker logs` 随重启丢失）。

**收益承诺重估**：docs/27 的 `12-15×` 无依据（乘积推演未实测）；§A.5 的 `1.6×` 算式不自洽且未实测；§2.3「bge-base 1024 维」有误（实为 **768 维**）。本次复核新拿到的实测：**bge-base × 整例 JSON = 0.815 s/条 vs large 3.81 s/条 = 4.7×**（口径与判定逻辑不变，被 T4 无效判据连带否决）。

**建议路线**：P0 正确性优先（决策规则升级为"余弦 ∧ 结构佐证" + 实体/操作/否定词/扩展名护栏 + 修小数护栏 + 留痕落库）→ P1 评测重建（per-req 域 + 真标签集 + 比 PR/F1）→ P2 零风险提速（ONNX int8 / 生成期预计算）→ P3 表征层（去各向异性）。

### 3.4 实施与复核（docs/27 附录 B + docs/28，v3.5.9 / v3.5.9.1）

**定标后的路线重定向**（10-12 拍板）：换空间（E/A）全线否决，改走**物理加速**（不碰模型/口径/阈值 → 判定逐对一致，无需重定标）：
- **分片并行**：去重 embed 入口支持 ProcessPool 分片；dev 默认串行（workers=1），服务器 `DEDUP_EMBED_WORKERS=auto/N` 开启；并行异常自动回退串行。
- **增量去重·预嵌入**：FP 子轮完成 / 续跑恢复 / 合并前三挂点提前把向量写入 B 缓存，主合并点全命中；进度消息按 miss 数估算。
- **不做** ONNX 量化（需改 base 镜像 + 重定标，暂缓）。

**探针数据**：ThreadPool 2 workers 仅 1.04×（假并行，torch intra-op 线程池进程级共享）、4 workers 0.38×（负优化）→ 线程池形态永久无效；ProcessPool 因 dev 机内存不足未完成基准 → **dev 不开并行**。

**实施后复核（§B.5）发现并已修复 3 个缺陷**：

| # | 缺陷 | 根因 | 触发条件 | 修复 |
|---|---|---|---|---|
| 1 | **分片并行向量错位**（严重） | 交织分片 `[texts[i::workers]]` 按 chunk 顺序 extend 拼回 → 向量整体错配文本 | 仅 `DEDUP_EMBED_WORKERS>1`（服务器开并行时） | 连续分块 + 按提交位置回填；新增 `test_dedup_chunk_order.py` 6 用例锁死 |
| 2 | **fp_progress 计数污染**（中） | `__dedup__` 假 FP 进度卡被 append 进 fp_subtasks 且计入 covered → covered > total，前端进度溢出 | 所有生成任务 | covered 统计排除 `__` 前缀非 FP 子任务 |
| 3 | **mp_context 声明与实现不符**（低） | 注释声称 spawn 但未设 mp_context，Linux 默认 fork（fork 已初始化 torch 有死锁风险） | 服务器开并行时 | 显式 `mp.get_context("spawn")` |

**为什么测试当年没拦住**：① 顺序 bug——bench 脚本与生产代码同款写法；② fp_progress——改 C1 时只 grep 了 orchestrator 调用方，**没跑既有单测**（违反"改约束必须全量 grep + 回归"纪律）。

**复核实证（真实数据）**：预热等价性——32 条真实用例 A 直算 vs B 分块预热+review 改写，removed 对逐条一致、miss=0；预热收益——直算 116.1s → 命中后 0.10s。
