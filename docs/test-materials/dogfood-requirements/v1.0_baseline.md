# 项目管理系统 v1.0 需求文档

> 产品：AI 测试用例生成平台
> 项目版本：v1.0（基线版——系统核心功能全貌）
> 优先级：P1

---

## 1. 项目背景

为提升测试用例编写效率，建设"需求驱动的 AI 测试用例自动生成平台"。本版本覆盖平台核心功能：需求管理、需求分析（解析/澄清/功能点）、测试用例生成与审核、知识库、影响分析、系统管理。

## 2. 用户角色

| 角色 | 职责与权限 |
|---|---|
| 管理员 | 系统全部功能：产品/模块/用户/角色管理、LLM 设置、知识库管理、删除操作 |
| 普通用户 | 需求上传、澄清回答、需求确认、生成用例、用例编辑与反馈、项目创建、归档、知识库问答 |
| 只读用户 | 查看各类列表与详情、知识库问答；无写权限 |

权限规则：基于角色的菜单权限控制；产品可配置可见用户列表，为空表示全员可见；未授权用户访问受控接口返回 403。用户密码采用加盐哈希存储；登录连续失败达到 5 次锁定账号 30 分钟。会话令牌有效期为 8 小时，过期需重新登录。

## 3. 功能需求

### 3.1 产品与项目结构管理

3.1.1 产品管理：管理员可创建产品。产品名称必填且长度 1-128 字符，系统内名称唯一，重名创建时提示"产品名称已存在"并拒绝。产品可填写描述（最长 1024 字符）。删除产品前系统展示关联数据统计（项目数、需求数、用例数）供确认，删除为级联删除，且仅管理员可执行。

3.1.2 项目管理：项目归属产品，名称必填（1-128 字符），版本号默认 1.0（最长 32 字符），同一产品内版本号不可重复，重复时创建失败并提示。项目支持"上线时间"属性（精确到秒），用于知识库检索排序与回归基线归属。

3.1.3 模块管理：模块归属产品，名称必填（1-64 字符）。模块间可建立依赖关系（默认类型 depends_on，强度默认 medium），以图谱可视化展示。功能点可归属一个或多个模块。

3.1.4 项目归档：归档以项目为单位发起。归档时项目下所有"已确认"状态的需求自动归档，归档触发需求知识入库（向量化）与功能点知识固化。已归档项目可重新激活。历史遗留的需求级归档接口已废弃，调用返回 409 错误并提示改用项目级归档。

### 3.2 需求文档上传

3.2.1 支持上传 .md / .markdown / .docx / .txt 格式的需求文档，支持单次多文件上传。单文件大小不得超过 10MB，超限提示"文件超过大小限制"。

3.2.2 非文本文件（伪装扩展名）须拒绝：文本类文件按 UTF-8 解码（失败回退 GBK）；无法识别为有效文本的文件返回 400 错误。

3.2.3 上传时须指定所属产品与项目，填写需求标题与优先级（P0/P1/P2）。上传成功后系统创建异步分析任务，用户可在任务管理页查看进度。

3.2.4 docx 文档中的内嵌图片应支持识别：配置了视觉大模型时调用识别并输出图片内容描述；未配置时在解析文本中保留图片占位标记，不中断解析。

### 3.3 需求解析与结构化

3.3.1 系统将需求文本解析为结构化的需求表示（SRR），包含：需求基本信息（标题/概述/角色）、主流程步骤、备选流程、业务规则、数据约束、角色权限等维度。

3.3.2 系统同步将需求拆分为功能点（FP）。每个功能点包含独立的子结构（子 SRR），承载该功能点内部的业务规则与数据约束；跨功能点的交互规则与共享约束保存在需求级总结构中。一条规则只在一处定义，不得重复。

3.3.3 同产品同模块下已存在同名功能点时，新需求直接复用该功能点定义，不重复生成。

3.3.4 功能点拆分失败时解析主流程不中断，但须在任务结果中记录降级标记，供后续环节感知。

### 3.4 需求澄清

3.4.1 解析完成后系统产出澄清问题。检测维度包括：需求完整性、表述歧义、内容遗漏、引用未定义（引用了文档中不存在的规则或字段）、同文档前后矛盾、多文档之间矛盾。

3.4.2 澄清优先查询知识库：系统能从知识库得到答案的问题自动补全（标记为已回答），无法回答的才转为人工澄清问题。每轮人工问题不超过 5 个。

3.4.3 每个澄清问题须归属到具体功能点。已回答的问题不再出现在后续轮次的问题清单中（可在澄清历史中查看）。

3.4.4 澄清最多进行 3 轮。用户提交答案（问题 ID 与答案文本的映射，可附整体补充说明）后，系统重新生成最终需求结构。3 轮后仍存在关键问题时应强制放行并在结果中标记，提示用户人工完善需求。

3.4.5 澄清完成的问答题进入澄清历史，按轮次记录问题数、回答数与知识库命中情况。

### 3.5 需求确认与功能点审核

3.5.1 需求状态流转：分析中 → 草稿 → 待审核 → 已确认 → 已归档。存在解析降级标记的需求不允许确认。所有功能点必须审核通过且已分配模块后，需求才能确认。

3.5.2 功能点支持：人工审核（逐个通过）、名称修改、多模块归属调整、结构字段逐项编辑、输入提示词后重新生成、多选合并为一个功能点。

3.5.3 需求补充说明后可重新分析：重新分析前当前结构自动存入历史版本；支持查看历史版本详情与恢复（恢复后需重新确认）。需求编辑采用乐观锁：提交时携带版本号，版本不一致返回 409 冲突。

3.5.4 并发编辑保护：同一需求被并发修改时，后提交者收到 409 冲突提示，需刷新后重试。

### 3.6 测试用例生成

3.6.1 仅"已确认"状态的需求可生成测试用例。生成入口为单一接口，采用服务端事件流（SSE）推送进度，阶段包括：解析（20%）、生成准备（25%）、门禁（40%）、影响分析（50%，仅优化类需求）、测试设计（62%）、用例生成（70%）、审核（90%）、完成（100%）。

3.6.2 生成前置守卫（按顺序校验，任一失败即终止并返回对应错误码）：需求存在（否则 404）、用户对该产品有权限（否则 403）、状态为已确认（否则 409）、影响分析条目全部确认（否则 409）、需求结构非空（否则 400）、无进行中的生成任务（否则 409）。

3.6.3 同一需求同时只允许一个生成任务。任务中断后可从断点续跑：系统保存已完成功能点的生成结果与输入指纹（需求内容哈希等），续跑时校验指纹一致才允许恢复，不一致则拒绝并要求重新生成。

3.6.4 生成策略：按功能点逐个定向生成；功能点为空时对需求整体一次性生成兜底；存在跨功能点交互规则时额外生成集成测试用例。单个功能点生成失败不阻断其他功能点。

3.6.5 用例类型覆盖：功能/边界/异常/安全四类。测试设计技术按规则触发：数据约束含范围（如 6-20 位）时生成边界值用例（最小值-1 至最大值+1 六个取值）；规则数不少于 2 条时生成决策表用例；备选流程含状态类情形（锁定/禁用/过期/取消/超时等）时生成状态迁移用例；存在主备选流程时生成场景组合用例；必填/长度/金额类字段生成错误推测用例（如空值、超长、负数）。

3.6.6 最少用例数量：按需求要点规模动态计算（主流程步骤数除以 3 向上取整，加备选流数、业务规则数、数据约束字段数），P0/P1 级需求不低于要点总数的 60%，上限 40 条。

3.6.7 用例去重：生成结果经精确重复、语义相似、子集包含、语义等价四级去重。跨轮次生成的用例做语义级合并（相似度阈值 0.92），且数值取值集合不同的用例不得合并。

3.6.8 质量门禁：需求结构评分须达到阈值（产品首个需求时 0.60，之后 0.75）；存在未解决的关键问题时不放行。门禁未通过回澄清环节，最多回环 3 轮，超限强制放行并提示人工处理。

3.6.9 用例编号规则：TC-{模块}-{批次号 4 位}-{序号 4 位}。

### 3.7 用例审核与入库

3.7.1 每条用例计算置信度（综合向量匹配度、完整度、一致性、生成自评分）。置信度 ≥0.70 的用例自动入库（状态 approved）；0.60-0.70 的进入待人工确认（reviewed）；低于 0.60 的记录到错误案例库。

3.7.2 审核发现覆盖缺口时自动补充生成一次：将未覆盖要点按功能点分组重新生成并二次审核；二次仍不达标则停止补充并标记。

3.7.3 入库前按标题去重（同标题保留置信度最高的一条）；单条入库失败不影响其他用例。

3.7.4 仅审核通过的用例写入向量库供后续检索复用。优化类需求生成时，受影响功能点的最新有效历史用例（按项目上线时间取最新，状态 approved）自动作为回归用例复用（标题加"[回归]"前缀），无历史用例的功能点由模型定向补生成。

3.7.5 覆盖率统计口径：分母为主流程步骤、备选流程、业务规则、数据约束、共享规则五类要点（业务规则与数据约束仅从功能点抽取）。要点标注率不足 30% 时覆盖率不可信，此时不输出"覆盖率"数字，改输出"观测覆盖率"，且不触发补生成。结果中输出的覆盖要点 ID 合法集合 = 已覆盖要点 ∪ 前置条件要点。

3.7.6 完成事件须透出：用例清单、审核报告、覆盖率、一致性检查结果、回归复用统计、降级标记集合、是否需人工介入、总耗时。

### 3.8 用例管理与导出

3.8.1 用例列表支持按需求、项目、产品、类型、状态筛选，分页大小不超过 100。

3.8.2 用例支持编辑、删除、单条与批量审核（通过/驳回并填写反馈意见）。人工确认后的用例成为权威用例，供后续需求检索复用。

3.8.3 用例导出支持 5 种格式：JSON、Markdown、Gherkin（Cucumber 框架）、pytest（Python 自动化脚本）、XMind 思维导图（zip 文件，层级为需求→功能点→用例→步骤）。导出必须指定用例 ID 列表，不允许不指定条件导出全部。

### 3.9 知识库

3.9.1 归档的需求与审核通过的用例进入知识库：结构化数据存入关系库，向量存入向量库。向量化异步执行，状态分未处理/处理中/已完成/失败四种，管理页展示双状态（已归档、已向量化）。

3.9.2 归档时同名功能点的跨版本知识自动聚合为"最新整理版"（CRSR）：标量字段取最新版本的值，列表字段按条目签名去重后合并。知识聚合失败不阻断归档。聚合结果向量化入库，同一功能点重复归档时覆盖更新同一条向量而非新增。

3.9.3 知识检索采用混合方式：向量检索（召回 20 条，相似度阈值 0.70）与关键词检索并行，结果融合排序后经重排模型精排，取最优若干条。检索限定当前产品与已归档状态；已删除内容不得出现在检索结果中。

3.9.4 检索排序考虑时间因素：同一功能多版本知识按上线时间衰减（半衰期 180 天），最新版本优先。知识库问答对涉及版本变更的问题按最新版本回答。

3.9.5 知识库问答：用户提问后流式返回答案，答案附带引用来源列表；来源须标注类型与权威层级（需求文档 > 功能点最新整理版 > 人工核准用例 > AI 生成用例），最新整理版与单版本记录冲突时优先采信最新整理版并标注说明。

3.9.6 问答记录持久化保存；支持人工纠错：纠错内容经审核后回流知识库，并刷新相关功能点的最新整理版知识。

3.9.7 知识库周期自检（每日一次，只读不改数据）：①聚合知识漂移检测（重算聚合结果与固化数据比对，不一致即漂移）；②跨版本规则矛盾检测（同一功能点不同版本规则冲突，输出冲突双方及来源版本）；③向量库与关系库对账（发现孤儿向量）。自检异常不影响主业务。

### 3.10 影响分析

3.10.1 需求包含优化语义（如"优化 XX 流程"）时，生成过程自动执行影响分析：识别被优化的原始需求，沿版本链找到历史用例，沿功能点依赖图双向遍历（上游依赖与下游被依赖）确定受影响范围，产出影响报告与回归测试建议。

3.10.2 影响分析结果须逐条人工确认（受影响/不受影响/移除）。存在未确认条目时测试用例生成被拦截，返回 409。

3.10.3 修改已归档需求的上线时间后，系统须同步刷新受影响功能点的回归基线归属与向量元数据，否则基线归属失效。

### 3.11 系统管理

3.11.1 用户与角色：管理员维护用户账号与角色分配；角色通过菜单权限数组控制功能可见性。系统初始化时内置管理员账号、默认产品与测试模式库。

3.11.2 大模型配置：支持配置多个大模型提供商，API Key 加密存储（展示时脱敏为前 3 后 4 位），可设置主提供商，配置即时生效，提供连通性测试。

3.11.3 调用保护：大模型调用异常时熔断（连续失败停止调用并自动恢复），支持指数退避重试与多提供商自动切换；单次生成任务的总调用预算 240 秒；鉴权失败（403/401）时立即禁用对应提供商 600 秒。

3.11.4 提示词管理：各环节提示词模板可在管理页查看与覆盖修改，保存于数据库运行时加载，支持一键恢复默认。

3.11.5 任务管理：需求分析与用例生成任务统一在任务页展示状态（运行中/已完成/失败/已中断/已中止/已取消）、进度与结果摘要。

3.11.6 死信队列：流水线意外异常进入死信队列供排查；系统主动拒绝的请求（如降级结构、检查点后端不可用）不进入死信队列。

3.11.7 操作日志：关键操作记录审计日志，详情为结构化数据。

## 4. 非功能需求

4.1 所有列表接口分页大小上限 100。
4.2 接口限流：默认每分钟 60 次，超限返回 429。
4.3 部署形态：Docker Compose 单机全栈，组件含应用服务、前端、PostgreSQL（含中文分词扩展）、Milvus 向量库、Redis、Celery 异步任务。
4.4 生成任务的断点检查点必须持久化到 PostgreSQL；持久化不可用时生成请求直接拒绝并明确报错，禁止降级为内存存储（重启丢失断点）。
4.5 所有静默失败路径必须记录降级标记并在完成事件中透出，前端可据此提示用户。
4.6 安全：跨域白名单、生产环境关闭接口文档、启动时校验密钥配置。

## 5. 验收标准

- 完整走通"上传 → 解析 → 澄清 → 确认 → 生成 → 审核 → 导出 → 归档 → 问答"全流程。
- 澄清一轮回答后无关键级追问（一轮收敛）。
- 生成的测试用例覆盖全部功能点要点，类型分布含功能/边界/异常/安全。
- 归档后知识库问答能命中刚归档的需求知识并正确标注来源。
- 全流程各阶段降级/失败均有可见标记，无静默失败。
