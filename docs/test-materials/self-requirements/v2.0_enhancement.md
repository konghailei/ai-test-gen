# AI-Test-Gen 平台 — 系统需求文档 v2.0（第二轮：协作与治理增强）

> 产品：AI-Test-Gen 平台（本系统）
> 用途：**自证测试（self-dogfood）** 第二轮 —— 在第一轮核心全流程之上，补充协作、质量治理、
> 多模态、版本管理等增强能力，验证系统的 KB 累积与越用越好用特性。
> 版本：v2.0（增强版）
> 对应系统版本：v4.0.2
> 优先级：P1
> 上一轮：v1.0_core_baseline.md

---

## 1. 本轮背景

第一轮覆盖了核心全流程。本轮在此基础上补充：多人协作、需求版本管理、用例质量治理、多模态识别、知识库编译化、评审报告等增强能力。这些能力在第一轮基线后逐步建设，本轮的验证重点是**知识库累积效应**（第二轮需求引用第一轮已归档的规则时，KB 应能命中并复用）。

## 2. 本轮新增/细化功能需求

### 2.1 多人协作与冲突检测

2.1.1 需求支持多人协作编辑，每次 SRR 被修改时 `revision` 自增，用于乐观锁冲突检测。

2.1.2 当同一需求被两个用户同时编辑时，后提交者若基于过期的 revision 提交，系统须提示冲突并要求刷新后重试，不得静默覆盖。

2.1.3 需求支持版本快照（`GET /api/requirements/{req_id}/versions`）：每次关键变更（澄清、确认、影响分析确认）保存版本，支持查看历史版本详情与回滚（`POST /api/requirements/{req_id}/versions/{version_index}/restore`）。

### 2.2 需求变更影响分析（增强）

2.2.1 需求级影响分析（`POST /api/requirements/{req_id}/impact-analysis`）：变更需求后，系统计算受影响的上下游功能点、受影响用例，并生成影响描述（`/impact-description`）。

2.2.2 影响描述支持人工修正（`PUT /api/requirements/{req_id}/impact-description/{fp_id}`），修正后确认落库（`POST /impact-analysis/confirm`）。

2.2.3 功能点依赖图谱支持：新增依赖边（`POST /requirements/{req_id}/fp/dependencies`）、删除依赖边、依赖边审核（review_status：pending/approved/rejected）。

2.2.4 功能点合并（`POST /requirements/{req_id}/fp/merge`）：同名或语义重复的功能点可合并，合并后保留原依赖关系。

### 2.3 用例质量治理

2.3.1 需求质量报告（`GET /api/requirements/{req_id}/quality-report`）：报告 SRR 覆盖率、功能点完整性、澄清收敛轮次等指标。

2.3.2 用例质量报告（`GET /api/knowledge/case-quality-report`）：报告用例类型分布、优先级分布、重复率、可执行性问题（如臆造接口、无触发路径、破坏性操作被写成常规用例）。

2.3.3 语义去重分级闸门（v3.5.10 引入）：
- 结构护栏：标题、步骤高度雷同的用例直接判重；
- LLM 窄带裁决：结构相似但表述差异较大的用例，交由 LLM 在窄带内裁决是否等价；
- 去重留痕：所有被判定删除的用例记录到 `dedup_removals` 表（可审计、可恢复）。

2.3.4 去重误删率须低于 5%。去重阈值（语义相似度 0.92）不得为降低冗余而随手调低（曾因放宽导致误删 25-34%）。

2.3.5 去重留痕查询接口（`GET /api/dedup-removals` 与详情）：支持查看被删用例的原因、相似度、原内容，支持恢复。

2.3.6 用例批量操作：按需求批量删除（`DELETE /api/testcases/batch/by-requirement/{req_id}`）。

### 2.4 多模态识别

2.4.1 需求文档中的内嵌图片（docx 内嵌图、原型 HTML 截图）支持视觉大模型识别，输出图片内容描述并纳入 SRR。

2.4.2 原型 HTML 上传（`v2.0_proto_html` 场景）：支持上传 HTML 原型文件，系统解析 DOM 语义树，提取页面结构、控件、交互说明。

2.4.3 视觉模型可独立配置（`PUT /api/knowledge/vision-llm`），与文本 LLM 解耦；未配置视觉模型时降级为保留图片占位标记。

2.4.4 图标语义识别：需求文档中的图标（如 📤上传 ✅成功 ❌失败 📋列表）须被正确识别为对应操作语义。

### 2.5 知识库编译化

2.5.1 知识库支持"编译化"整理：将分散的需求知识编译为结构化条目（`GET /api/knowledge/entries`），支持人工增删改。

2.5.2 知识条目可关联来源需求，支持引用上限与来源标注格式规范。

2.5.3 灰度开关 `KB_CRSR_ENABLED`（环境变量配置，非设置页控件）：控制功能点权威完整版 SRR（CRSR）的使用；关闭时回退到子 SRR。

2.5.4 知识库缓存（kb_cache）：高频查询结果缓存，提升问答响应速度；缓存须在知识更新时失效。

### 2.6 评审报告与提示词进化

2.6.1 评审报告（review-reports）：系统对生成质量做周期性评审，输出问题清单，支持问题采纳（`POST /api/review-reports/{report_id}/issues/adopt`）。

2.6.2 提示词进化（prompt-evolution）：基于评审结果生成提示词候选版本，支持激活（`POST /api/review-reports/prompt-evolution/{record_id}/activate`）。

2.6.3 提示词历史（`GET /api/admin/prompts/{module}/{name}/history`）：记录每次提示词变更，支持回滚。

### 2.7 用户通知与告警

2.7.1 管理员通知（AdminNotification）：LLM 供应商禁用、全败告警等关键事件产生通知，支持标记已读（`POST /api/settings/notifications/read`）。

2.7.2 项目待归档/取消待归档（`/pending-archive`、`/cancel-pending-archive`）：项目归档支持两阶段确认，降低误操作。

2.7.3 项目重新激活（`/reactivate`）：已归档项目可恢复为活动状态，需求与知识关联保持。

### 2.8 管理员看板

2.8.1 管理员看板（`GET /api/products/admin/dashboard`）：展示产品数、项目数、需求数、用例数、知识库统计等总览。

2.8.2 系统资源监控（`GET /api/observability/system-resources`）：CPU、内存、推理份额实时监控，首页透出。

2.8.3 LLM 调用日志（`GET /api/admin/llm-logs`）：记录每次 LLM 调用的耗时、tokens、成功/失败，供成本与质量分析。

## 3. 非功能需求（本轮补充）

3.1 知识库累积：第二轮需求引用第一轮已归档规则时，KB 命中率应高于第一轮的首次命中率（越用越好用）。

3.2 并发：支持 3 个用户同时上传不同需求并走澄清流程，不得报错、超时、数据库冲突或死锁。

3.3 多用户权限隔离：普通用户不得访问其他用户不可见产品的数据；管理员可见全部。

3.4 缓存一致性：知识条目更新后，相关查询缓存须在 60 秒内失效。

## 4. 验收标准

- 第二轮需求能命中第一轮归档的知识并正确复用（KB 累积生效）。
- 多人协作冲突被正确检测，不静默覆盖。
- 语义去重误删率 < 5%，去重留痕可审计可恢复。
- 多模态图片识别正确，图标语义识别准确。
- 影响分析能检索出跨需求的受影响功能点。
- 3 用户并发上传无异常。
