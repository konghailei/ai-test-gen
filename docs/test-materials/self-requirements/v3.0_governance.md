# AI-Test-Gen 平台 — 系统需求文档 v3.0（第三轮：稳定性、可观测与边界治理）

> 产品：AI-Test-Gen 平台（本系统）
> 用途：**自证测试（self-dogfood）** 第三轮 —— 覆盖系统的稳定性保障、可观测性、
> 并发/资源治理、异常处理与边界细节，是"小功能点"的集中补充轮。
> 版本：v3.0（治理版）

## 1. 本轮背景

第一轮覆盖核心链路，第二轮覆盖协作与治理增强。本轮聚焦**稳定性、可观测性与边界治理**——这些"小功能点"在前两轮中描述密度低，容易被生成器遗漏，本轮集中补充，用于验证系统对细粒度功能点的提取与用例覆盖能力。

## 2. 本轮新增/细化功能需求

### 2.1 长任务稳定性

2.1.1 事件循环卡顿看门狗（loop_watchdog）：以 100ms 采样事件循环延迟，超过 0.5s 记 warn、超过 3s 记 error；超阈值时采样全线程 Python 调用栈（用于定位同步阻塞）。指标经 `GET /api/health` 的 `data.event_loop` 透出（字段 max_lag_ms、warn 次数、error 次数）。

2.1.2 LLM 调用执行器隔离（llm_executor）：LLM 调用在专用常驻执行线程 + 常驻事件循环中运行，避免库内部同步代码（如 litellm 流处理）阻塞主事件循环。`GET /api/health` 的 `data.llm_executor` 须显示 `enabled: true, isolated_loop: true`。

2.1.3 占位阻塞守卫：静态检查（AST 守卫）禁止在 `async def` 内裸调同步阻塞调用（`vector_store.*`、`reranker.*` 及含同步阻塞的嵌套助手）；CI 拦截，防止回退。

2.1.4 分析任务看门狗（task_watchdog）：定期扫描超过 60 分钟未更新的 running 任务，标记为 stale；进程重启后所有 running/pending 任务标记为 interrupted，卡在 analyzing 的需求联动回退为 draft。

2.1.5 任务取消：需求分析与用例生成任务均支持取消，取消须真正终止资源占用（不残留并发槽位）。

### 2.2 生成并发与资源治理

2.2.1 资源感知并发控制（v4.0.2）：根据 CPU 逻辑核数、物理核数、可用内存动态计算推理份额（`inference_share`），资源紧张时生成任务排队而非直接失败。

2.2.2 首页服务器资源监控：实时展示 CPU、内存、推理份额占用；生成排队时前端显示队列位置。

2.2.3 生成互斥：同一需求同时最多一个 pending/running 的生成任务（DB 层部分唯一索引 `uq_analysis_tasks_active_generation` + 事务内 advisory lock 双重保障）。

2.2.4 并发 FP 生成时，本地模型推理的 CPU/GIL 争抢须控制在可接受范围（事件循环 warn 级卡顿 < 2.2s）。

### 2.3 向量化一致性

2.3.1 向量写入出箱（vector_outbox）：PG 事务与 Milvus 写入解耦，PG 侧记录待写入向量，异步消费者投递到 Milvus，保证最终一致。

2.3.2 出箱状态可观测（`GET /api/observability/vector-outbox`）：展示待处理/已处理/失败数量。

2.3.3 孤儿向量对账（scan_orphan_vectors）：定期扫描 Milvus 中存在但 PG 中已删除的向量，标记待清理。

2.3.4 向量化失败须记录 `vectorization_error`，且不得静默丢弃（用例级向量化状态与需求级对齐）。

2.3.5 `revision` 字段类型为 BIGINT（毫秒时间戳约 1.8e12），禁止用 INTEGER（int32 溢出）。

### 2.4 错误处理与降级

2.4.1 死信队列：流水线意外异常（非系统主动拒绝）进入死信队列供排查。系统主动拒绝的请求（降级结构、检查点后端不可用、需求状态非法）不进入死信队列。

2.4.2 降级标记透传：所有静默失败路径（FP 拆分失败、向量化失败、影响分析降级、分片审核部分失败等）须记录 degraded_flags 并在完成事件中透出。

2.4.3 分片审核 fail-closed：审核分片部分失败时，未审核用例不得自动通过，review_status 标记为 partial，未审核的 fp_ids 记录到 `unreviewed_fp_ids`。

2.4.4 LLM 全败处理：某提供商连续失败达到阈值触发熔断并禁用 600 秒，同时产生管理员告警通知。

2.4.5 鉴权失败（401/403）时立即禁用对应提供商，不重试（避免无谓调用）。

### 2.5 检索质量与边界

2.5.1 混合检索 RRF 融合：向量路与 BM25 路结果经 RRF 融合，融合结果标记来源类型（`_score_kind`），用于区分相似度量纲。

2.5.2 相关度门槛仅作用于向量路：BM25 路的 similarity 是 PG ts_rank（量纲不可比），不得施加同一阈值，否则在 Milvus 不可用降级时会把结果滤空。

2.5.3 Milvus 不可用降级：Milvus 不可用时回退为仅 PG 检索（`kb_status` 标记降级），保证知识问答基本可用。

2.5.4 检索结果脱敏开关：`KB_REDACT_SENSITIVE`（总开关）、`KB_REDACT_PII`（PII 子开关）。

2.5.5 澄清答案质量：系统 `default_answer` 不得为伪答案（复述问题），推导不出具体值时留空。

### 2.6 提示词与配置

2.6.1 生成任务总调用预算 240 秒；单次 LLM 调用有首响应超时与空闲双超时。

2.6.2 提示词覆盖：各环节提示词（fp_agent、gen_agent、clarify_agent、review_agent 等）均可在管理页覆盖，运行时热加载。

2.6.3 配置项（如 `KB_QA_MIN_SIMILARITY`、`KB_CRSR_ENABLED`、`DEDUP_EMBED_WORKERS`）须有明确默认值与回退语义，禁止"声明了但无消费方"的假配置。

### 2.7 数据库 Schema 演进

2.7.1 系统启动时自动检测 ORM 模型与实际数据库 schema 的差异，对新增表执行建表、对已存在表补缺失列。

2.7.2 建表/补列须幂等（重复启动不报错）：`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`。

2.7.3 需求子目录/表结构变更须保持向后兼容，存量数据不丢失。

### 2.8 前端交互边界

2.8.1 XMind 编辑页支持全屏编辑（不支持原生全屏的环境降级为沉浸模式）、撤销/重做、本地草稿（localStorage）。

2.8.2 草稿须在保存成功后清除；刷新页面时询问是否恢复草稿（StrictMode 下不得弹两次）。

2.8.3 窗口缩放时画布须重算尺寸，不得固定不动。

2.8.4 编辑节点标题时按 ESC 只退出编辑，不得连带退出全屏。

2.8.5 脏数据容错：空 type / 空标题用例不产生空标题节点，类型标签省略而非显示"其他"。

## 3. 非功能需求（本轮补充）

3.1 空闲时事件循环最大卡顿 < 100ms，warn/error 计数为 0。

3.2 生成期间 health P95 < 2s、login P95 < 5s、cancel 可达。

3.3 数据一致性：PG 与 Milvus 的向量最终一致，出箱积压可观测。

3.4 幂等性：系统重启、重复初始化、重复归档请求均须幂等。

3.5 可观测性：关键指标（事件循环、LLM 执行器、向量出箱、资源占用）均可通过接口查询。

## 4. 验收标准

- 生成期间其他 API 端点保持可用（§A 三条验收通过）。
- 事件循环看门狗正常工作，空闲 max_lag_ms < 100，error 为 0。
- 语义去重留痕完整，误删可恢复。
- 向量出箱最终一致，无孤儿向量长期残留。
- 所有降级路径均有可见标记，无静默失败。
- 数据库 schema 演进幂等，存量数据不丢失。
- XMind 编辑页所有交互边界正常。
