# AI-Test-Gen 平台 — 系统需求文档 v1.0（第一轮：核心全流程基线）

> 产品：AI-Test-Gen 平台（本系统）
> 用途：**自证测试（self-dogfood）** —— 用本系统的需求文档喂给本系统，走完整 11 步流程生成测试用例，
> 再用生成的用例反过来验证系统自身功能的正确性。
> 版本：v1.0（基线版，系统核心功能全貌）
> 对应系统版本：v4.0.2
> 优先级：P1

---

## 1. 项目背景

构建"需求驱动的 AI 测试用例自动生成平台"，把自然语言需求文档转化为可执行、可审核、可追溯的测试用例。本版本覆盖平台核心链路：需求上传 → 解析 → 澄清 → 确认 → 影响分析 → 用例生成 → 审核 → 归档向量化 → 知识库问答。

## 2. 用户角色

| 角色 | 职责与权限 |
|---|---|
| 管理员 | 全部功能：产品/模块/用户/角色管理、LLM 配置、知识库治理、删除操作、系统可观测 |
| 普通用户 | 需求上传、澄清回答、需求确认、用例生成与编辑、项目创建、归档、知识库问答 |
| 只读用户 | 查看列表与详情、知识库问答；无任何写权限 |

权限规则：基于角色的菜单权限控制；产品可配置可见用户列表，为空表示全员可见；未认证（未提供/无效令牌）返回 401，已认证但无权限返回 403。用户密码加盐哈希存储；登录连续失败达到 5 次锁定账号 30 分钟；会话令牌有效期 8 小时，过期需重新登录。

## 3. 功能需求

### 3.1 产品与项目结构管理

3.1.1 产品管理：管理员可创建产品。产品名称必填且长度 1-128 字符，系统内名称唯一，重名创建时提示"产品名称已存在"并拒绝。产品可填写描述（最长 1024 字符）。删除产品前系统展示关联数据统计（项目数、需求数、用例数）供确认，删除为级联删除，且仅管理员可执行。

3.1.2 项目管理：项目归属产品，名称必填（1-128 字符），版本号默认 1.0（最长 32 字符），同一产品内版本号不可重复，重复时创建失败并提示"该版本号已存在，请使用其他版本号"。项目支持"上线时间"属性（精确到秒），用于知识库检索排序与回归基线归属。

3.1.3 模块管理：模块归属产品，名称必填（1-64 字符），同一产品内模块名称唯一。模块间可建立依赖关系（默认类型 depends_on，强度默认 medium，取值 high/medium/low），以图谱可视化展示。功能点可归属一个或多个模块。

3.1.4 项目归档：归档以项目为单位发起。归档时项目下所有"已确认"状态的需求自动归档，归档触发需求知识入库（向量化）与功能点知识固化。已归档项目可重新激活。项目归档支持"待归档"两阶段：先标记待归档（可取消），再确认执行。

### 3.2 需求文档上传

3.2.1 支持上传 .md / .markdown / .docx / .txt 格式的需求文档，支持单次多文件上传。单文件大小不得超过 10MB，超限提示"文件超过大小限制"。

3.2.2 非文本文件（伪装扩展名）须拒绝：文本类文件按 UTF-8 解码（失败回退 GBK）；无法识别为有效文本的文件返回 400 错误。

3.2.3 上传时须指定所属产品与项目，填写需求标题（1-512 字符）与优先级（P0/P1/P2）。上传成功后系统创建异步分析任务，用户可在任务管理页查看进度。

3.2.4 docx 文档中的内嵌图片应支持识别：配置了视觉大模型时调用识别并输出图片内容描述；未配置时在解析文本中保留图片占位标记，不中断解析。

3.2.5 多文件上传（upload/multi）：一次请求可提交多个文件，逐个创建独立需求与解析任务，任一文件失败不影响其他文件。

### 3.3 需求解析与结构化（SRR/FP）

3.3.1 系统将需求文本解析为结构化的需求表示（SRR），包含：需求基本信息（标题/概述/角色）、主流程步骤、备选流程、业务规则、数据约束、角色权限等维度。

3.3.2 系统同步将需求拆分为功能点（FP）。每个功能点包含独立的子结构（子 SRR），承载该功能点内部的业务规则与数据约束；跨功能点的交互规则与共享约束保存在需求级总结构中。一条规则只在一处定义，不得重复。

3.3.3 表单/字段级校验规则不独立拆分为功能点，归入所属功能点的业务规则与数据约束维度。

3.3.4 同产品同模块下已存在同名功能点时，新需求通过"功能点复用"接口（`POST /api/requirements/{req_id}/fp/reuse`）复用该功能点定义，不重复生成。

3.3.5 功能点拆分失败时解析主流程不中断，但须在任务结果中记录降级标记（`functional_points` 降级），供后续环节感知。

3.3.6 解析任务进行时，系统支持主动取消（`POST /api/requirements/tasks/{task_id}/cancel`），取消后任务转"已取消"状态且不残留运行中的资源占用。

### 3.4 需求澄清

3.4.1 解析完成后系统产出澄清问题。检测维度包括：需求完整性、表述歧义、内容遗漏、引用未定义（引用了文档中不存在的规则或字段）、同文档前后矛盾、多文档之间矛盾。

3.4.2 澄清优先查询知识库：系统能从知识库得到答案的问题自动补全（标记为已回答），无法回答的才转为人工澄清问题。每轮人工问题不超过 5 个。

3.4.3 澄清最多 3 轮。第 1 轮严谨回答提交后应无 critical/important 级追问（一轮收敛）；第 3 轮仍有问题时降级为 optional 强制放行，并在 SRR 标记 `_clarify_force_passed=true`。

3.4.4 澄清问题须去重：跨来源（知识库语义路 `llm_semantic.*` 与规则路 `prd.*`）产生的问题不得重复，重复率须低于 10%。

3.4.5 系统提供的"建议答案"（default_answer）仅为 AI 依上下文推断的参考，不得为复述问题的空话；推导不出具体值时该字段留空。

### 3.5 功能点审核与需求确认

3.5.1 功能点审核前置条件：功能点必须已分配至少一个模块，否则审核接口返回 409 并提示"功能点未分配模块，请先编辑该功能点并选择对应模块后再审核通过"。

3.5.2 审核结果分"通过"（approved）与"需复核"（reviewed）两类；需求确认前置条件为所有功能点均为 approved 且已分配模块。

3.5.3 需求确认（`POST /api/requirements/{req_id}/confirm`）：需求状态由 pending_review 流转为 confirmed。需求状态流转为：analyzing → draft（有澄清问题）→ pending_review（无问题或强制放行）→ confirmed → archived。

3.5.4 已确认（confirmed）的需求可发起用例生成；已归档（archived）的需求不可直接生成，需先 resume 续跑。

### 3.6 用例生成

3.6.1 用户在需求确认后发起用例生成（SSE 流式）。生成任务为分钟级长任务，生成期间须上报阶段进度（分析影响 → 分片生成 → 质量闸门 → 审核）。

3.6.2 生成期间系统其他 HTTP 端点须保持可用：`GET /api/health` P95 延迟 < 2s、`POST /api/auth/login` P95 < 5s、任务取消端点可达（不得超时）。

3.6.3 用例类型覆盖：功能（functional）、边界（boundary）、异常（exception）、安全（security）、集成（integration）、回归（regression）、性能（performance）、探索性（exploratory）。

3.6.4 每条用例须包含：标题、类型、优先级（P0/P1/P2）、前置条件、操作步骤（含每步预期）、顶层预期结果（expected）、断言（assertions）、备注（notes）。

3.6.5 用例生成的语义去重：同批次内跨功能点的等价用例不得重复产出，去重采用分层闸门（结构护栏 + LLM 窄带裁决），去重删除须留痕（`dedup_removals` 表可审计可恢复）。

3.6.6 生成任务的检查点必须持久化到 PostgreSQL；持久化不可用时生成请求直接拒绝并明确报错，禁止降级为内存存储。

3.6.7 生成并发控制：系统根据服务器资源（CPU/内存）动态调节并发度，资源紧张时排队而非直接失败，并在首页透出服务器资源监控。

### 3.7 用例审核与编辑

3.7.1 生成的用例经审核环节标记为"通过"（approved）或"待复核"（reviewed）。审核分片失败时采取 fail-closed 策略：未审核的用例不得自动通过。

3.7.2 用例支持人工编辑（`PUT /api/testcases/{case_id}`）：可修改标题、步骤、预期、类型、优先级等字段。

3.7.3 用例支持反馈（`POST /api/testcases/{case_id}/feedback` 与批量反馈），反馈内容用于质量改进。

3.7.4 用例可导出为 XMind 与 Markdown 格式；导出树结构与页面分组一致（功能测试组 = functional + boundary + exception + exploratory；integration 展示为"场景测试"；regression 独立分组）。

3.7.5 用例分类型分组展示：细分类型经标题前缀保留（如 `[P0][边界值]`），不得出现英文原始值外泄。

### 3.8 影响分析

3.8.1 影响分析以功能点为入口（`GET /api/products/{product_id}/fp/impact`），基于依赖图谱以 BFS 方式计算受影响的上下游功能点。

3.8.2 影响分析须检索出与变更相关的功能点，依赖图谱覆盖变更相关功能点；分析结果可在需求级（`POST /api/requirements/{req_id}/impact-analysis`）确认落库（确认为 `POST /api/requirements/{req_id}/impact-analysis/confirm`）。

3.8.3 功能点依赖关系支持版本化管理：变更时冻结为历史版本，支持版本间差异对比（`GET /api/products/fp/dependency-versions/{v1}/diff/{v2}`）。

### 3.9 知识库与向量化

3.9.1 归档触发知识入库：需求级向量与功能点级向量均写入 Milvus。需求级向量 metadata 含 type=requirement/project_id/product_id/status；功能点级向量 metadata 含 type=functional_point/fp_id/module_id。

3.9.2 向量化状态追踪：需求、功能点、用例均有 `vectorization_status`（pending → completed，无 failed）。向量写入走事务性出箱（PG → Milvus outbox），保证一致性。

3.9.3 知识库统计（`GET /api/knowledge/stats`）：每归档一个项目，总 SRR 向量 +1、功能点向量 +N。

3.9.4 知识库支持诊断（`GET /api/knowledge/diagnostics`）与用例质量报告（`GET /api/knowledge/case-quality-report`）。

### 3.10 知识库问答

3.10.1 知识库问答（`POST /api/knowledge-qa/ask`，SSE 流式）：用户提问后系统检索知识库并生成带来源标注的回答。

3.10.2 检索采用混合检索（向量 + BM25）与 RRF 融合；向量路结果设相关度下限（默认 0.50），低于阈值的噪声来源须被过滤，避免"展示来源却答未找到"的自相矛盾。

3.10.3 多历史版本时须按最新版本回答（依 go_live_date / project_version），不取最旧版本。

3.10.4 提问长度上限 500 字符，前端输入框直接限制并显示计数（n/500），后端同口径校验（超限返回 422）。

3.10.5 回答正文、claims、来源展示均须脱敏：密钥/token（`sk-*`、JWT、Bearer、key=value 形式的 api_key/token/secret/password）为硬要求；PII（手机号/身份证/邮箱）为可选超集。

3.10.6 知识问答支持追问（`/chat`）、历史记录（`GET /api/knowledge-qa/history`）与删除历史。

### 3.11 知识库纠正

3.11.1 用户可对知识问答的答案发起纠正（`correction`），系统记录纠正状态（none/pending/approved/rejected）、纠正模块、纠正目标（需求级或功能点级）。

3.11.2 纠正审核流：纠正提交后进入待审核队列（`GET /api/knowledge-qa/corrections`），审核通过后纠正内容回写知识库。

3.11.3 LLM 失败的问答记录（answer_status=failed）不得进入纠错候选；记录须含 error_message。

### 3.12 系统管理

3.12.1 用户与角色：管理员维护用户账号与角色分配；角色通过菜单权限数组控制功能可见性。系统初始化时内置管理员账号、默认产品与测试模式库。

3.12.2 大模型配置：支持配置多个大模型提供商，API Key 加密存储（展示时脱敏为前 3 后 4 位），可设置主提供商，配置即时生效，提供连通性测试（`POST /api/settings/llm/test`）。支持思考模式开关与自定义思考参数。

3.12.3 调用保护：大模型调用异常时熔断（连续失败停止调用并自动恢复），支持指数退避重试与多提供商自动切换；单次生成任务总调用预算 240 秒；鉴权失败（403/401）时立即禁用对应提供商 600 秒。

3.12.4 提示词管理：各环节提示词模板可在管理页查看与覆盖修改，保存于数据库运行时加载，支持一键恢复默认与历史版本查看。

3.12.5 任务管理：需求分析与用例生成任务统一在任务页展示状态（运行中/已完成/失败/已中断/已中止/已取消）、进度与结果摘要。

3.12.6 可观测：系统提供服务器资源监控（`GET /api/observability/system-resources`）、任务链路追踪（`GET /api/observability/trace/{task_id}`）、向量出箱状态（`GET /api/observability/vector-outbox`）。

3.12.7 操作日志：关键操作记录审计日志，详情为结构化数据。

## 4. 非功能需求

4.1 所有列表接口分页大小上限 100；`page_size` 小于 1 或大于 100 时返回 422（参数校验拒绝，不做静默截断，避免回显值失真）。

4.2 接口限流：默认每分钟 60 次，超限返回 429。

4.3 部署形态：Docker Compose 单机全栈，组件含应用服务（API）、前端、PostgreSQL（含中文分词扩展 zhparser）、Milvus 向量库、Redis、Celery 异步任务、MinIO 对象存储、etcd。

4.4 生成任务的断点检查点必须持久化到 PostgreSQL；持久化不可用时生成请求直接拒绝并明确报错，禁止降级为内存存储（重启丢失断点）。

4.5 所有静默失败路径必须记录降级标记并在完成事件中透出，前端可据此提示用户。

4.6 性能：生成期间 health 端点 P95 < 2s；空闲时事件循环最大卡顿 < 100ms。

4.7 安全：跨域白名单、生产环境关闭接口文档、启动时校验密钥配置。

## 5. 验收标准

- 完整走通"上传 → 解析 → 澄清 → 确认 → 用例生成 → 审核 → 编辑 → 导出 → 归档 → 问答 → 纠正"全流程。
- 澄清第 1 轮严谨回答后无 critical/important 级追问（一轮收敛）。
- 生成的用例覆盖全部功能点要点，类型分布含功能/边界/异常/安全。
- 归档后知识库问答能命中刚归档的需求知识并正确标注来源。
- 影响分析能检索出变更相关的功能点并生成正确的依赖图谱。
- 知识库纠正能正确回写并生效。
- 全流程各阶段降级/失败均有可见标记，无静默失败。
