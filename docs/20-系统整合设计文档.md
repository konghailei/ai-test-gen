## 1. 整体架构

### 1.1 五层架构

```
接入层    Web UI (React 18 + Vite) ｜ API (FastAPI, /api 前缀) ｜ L1 防护：RPM 限速 + JWT + RBAC
   ↓
编排层    LangGraph DAG 流水线（parse→prepare→gate→impact→test_design→generate→review）
          L2 防护：断路器 + 指数退避重试 + 多提供商故障转移
   ↓
引擎层    Prompt / Embedding(bge-large-zh) / RAG(混合检索) / Format / Quality 引擎
          L3 防护：UTCF Schema 校验 + LLM-as-Judge 抽样
   ↓
数据层    PostgreSQL(16+ 表, zhparser) ｜ Milvus(5 Collection) ｜ Redis(DLQ/Celery)
          L4 防护：事务性出箱 + DLQ + 幂等守卫 + fail-closed
```

### 1.2 服务拓扑

Docker Compose 单机全栈 8 容器：`backend`(FastAPI:8000)、`frontend`(Vite build)、`postgres`(:5432, ai_test_gen 库)、`milvus`(:19530)、`redis`(:6379)、`celery_worker`、`attu`（Milvus 管理界面，可选）、`minio`（Milvus 依赖存储）。

镜像分层：`ai-test-gen-base`（依赖层，Dockerfile.base 带构建期硬校验）→ `backend`（仅 COPY 代码）。**依赖变更必须重建 base 镜像**（日常 `up -d --build` 永不装依赖）。

## 2. Agent 流水线设计

### 2.1 编排器（orchestrator.py）

LangGraph StateGraph，生成链路 8 节点：

```
START → parse → select_channel(key 保留，内部 _prepare_node)
   → [enable_clarify?] clarify → gate
   → [impact?] impact → test_design → generate → review → END
条件边：gate 未通过且轮次<3 → 回 clarify；达上限强制放行(forced_pass)
```

关键设计：

- **state 字段必须显式声明**——LangGraph 未声明字段被静默过滤（历史上断点续跑因此从未生效，v3.4 修复）。
- SSE 事件统一 `event=message`，`data.stage` 标阶段；进度：parse 20 / prepare 25 / clarify 30 / gate 40 / impact 50 / test_design 62 / generate 70 / review 90 / done 100。
- `_producer` 不吞异常：astream 异常经队列传消费循环，yield error 事件（防"假完成 0 用例"）。

### 2.2 Agent 职责

| Agent | 职责 | LLM |
|---|---|---|
| ReqAgent | 原始文本 → 总 SRR + FP 列表（各带 sub_srr） | ✓ |
| ClarifyAgent | 规则层检测（引用未定义/跨节矛盾/PRD 专项/原型专项）+ LLM 语义检测 → KB 自动补全 → 人工问题 | ✓ |
| ImpactAgent | 优化需求的影响范围（双向 BFS）+ 生成指导 | ✓ |
| TestDesignAgent | 测试设计蓝图（技术触发规则）+ 回归装配 RTS | ✗ 零 LLM |
| GenAgent | FP 定向生成（六阶段，见 §4.3） | ✓ |
| ReviewAgent | 多因子置信度 + 规则预检 + LLM 六维审核 + KB 回流 | ✓ |
| QualityGate | 门禁组件（非 Agent）：Schema/关键字段/评分阈值/Critical | ✗ |

## 3. 需求分析链路设计

### 3.1 双 SRR 分层（v2.0 核心架构）

- **总 SRR（interaction_srr）**：跨 FP 交互规则、共享业务规则、契约。要点抽取只含 happy_path / alternate_flows / precondition / shared_rule 四类。
- **FP 子 SRR（sub_srr）**：FP 内部流程/规则/约束，含 business_rules 与 data_constraints（v2.48 从总 SRR 下沉至此）。
- 一条规则只在一处定义；覆盖率分母与生成必覆盖清单同源（`utils/coverage.py:collect_points`）。

### 3.2 澄清子系统（ClarifyAgent）

三层检测管线：

1. **规则层（确定性）**：引用未定义预扫描注入 hint、跨节矛盾、PRD 新建功能专项（上限处理/降级触发/风险-能力一致性）、原型类问题模板。规则层产出必须确定性到达消费方（不得只当 LLM 提示词线索）。
2. **LLM 语义层**：完整性/歧义性/遗漏；检测前移至 KB 查询之前。
3. **KB 补全分流**：completeness/ambiguity 类先查 KB，能答自动补全（answered=true），答不出转人工；conflict 类直接人工。人工问题 ≤5/轮。

轮次控制：MAX_CLARIFY_ITERATIONS=3；第 3 轮强制放行置 `_clarify_force_passed`（文档结构性缺陷信号，登记缺陷清单回补文档，不靠加轮次消化）。多轮收敛禁止发散（v3.0.1）：后续轮只问新增主题，不重复已答主题。

### 3.3 状态机与守卫

```
analyzing → draft →(澄清完成/强制放行)→ pending_review →(confirm)→ confirmed →(项目归档)→ archived
confirm 守卫：降级标记（_finalize_degraded/_clarify_degraded/_recheck_skipped）拒绝；
              所有 FP approved 且已分配模块。
regenerate：extra_notes 追加 → 当前 SRR 快照入 _version_history → 重新解析。
```

## 4. 用例生成链路设计

### 4.1 入口守卫（六道，顺序执行）

404 需求存在 → 403 产品可见 → 409 status=confirmed → 409 影响分析全确认 → 400 SRR 非空（禁回退 raw_text）→ 409 并发互斥。

### 4.2 并发互斥（task_guard.py，v3.4）

同一事务内：`pg_advisory_xact_lock` → 僵尸回收（running 且 updated_at>6h → interrupted）→ 活动检查 → 插入任务；DB 层 partial unique index 兜底。失败分类：仅唯一索引冲突算 409 conflict，其他 DB 错误 500。resume 同受互斥。

### 4.3 GenAgent 六阶段

1. **KB 轻量检索**：同模块 approved 用例 Top-3 作 Few-shot。
2. **测试模式库检索**：向量搜 patterns Top-3（`asyncio.to_thread` 包裹避免阻塞事件循环）。
3. **Prompt 构建**：动态最小用例数（`ceil(主流程/3)+备选流+规则+数据字段数`，P0/P1 取 max(下限, 要点×0.6)，封顶 40）作硬约束；FP 定向时 pop 掉 points 强制限范围。
4. **LLM 调用**：temperature=0.4，max_tokens=32768，允许数组输出。
5. **后处理**：编号 `TC-{模块}-{批次}-{序号}`、要点标注兜底回填（3-gram，min_ratio=0.35）。
6. **去重合并**：四级去重（精确/语义/子集/LLM 等价）→ 跨子轮语义去重（整例 embedding ≥0.92 且数字集合相同才合并——数字护栏防"1-200 字符"与"1-500 字符"被误并）→ merge_regression_cases 并入 RTS 基线 → 覆盖率统计（基于合并后终集）。

### 4.4 三条生成通道

| 通道 | 触发 | 行为 |
|---|---|---|
| 逐 FP 分片（主） | FP 非空 | 每 FP 独立生成；单 FP 失败不阻断；每 FP 完成写 checkpoint |
| 全量兜底 | FP 为空 | 单次全量生成（防 0 用例静默） |
| 跨 FP 集成 | 存在 cross_fp_flows/shared_rules | 独立生成 integration 类型 |

### 4.5 测试设计技术触发（TestDesignAgent，规则非 LLM）

| 技术 | 触发条件 | 生成要求 |
|---|---|---|
| 等价类+边界值 | constraints 含范围符号（`-`/`~`/`至`/`≤`…） | min-1~max+1 六点 |
| 决策表 | ≥2 条 validation/business/workflow 规则 | 2^n 组合合并 |
| 状态迁移 | 备选流含状态关键词（锁定/禁用/过期/超时…） | 正向全转换+反向非法 |
| 场景法 | 主+备选流并存，或共享规则+FP≥2 | 基本流+备选流组合 |
| 错误推测 | 必填/长度/金额类字段 | 空值/超长/负数，截 15 条 |
| 正交/因果图 | **无触发器** | 适用性恒 false（已知设计现状） |

### 4.6 审核与回流（ReviewAgent + persist_to_kb）

- 置信度公式：`match×0.4 + completeness×0.3 + consistency×0.2 + self×0.1 + pattern_bonus`（match 来自同产品向量 Top-3）。
- 分级入库：≥0.70 approved（出箱投递向量）；0.60-0.70 reviewed（人工确认）；<0.60 或 blocker → error_cases。（0.70 阈值为 v3.5 自 0.85 下调：冷启动理论上限 0.6-0.7，0.85 永不可达。）
- 回流前标题级去重（跨子轮重复防线）；savepoint 逐条隔离。
- 补生成闭环 ≤1 次：uncovered 按 FP 分组定向补生成 → 二次 review → 仍不达标 supplement_exhausted。

### 4.7 可靠性机制（v3.4 收口）

- **断点续跑**：checkpoint 含输入指纹（req_id/product/revision/srr_sha256/fp_set_sha256/prompt_version/model/schema_version），续跑前重算比对，不一致 409；显式 fallback_to_restart 才弃断点。checkpoint 后端强制 postgres，初始化失败 fail-closed 拒绝（不静默降级 memory）。
- **事务性出箱（vector_outbox）**：PG 业务行与投递意图同事务；relay 至少一次幂等投递 Milvus；聚合类型白名单 `("test_case","requirement","fp_crsr")`。Milvus 抖动不再判发布不完整（自愈），仅入箱失败计 vector_write_failed。
- **发布门禁（publication_policy）**：`decide_publication()` 纯函数唯一决策点；persist_to_kb 副作用边界二次校验。
- **done 事件**：透出 srr/cases/review_report/point_coverage/consistency_check/regression_reuse_summary/degraded_flags/manual_action_required/duration_ms。

## 5. 知识库设计

### 5.1 存储与检索

- PG（权威层，各版本 SRR 不可变）+ Milvus（检索层）双存储；写入一律走事务性出箱。
- 混合检索：向量（bge-large-zh-v1.5，Top-K=20，阈值 0.70）+ BM25（zhparser）→ RRF 融合（含时间衰减，半衰期 180 天）→ Cross-Encoder 重排（bge-reranker-base）。硬过滤：product_id + status=archived。
- 嵌入与重排为本地 CPU 推理：async 路径必须 `asyncio.to_thread` 包裹。

### 5.2 CRSR 编译层（v3.5.0，对标 LLM Wiki）

三范式混合体：retrieve-first（混合检索）+ compile-first（CRSR）+ graph（FPDependency）。权威层级：L0 需求文档 > L1 FP/CRSR > L2 人工核准用例 > L3 AI 生成用例。

- **聚合规则**（fp_crsr.py `aggregate_crsr` 纯函数）：同名 FP 跨版本——标量字段取最新版本值；数组字段按签名（`_item_markers`）去重并集。
- **固化时机**：归档（products.py 归档链路）+ KB 纠错（knowledge_qa.py 纠错链路）→ `consolidate_crsr()` → 成功后**同事务**出箱入队（aggregate_type="fp_crsr"）。
- **向量 ID**：`CRSR-` + md5(product_id|fp_name) 前 16 位——确定性幂等，重复归档覆盖不堆积。metadata 必含 `type=fp_crsr`、`status=archived`（漏了被硬过滤永远检不到）、product_id、fp_name、version_count、latest_version_ref、consolidated_at。
- **消费方接线（5 处守卫）**：出箱白名单 T1 / KB 问答类型映射 T2（防 N-6 同款误标→孤儿过滤静默失效）/ 来源富化 T3 / prompt 采信规则 T4（最新整理版优先）/ 固化链路入箱 T5。灰度开关 KB_CRSR_ENABLED。
- **clarify KB 补全链路不接 fp_crsr**（有意设计）：clarify 的 doc_type="requirement" 定位是需求级补全，FP 粒度混入会导致补全粒度错乱（v2.8.53 决策）。

### 5.3 Lint 防腐自检（kb_lint.py，v3.5.0）

挂 main.py lifespan 周期任务（默认 24h，fail-open）。三查全只读：

| 查 | 逻辑 | 产出 |
|---|---|---|
| L1 CRSR 漂移 | 重算聚合 vs 固化行逐字段比对 | 漂移清单 → 人工确认后重新固化+出箱 |
| L2 跨版本矛盾 | 同 rule id 不同文本 / 同约束字段不同限制 | 矛盾清单（P1 矛盾标注的数据源） |
| L3 向量孤儿 | Milvus vs PG 对账 | 孤儿清单 → 人工确认修复 |

### 5.4 KB 问答（knowledge_qa）

SSE 按 event 名分派；done.data.answer_full 最全。来源富化标注类型（functional_point/fp_crsr/requirement）与权威层级；fp_crsr 显示"功能点名（最新整理版，聚合 N 个版本）"；prompt 规则：CRSR 与单版本冲突优先采信 CRSR 并标注，无 CRSR 时多版本以日期靠后为准。人工纠错 → 审核 → 回流 + CRSR 刷新 + 出箱。

## 6. 原型 HTML 解析设计

数据流：`upload/multi` → phase 0 解析循环（双入口对称：`_parse_uploaded_files` + 后台协程循环）→ `html_proto_extract.py` → BS4 解析 → 安全剥离 → 语义树 YAML + 表格 Markdown → `【原型：文件名】` 拼接进 combined_raw → ReqAgent（ui_rules 映射）→ ClarifyAgent（原型专项问题）。

核心机制：

- **安全剥离**（强制）：script/style/noscript/template decompose；on* 属性过滤；javascript:/data:text/html 链接剔除；iframe/object/embed 剔 URL 标 [external]；注释剔除。
- **语义树**：ARIA 角色映射（textbox/checkbox/radio/combobox/button/link/table/dialog…），表单约束属性全保留（生成边界值用例依据）；字段命名 6 级优先级；表格转 Markdown。
- **归一化**：无名 img 丢弃；匿名容器压平（children 上提）；**HTML 注释不计为文本节点**（`Comment` 是 `NavigableString` 子类，必须过滤，否则深嵌套原型语义树膨胀 5 倍+）。
- **预算**：节点 ≤400（超限截断+标记）、墙钟 ≤10s（超时降级纯文本）、输出 ≤20K 字符；解析失败降级纯文本不阻断其他文件；纯壳页面 proto_no_semantics。降级标记全部入 degraded_flags 终态可见。
- **防注入**：原型内容按数据处理，指令类文字不执行。
- 依赖：beautifulsoup4 + lxml（装在 base 镜像，变更须重建 base）。

## 8. 稳定性与安全设计

| 层 | 机制 |
|---|---|
| 接入 | Token Bucket（60 RPM）、JWT 8h、RBAC、产品可见性隔离 |
| 编排 | 断路器三状态机、指数退避+全抖动、多提供商故障转移、LLM 总预算 240s、403/401 熔断 600s |
| 引擎 | UTCF Pydantic Schema 校验、QualityGate 动态阈值（冷启动 0.60/正常 0.75） |
| 数据 | 事务性出箱、DLQ（入口确定性拒绝不入队）、幂等 upsert、fail-closed 终态可见 |

安全：API Key Fernet 加密（响应脱敏前3后4）、PBKDF2-SHA256 密码、CORS 白名单、生产关 docs、启动密钥校验、中间件链 `CORS→logging→auth→rate_limit→路由→异常处理`。
