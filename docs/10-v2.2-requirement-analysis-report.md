## 1. 执行摘要

### 今日完成的核心工作

本次迭代（v2.0 → v2.2）围绕**需求分析质量**和**用户体验**两个维度，完成了 15 项改进：

| 维度 | 数量 | 核心收益 |
|------|------|---------|
| **架构重构** | 3 项 | 消除 SRR 规则重复；交互层与内部层职责分离 |
| **KB 增强** | 1 项 | KB 基线补全从"全量返回"升级为按维度精准回答 |
| **FP 增强** | 4 项 | 去重跳过 LLM 节省成本；模块多选提升灵活性；自动同步确保一致性 |
| **交互修复** | 4 项 | 按钮放开、版本切换、Object 显示、FP 重拆 |
| **稳定性** | 3 项 | DLQ 死信队列、一致性检查、轻量 KB 检索 |

### 量化影响

| 指标 | 之前 | 之后 |
|------|------|------|
| SRR 中规则重复 | 每条规则出现 2 次（总 SRR + FP SRR） | **0 次** |
| KB 基线补全回答长度 | 559 字符（全量 5 维度） | **~110 字符**（精准 1 维度） |
| 同模块 FP 重复 LLM 调用 | 每次全量生成 | **已存在名称跳过** |
| 重新生成后 FP 内部 SRR 是否更新 | ❌ 遗漏（本次修复） | ✅ 自动触发 |
| 历史版本显示 | `[object Object]` | **结构化渲染** |
| 生产环境写入失败恢复 | 无 | **DLQ 可追溯可重试** |

## 2. 需求分析全链路流程

### 2.1 端到端流程

```
上传需求 → ReqAgent 解析 → ClarifyAgent 澄清 → 确认/重新生成 → FP 管理 → 历史版本 → 归档
```

详细流程参见下图（已作为 SVG 渲染在本文档对应章节），以及文档 `docs/09-requirement-analysis-pipeline.md`。

### 2.2 7 大阶段总览

| 阶段 | 名称 | 关键组件 | 核心产出 |
|------|------|---------|---------|
| ① | 需求上传 | `upload_requirement` API | 原始文档入库，初始 status = `analyzing` |
| ② | 需求解析 | `ReqAgent.parse()` | **interaction_srr**（总 SRR = 交互层）+ **功能点列表**（含子 SRR） |
| ③ | 需求澄清 | `ClarifyAgent` + KB 检索 | 细化 SRR；KB 自动补全或人工问题列表 |
| ④ | 确认 / 重新生成 | `confirm` / `regenerate` API | 确认后解锁用例生成；重新生成触发 LLM 重解析 + 自动 fp_split |
| ⑤ | FP 管理 | FP CRUD + 审核 | 审核通过 → 可生成用例；编辑/合并/重生成/依赖图谱 |
| ⑥ | 历史版本 | `_version_history` + restore | 每次重新分析前自动快照；v2.2 支持一键切换 |
| ⑦ | 需求归档 | `archive` API | SRR 写入 Milvus 知识库；FP 锁定为只读 |

### 2.3 状态流转

```
upload → analyzing → draft → pending_review → confirmed → archived
                         ↑                               
                  ┌──────┘ (补充重新生成)               
                  │         ⭐ v2.2 所有非归档状态均可
                  │
              v2.2 restore: 任意状态 → 先快照当前 → 覆盖目标版本 → pending_review
```

## 3. v2.0 / v2.2 核心架构变更

### 3.1 双 SRR 分层架构（v2.0）

**问题**: 旧架构中，总 SRR 是全量规则（= 所有 FP 子 SRR 的并集），同一规则出现两次。

**方案**: LLM 一次性产出两份互不重叠的 SRR。

```
LLM 输出
├── interaction_srr (写入 Requirement.srr_json)      ← 总 SRR / 交互层
│   ├── cross_fp_flows:        FP 间调用顺序 + 数据契约
│   ├── shared_business_rules:  跨 ≥2 个 FP 的共享规则
│   ├── fp_contracts:           FP 间接口约定
│   ├── global_constraints:     全局性约束
│   └── acceptance_criteria:    跨 FP 验收标准
│
└── functional_points[] (写入 functional_points 表)   ← FP 内部层
    └── sub_srr:
        ├── flows.happy_path         FP 内部正常流程步骤
        ├── flows.alternate_flows    FP 内部异常分支
        ├── business_rules           FP 专属业务规则
        ├── data_constraints         FP 专属数据约束
        ├── acceptance_criteria      FP 专属验收标准
        └── test_hints               FP 测试提示
```

**原则**: 一条规则只在一处定义。单 FP → sub_srr；跨 FP → interaction_srr。禁止重复。

**文件变更**: `fp_agent.py`（prompt 新增交互层规则 + JSON 格式）、`req_agent.py`（解析 interaction_srr）、`requirements.py`（fp_split 使用 interaction_srr 更新 req.srr_json）

### 3.2 KB 基线补全精准化（v2.0）

**问题**: KB 基线补全对所有 5 种澄清问题（正常流程/异常流程/数据约束/业务规则/验收标准）都返回同一份 559 字符的完整 SRR 块，导致用户看到"全量回答"。

**方案**: 新增 `_detect_baseline_focus(question)` 函数，从问题文本识别关心的维度。

```
正常流程问题   → 关键词"流程/步骤/Happy" → 只返回 happy_path 块
异常流程问题   → 关键词"异常/边界/错误" → 只返回 alternate_flows 块  (先判异常再判正常)
数据约束问题   → 关键词"字段/类型/约束" → 只返回 data_constraints 块
业务规则问题   → 关键词"规则/校验/限制" → 只返回 business_rules 块
验收标准问题   → 关键词"验收/通过/满足" → 只返回 acceptance_criteria 块
```

**效果**: 回答长度从 559 字符降至 ~110 字符（80% 缩减），用户不再看到无关维度。

**文件变更**: `clarify_agent.py`（_detect_baseline_focus + _query_kb_for_answers + _verify_kb_answers + _apply_kb_answers 4 处改动）

### 3.3 FP 去重跳过 LLM（v2.0）

**问题**: 同模块的增量需求上传时，LLM 重新生成所有 FP——包括过往已生成过的同名 FP。

**方案**: 三级去重流水线。

```
上传新需求
 │
 ├─ ① 查询同模块已有 FP 名 (PG DISTINCT)
 │
 ├─ ② 注入 Prompt 硬约束:
 │     "以下功能点已存在，禁止重新生成，标记 reuse_existing: true"
 │
 ├─ ③ LLM 仅生成真正新的 FP
 │    (过滤 reuse_existing 条目)
 │
 ├─ ④ 复制已有 FP 到新需求 (新 ID + 原 sub_srr)
 │    + LLM 新 FP
 │
 └─ → 完整 FP 列表
```

**效果**: 减少不必要的 LLM 调用；同模块跨需求 FP 名称保持一致。

**文件变更**: `req_agent.py`（_fp_extract_from_raw）、`requirements.py`（fp_split 全量重拆分路径）

### 3.4 FP 模块多选（v2.2）

**问题**: FP 只能关联单个模块。功能可能同时涉及"用户中心"和"权限管理"两个模块。

**方案**: 模型层加 `modules` JSON 字段；前端改为多选复选框。

```
旧: module_id: "MOD-001" (单 FK)
新: modules: ["MOD-001", "MOD-003"] (JSON 数组，兼容旧 module_id)
```

**文件变更**: `models.py`、`FPUpdateRequest`、`FunctionalPoints.tsx`、`FPSRRViewer.tsx`、`client.ts`、`types/index.ts`

### 3.5 历史版本管理增强（v2.2）

**新增能力**:

1. **版本快照**: 每次重新分析前，原 SRR 完整快照存入 `_version_history` 数组
2. **Object 显示修复**: 规则/约束等对象字段不再显示 `[object Object]`，改为 `JSON.stringify` 兜底
3. **版本切换**: `POST /{id}/versions/{idx}/restore` — 当前 SRR 先行快照 → 目标版本覆盖

**状态保护**: 切换后 status 回退到 `pending_review`，需重新确认。原 SRR 不会丢失（已自动快照）。

## 4. 需求分析各阶段详解

### 4.1 阶段①: 需求上传

| 项目 | 说明 |
|------|------|
| **API** | `POST /api/requirements`、`POST /api/requirements/file`、`POST /api/requirements/multi` |
| **输入** | Markdown 文本 / ZIP 压缩包（含 .md + 图片）/ JSON |
| **流程** | 格式检测 → ReqAgent.parse() → 提取 FP → 保存 |
| **v2.0 增强** | ReqAgent 同时产出 interaction_srr + FP 列表；FP 提取时查已有名跳过 LLM |
| **状态** | `analyzing` → (成功) `draft` / (失败) `parse_failed` |

### 4.2 阶段②: ReqAgent 需求解析

| 项目 | 说明 |
|------|------|
| **文件** | `backend/app/agents/req_agent.py` |
| **核心方法** | `parse(raw_requirement, product_id)` |
| **输出格式** | `{ requirement: { title, summary, priority, modules }, flows: { happy_path, alternate_flows }, business_rules, data_constraints, acceptance_criteria, preconditions }` |
| **v2.0 增强** | 同步提取 FP（`_fp_extract_from_raw`）→ interaction_srr + FP 子 SRR |
| **v2.0 去重** | 查同模块已有 FP 名 → Prompt 硬约束 → 跳过 LLM |

### 4.3 阶段③: ClarifyAgent 需求澄清

| 项目 | 说明 |
|------|------|
| **文件** | `backend/app/agents/clarify_agent.py` |
| **入口** | `GET /{id}/clarify/questions` → 获取问题列表 |
| **提交流程** | `POST /{id}/clarify/answers` → 提交答案 → 重新解析 |
| **检测维度** | 完整性 (Checklist) / 歧义性 (LLM) / 遗漏 (模式对比) |
| **KB 自动补全** | 向量检索 → `_detect_baseline_focus` 精准定位维度 → 自动填充 (v2.0) |
| **人工问答** | KB 答不出 → 生成至多 5 个问题 → 人工回答 |
| **迭代限制** | 最多 3 轮 |
| **冷启动** | kb_empty=True → 深度人工澄清（5 个影响范围/边界/依赖问题）|

### 4.4 阶段④: 确认 / 重新生成

| 操作 | API | v2.2 变更 |
|------|-----|-----------|
| 确认完成 | `POST /{id}/confirm` | 无变化 — status → confirmed，解锁用例生成 |
| 补充重新生成 | `POST /{id}/regenerate` | **v2.2**: 重新解析后自动触发 `fp_split`（之前遗漏了 FP 内部 SRR 更新） |
| 版本快照 | (内置于 regenerate) | v2.0: 重新生成前原 SRR 自动入 `_version_history` |
| 按钮状态 | 前端 RequirementDetail | **v2.2**: draft / pending_review 状态也可点击「补充重新生成」（之前仅 active/confirmed） |

### 4.5 阶段⑤: FP 管理

| 操作 | API | 功能 |
|------|-----|------|
| 列表 | `GET /{req_id}/fp` | 按模块分组展示 FP + 子 SRR |
| 编辑 | `PUT /{req_id}/fp/{fp_id}` | 修改名称/**多模块**（v2.2）、子 SRR 字段 |
| 审核 | `PATCH /{req_id}/fp/{fp_id}/approve` | pending_review → approved |
| 重生成 | `PATCH /{req_id}/fp/{fp_id}/regenerate` | hint → LLM 重新生成该 FP 子 SRR |
| 合并 | `POST /{req_id}/fp/merge` | 多选 → LLM 合并为一个 FP |
| 删除 | `DELETE /{req_id}/fp/{fp_id}` | 级联删除依赖 |
| 拆分 | `POST /{req_id}/fp/split` | 全量重新拆分（v2.0: 复用已有 FP 名） |
| 依赖 | `GET /{req_id}/fp/dependencies` | FP 间依赖关系 |
| 图谱 | `GET /{product_id}/fp/dependency-graph` | 跨需求 FP 依赖可视化 |
| 影响 | `GET /{product_id}/fp/impact` | BFS 3 层影响分析 |

### 4.6 阶段⑥: 历史版本

| API | 功能 | v2.x 状态 |
|-----|------|-----------|
| `GET /{id}/versions` | 版本摘要列表（标题/时间/触发原因）| v2.0 |
| `GET /{id}/versions/{idx}` | 完整 SRR 快照（结构化渲染）| v2.2 修复 Object 显示 |
| `POST /{id}/versions/{idx}/restore` | 切换使用历史版本 | **v2.2 新增** |

### 4.7 阶段⑦: 需求归档

`POST /{id}/archive` → status → `archived` → SRR 写入 Milvus → FP 锁定只读 → 后续需求可基线参考。

### 5.2 相对于架构设计的优势

| # | 领域 | 实际实现 | vs 设计 |
|---|------|---------|---------|
| 1 | SRR 分层 | 交互层 + FP 内部层，零重复 | 设计未覆盖，实现更强 |
| 2 | FP 去重 | 同模块已有名跳过 LLM | 设计未覆盖，节省成本 |
| 3 | KB 补全 | 按维度精准返回 | 设计只说"相似度>0.85"，实现更精细 |
| 4 | 版本管理 | 自动快照 + 一键切换 | 设计未覆盖，用户价值高 |
| 5 | 模块选择 | FP 多模块关联 | 设计仅有 module_id，实现更灵活 |

### 5.3 仍弱于架构设计的地方

| # | 领域 | 差距 | 严重度 |
|---|------|------|--------|
| 1 | MatchAgent / KB 检索 | GenAgent 不再检索历史用例（v3.1 移除），跨需求用例复用丧失 | 🟡 |
| 2 | GenAgent 一致性检查 | 架构要求"多次生成方差 <10%"，代码空白 | 🟡 |
| 3 | 覆盖率矩阵 | 架构要求 FP/SRR 字段级覆盖率输出，未实现 | 🟡 |
| 4 | DLQ 死信队列 | 架构要求 Phase 2 实现，v2.2 已补充轻量版 ✅ | ✅ 已修复 |
