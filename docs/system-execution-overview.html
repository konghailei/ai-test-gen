从需求上传到用例入库的完整执行链路。核心约束一句话： 需求必须先「人工确认」才能生成；生成走 7 节点的执行 DAG；进有 6 道守卫，出有 3 档门禁； 中途每一步都可断点续跑，但输入指纹必须一致。

阶段一 · 需求分析链路

目标是把一份非结构化文档变成结构化的双层 SRR，并拿到人的确认。

1上传需求

ReqAgent

支持 docx / markdown / 图片（多模态识别）。产出双层 SRR：总 SRR（整体约束）+ 功能点 SRR（逐模块）。

2澄清问答

ClarifyAgent

先查知识库，查得到就自动补全、不再打扰人；查不到才生成问题。最多 3 轮，第 3 轮强制放行并打标记。

3待确认

pending_review

解析与澄清结果进入待确认态，人工在确认页核对 SRR 内容。

4人工确认

confirmed

确认后需求才具备生成资格。这是生成入口的硬门槛（守卫 3），未确认一律 409。

需求状态机：
draft→ analyzing→ pending_review→ confirmed→ archived⇄ active

澄清重解析会把需求退回 draft，需要重新确认；生成失败回退时也会回到 confirmed（而不是 draft），避免用户被迫重走整条确认链。

阶段二 · 用例生成 DAG（7 个执行节点）

LangGraph 编排，节点进度直接驱动前端进度条。主链路一条直线，唯一回边是审核后的补生成。

1需求解析20%

parse

加载 SRR 并校验非空。不调用 LLM，纯数据准备。

2生成准备25%

select_channel

构造本次生成的环节开关：是否启用影响分析、多类型生成与完整审核。

3质量门禁40%

gate

按评分与关键问题判定。未通过时不回环，直接强制放行进入影响分析。

4影响分析50%

impact

仅优化需求启用：沿原需求取历史用例，产出生成指引供下游注入。

5测试设计62%

test_design

零 LLM 调用。产出测试设计蓝图：技术适用性、边界与决策表目标等。

6用例生成70%

generate

按三条路径生成（见下），逐功能点落 checkpoint；单点失败不阻断。

7审核入库90%

review

置信度 + 规则预检 + LLM 六维审核 + 覆盖统计；必要时补生成一次。

回边说明：
  • 审核 → 生成：审核发现覆盖缺口才补生成，最多 1 次；二次仍缺则标记「补生成已用尽」，不让前端误以为还会继续补。

终点 done 100%：用例落库 + 知识库回流。

执行规范

三张表分别对应「进得来」「怎么生成」「出得去」。

入口 · 六道前置守卫

顺序校验项失败码说明
1需求存在404需求 ID 无效直接中断
2产品可见性403只能对自己可见产品下的需求发起生成
3状态为 confirmed409必须先走完 解析 → 澄清 → 人工确认

生成 · 三条路径

路径触发条件作用
逐功能点分片（主）功能点列表非空每个功能点用独立小 prompt 定向生成，质量最高；用例缺归属时补为对应功能点
全量兜底功能点列表为空一次性按整份 SRR 生成，防止功能点拆分失败的需求静默产出 0 条用例
跨功能点集成存在跨功能点流程 / 共享业务规则独立组装全局片段生成组合场景，类型归一为集成用例，避免拆分后丢失跨模块场景

出口 · 三档发布门禁

决策触发条件处置
自动发布覆盖证据与合同校验全部通过直接写入知识库并固化用例
人工审核覆盖情况未知，或存在警告项转人工审核队列，不自动入库
阻断合同校验失败拒绝入库并给出原因

门禁判定是纯函数（可单测、可复现），并在真正写库的副作用边界做二次校验，防止判定与写入之间状态漂移。

贯穿全程的五项机制

这些不是某个节点专属，而是整条链路都在生效的约束。

断点续跑

每个功能点完成即写检查点。检查点携带输入指纹（需求 ID、产品、修订号、SRR 哈希、功能点集合哈希、提示词版本、模型、合同版本），续跑前逐字段比对，不一致直接拒绝，避免把旧产物拼到新输入上。

容错策略

单个功能点生成失败不阻断整体，标记为失败并继续；续跑时会自动重试这些点。整体失败则落明确终态，不留下无提示的悬挂任务。

多层去重

生成器内部四级去重（精确 / 语义 / 子集 / 等价）→ 三条路径汇总时再做一次标题级去重 → 入库前对同标题只保留置信度最高的一条。

向量出箱

业务事务内只写意图，由独立的 relay 幂等投递到向量库并退避重试。业务提交不会因为向量库抖动而失败或产生不一致。

并发互斥

同一需求同时只允许一个生成任务：应用层原子占位 + 数据库唯一索引双保险。僵尸任务由看门狗按超时回收。
