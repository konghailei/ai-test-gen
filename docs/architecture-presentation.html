1. 系统定位与核心理念

我们要解决什么问题？

传统测试用例编写面临三大痛点：

📊 工作量大：一个中等规模需求（10+ 功能点）需要编写 50-100 条测试用例，手工编写耗时 2-3 天

🐛 覆盖不全：人工容易遗漏边界条件、异常路径、安全场景

🔄 重复劳动：相似需求的用例模式重复编写，缺乏积累复用

我们的解决方案

核心理念：闭环积累

系统不是一次性的生成工具，而是越用越聪明的知识系统：

  1. 上传需求文档 → AI 解析为结构化格式
  2. 检索知识库历史 → 补全缺失信息
  3. AI 生成测试用例 → 人工审核
  4. 审核通过用例入库 → 成为下次生成的参考
简单示例

第一次上传"用户登录"需求 → 生成 20 条用例 → 审核通过入库

第二次上传"用户注册"需求 → KB 自动检索到"登录"的历史用例 → 参考其模式生成"注册"用例（复用了密码校验、错误提示等模式）

为什么用 LangGraph？

LangGraph 提供了有状态的多步 Agent 编排能力：

  • 状态管理：PipelineState 在节点间传递
  • 条件路由：质量门禁通过→生成，不通过→回到澄清

  • 可视化：DAG 图可导出调试

稳定性保障：

  • 断路器（向量 DB 故障率 >20% 降级）

3.1 技术栈详解 — 数据库与存储

Milvus（向量数据库）

用途：语义相似度检索

核心场景：

  • ClarifyAgent 检索相似历史需求
  • GenAgent 检索 Top-3 相似用例作 Few-shot
  • ReviewAgent 检测重复用例

索引：HNSW（Hierarchical Navigable Small World）

维度：1024（bge-large-zh 模型）

为什么不用 PostgreSQL 的 pgvector？

Milvus 专为向量优化，10 万条以上检索性能远超 pgvector。但系统保留了 pgvector 作为降级方案——当 Milvus 故障时自动切换。

PostgreSQL（关系数据库）

用途：结构化数据存储 + 全文检索

核心特性：

  • JSONB 字段存储 SRR/用例 JSON
  • pgvector 扩展（向量降级备份）
  • zhparser 扩展（中文全文检索）
  • 22+ 张表，覆盖需求/用例/依赖/追溯

Redis + MinIO

Redis：L1 多级缓存 + Celery 消息队列 broker

MinIO：S3 兼容对象存储，存放上传的文档和导出产物

3.2 技术栈详解 — LLM 大模型

LLM 供应商策略

主模型：DeepSeek（默认）

  • 成本低（约为 GPT-4 的 1/10）
  • 中文理解能力强
  • 支持 128K 上下文（长需求文档）

备用模型：GPT-4o / Qwen

多模态模型：独立配置，用于图片识别

litellm 统一抽象层

通过 litellm.acompletion 统一调用所有供应商，切换模型只需改配置，不改代码：

# 切换供应商只需改环境变量
LLM_PROVIDER=deepseek  # 或 openai/qwen
# 代码完全不变
result = await llm_client.call_json(...)

4. Agent 协作流水线

系统的核心是 6 个 AI Agent 通过 LangGraph DAG 编排，形成完整的"需求→用例"生成流水线。

📄
ReqAgent
需求解析：将 docx/md 文档解析为结构化 SRR JSON。支持表格提取、多模态图片识别、FP 一体式提取。
🔍
ClarifyAgent
需求澄清：三级检测（完整性/歧义性/遗漏），KB 自动补全，未答问题转人工澄清。
🚦
QualityGate
质量门禁：动态阈值评分（默认 0.75 / 冷启动 0.60）。不通过则回到 ClarifyAgent 迭代。
🕸️
ImpactAgent
影响分析：模块依赖图 BFS（最大 3 跳），识别受影响的历史需求和用例，规划回归范围。
✍️
GenAgent
用例生成：多维度生成（功能/边界/异常/安全），KB Top-3 用例作 Few-shot 参考。
✅
ReviewAgent
用例审核：6 维度评估（完整性/去重/可执行/一致性/追溯/覆盖），多因子置信度计算。

4.1 Agent 流水线 — 完整流程

1
ReqAgent.parse() — 需求解析
上传 docx/md → 提取文本+表格+图片 → LLM 解析为 SRR JSON → 一体式提取 FP + 依赖关系
2
ClarifyAgent.clarify() — 需求澄清
规则检测 → KB 检索补全 → 字段冲突处理 → 未答问题转人工
3
QualityGate.check() — 质量门禁
Schema 校验 + 质量评分 → 通过？进入下一步 / 不通过？回到步骤 2（最多 3 轮）
↻
循环控制（最多 3 轮）
MAX_CLARIFY_ITERATIONS=3，第 3 轮仍不通过则 force_pass 强制放行
4
ImpactAnalysisAgent.analyze() — 影响分析
模块依赖图 BFS → 追溯矩阵定位 → 用例操作规划（update/add/delete/keep）
5

KB Top-3 用例 Few-shot → 多维度生成 → 置信度自评估
6
ReviewAgent.review() — 用例审核
规则预检 + LLM 6 维度审核 → 多因子置信度加权 → 需要补充？回到步骤 5
✓
FormatEngine + 回流存储
UTCF → Gherkin/pytest/Markdown 输出 → 向量 DB + PG 双写 → 进入知识库供下次使用

4.2 LangGraph DAG 编排器详解

DAG 节点与路由

# orchestrator.py 核心结构

PipelineState = TypedDict:
    srr: dict          # 需求 SRR
    questions: list    # 澄清问题
    gate_passed: bool  # 门禁是否通过
    iteration: int     # 澄清轮次
    test_cases: list   # 生成的用例

# DAG 构建
graph = StateGraph(PipelineState)
graph.add_node("parse", _parse_node)
graph.add_node("clarify", _clarify_node)
graph.add_node("gate", _gate_node)
graph.add_node("impact", _impact_node)
graph.add_node("gen", _gen_node)
graph.add_node("review", _review_node)

# 条件路由
graph.add_conditional_edges("gate", 
    _route_after_gate)  # 通过→impact / 不通过→clarify
graph.add_conditional_edges("review",
    _route_after_review)  # 需补充→gen / 完成→END

循环控制逻辑

should_retry(iteration, gate_passed)

门禁未通过 且 迭代次数 < 3 → 回到澄清

should_force_pass(iteration, gate_passed)

迭代次数 >= 3 → 强制放行（避免死循环）

为什么最多 3 轮？

经验表明，3 轮澄清足以覆盖 95% 的需求缺口。更多轮次会导致用户疲劳，边际收益递减。第 3 轮未解决的问题标记为"optional"，不阻断流程。

SSE 进度推送

每个节点完成后通过 SSE 推送进度事件：

make_sse_event("parse", "解析完成", progress=30)
make_sse_event("clarify", "发现3个问题", progress=70)

5.1 需求分析 — ClarifyAgent 澄清闭环

三级检测机制

① 完整性检测

检查 critical/important 字段是否缺失

如：无 happy_path、无业务规则、无边界条件

② 歧义性检测

检测模糊表述、未量化指标、矛盾描述

如："快速响应"（多快？）、"安全校验"（什么校验？）

③ 遗漏检测

需求模式库匹配，发现同类需求常有的维度

如：CRUD 模式应有"删除确认"但当前缺失

KB 自动补全流程

①
检测缺失字段
②
LLM 生成 KB 查询（动态）
③
向量检索 + PG 查询
④
LLM 校验答案可信度
⑤
字段冲突处理 + 自动补全
⑥
未答问题 → 人工澄清

5.2 字段冲突优先级 — 谁说了算？

当多个来源提供了同一字段的值时，系统按严格的优先级处理：

① USER_INPUT（优先级 0）
用户原文中明确写出的值 — 最高权威，不可覆盖
↓ 优先级递减
② HUMAN_ANSWERED（优先级 1）
用户通过澄清面板回答的值
↓
③ KB_INFERRED（优先级 2）
从知识库检索并校验后补全的值
↓
④ PATTERN_DEFAULT（优先级 3）
需求模式库的默认值
↓
⑤ LLM_INFERRED（优先级 4）
LLM 推断的值 — 最低优先级，可被任何来源覆盖
场景示例

字段"密码长度限制"：LLM 推断为 6 位（优先级 4）→ KB 检索到历史需求规定 8 位（优先级 2）→ KB 覆盖 LLM → 最终值 8 位。但用户原文写了"至少 10 位"（优先级 0）→ 不可被覆盖 → 最终值 10 位。

5.3 双 SRR 分层架构（SSOT 原则）

什么是 SSOT？

SSOT = Single Source of Truth（单一数据源）

每个信息只在一个地方定义，避免多处重复导致不一致。

系统中的双 SRR

总 SRR

只描述：总体功能概述 + 跨功能点交互规则

  • requirement — 需求元信息
  • cross_fp_flows — 跨功能点流程
  • shared_business_rules — 共享业务规则
  • fp_contracts — 功能点间契约
  • fp_index — 功能点索引

FP sub_srr

只描述：单个功能点内部细节

  • 该 FP 的 happy_path / 异常路径
  • 该 FP 专属的业务规则
  • 该 FP 的边界条件

为什么需要分层？

❌ 不分层的问题

总 SRR 包含每个 FP 的详细步骤 → 修改一个 FP 要同时改两处 → 容易遗漏 → 数据不一致

✅ 分层后

总 SRR 只引用 fp_index → FP 修改只需改 sub_srr → 总 SRR 不变 → 天然一致

Epic/Feature 层级类比

类似 Jira 的 Epic → Story 层级：

  • Epic（总 SRR）：用户中心 v2.0 — 描述整体目标
  • Story（FP sub_srr）：登录功能 / 注册功能 / 密码重置 — 各自独立详述
追溯矩阵

需求 → 功能点（FP）→ 测试用例 三级追溯，每条用例都能追溯到具体需求字段。

6. 知识库设计 — 双引擎存储

为什么需要双引擎？

只用向量库

✅ 语义检索强

❌ 无法精确查询（按 ID/状态/产品过滤）

❌ 事务一致性弱

双引擎互补

✅ 向量库：语义相似度检索

✅ PG：精确查询 + 事务 + JSONB

✅ 故障降级（向量库挂了用 pgvector）

异步双写

通过 Celery worker 保证最终一致性：

# 主流程写入 PG（同步）
await session.commit()

# 异步写入 Milvus（Celery）
@celery.task
def write_to_milvus(data):
    vector_store.upsert(data)

# 每小时对账修复不一致
schedule_reconcile_task()

6.1 知识库 — 混合检索策略

三路检索 + RRF 融合

V
向量检索（Milvus）
语义相似度 — "登录" 能匹配到 "身份认证"
K
BM25 关键词检索（PG）
精确关键词匹配 — "RBAC" 必须包含 "RBAC"
P
模式匹配（需求模式库）
抽象维度匹配 — CRUD 模式匹配 CRUD 模式
R
RRF 融合 + Cross-Encoder 重排
Reciprocal Rank Fusion 融合三路结果 → Cross-Encoder 精排

为什么需要混合检索？

场景对比
只用向量检索

查询"RBAC 权限" → 可能返回"角色管理"（语义相似但不是 RBAC）

混合检索

向量检索找到"角色管理" + BM25 找到含"RBAC"的文档 → 融合后"RBAC"文档排名更高

断路器降级

L2 断路器

当 Milvus 故障率 > 20% 时，自动降级为纯 BM25 关键词检索，保证系统可用性。

按模块过滤（v2.19）

防止跨模块相同功能点误匹配

不同模块可能存在相同功能点（如 "auth" 和 "order" 都有"查询"），KB 检索时按 modules 过滤，只匹配同模块历史需求。

三层过滤传递

① ClarifyAgent：从 SRR 读取 modules → 透传 hybrid_searcher

② BM25 检索：SQL 用 json_array_elements_text + ANY(string_to_array) 实现数组交集过滤

③ 缓存键：(query, product_id, modules, coll_type) 四元组 — 避免跨模块缓存污染

检索参数

参数值说明
MATCH_TOP_K20初始检索数量
FEW_SHOT_SIMILARITY0.70Few-shot 阈值
KB_SIMILARITY0.85KB 补全阈值

6.2 知识库 — 冷启动与版本管理

冷启动模式

系统首次使用时，知识库为空，如何工作？

触发条件

  • kb_empty = True（知识库完全为空）
  • product_first = True（当前产品的第一个需求）

行为变化

  • QualityGate 阈值从 0.75 降至 0.60
  • ClarifyAgent 切换深度人工澄清模式
  • 不依赖 KB 补全，全部走人工澄清
为什么不直接放行？

冷启动时阈值降为 0.60 而非 0，仍然把关核心字段（如 happy_path、业务规则）。完全放行会导致生成的用例质量差，失去用户信任。

需求版本链

通过 supersedes / superseded_by 维护版本演进：

REQ-001 v1.0 (原始需求)
    ↓ supersedes
REQ-001 v2.0 (优化需求)
    ↓ supersedes
REQ-001 v3.0 (最新版本)

# KB 检索时优先返回最新版本
# 但保留历史版本供影响分析

需求依赖图谱

通过 req_dependencies 表维护依赖关系：

  • depends_on — A 依赖 B
  • related_to — A 与 B 相关
  • conflicts — A 与 B 冲突
  • replaces — A 替代 B

ImpactAnalysisAgent 通过 BFS 遍历此图，找到所有受影响的需求。

6.3 GenAgent — 测试用例生成

生成流程

1
KB Few-shot 检索
检索 Top-3 相似 approved 用例（阈值 0.70）作为示例
2
多维度 Prompt 构建
功能用例 + 边界用例 + 异常用例 + 安全用例
3
LLM 生成（temperature=0.4）
max_tokens=32768，支持大批量生成
4
后处理 + 向量写入
去重、格式校验、并发写入 Milvus

为什么用 Few-shot？

Few-shot vs Zero-shot
Zero-shot

LLM 自由发挥 → 用例格式不统一、断言方式各异、质量不稳定

Few-shot（Top-3）

提供 3 条已审核用例作参考 → 格式统一、断言规范、符合团队习惯

UTCF 格式

统一测试用例格式（Universal Test Case Format）：

  "id": "TC-AUTH-0001-0001",
  "title": "正确账号密码登录成功",
  "type": "functional",

  "steps": [
    {"action":"输入正确账号","data":"admin@test.com"},

8. 错误处理与稳定性保障

错误可见性原则

核心原则

流水线中任何关键步骤失败必须中断流水线、标记任务 failed、携带 error 字段，禁止静默吞错后标记 completed。

中断型错误

  • ClarifyAgent 崩溃 → 保存基础 SRR → failed
  • FP 保存失败 → failed
  • FP 拆分失败 → failed

降级型错误

  • 最终 SRR 生成失败 → 降级用首次结果
  • 标记 degraded=true + degraded_reason
  • 前端展示橙色警告

稳定性保障机制

🛡️ L2 断路器

向量 DB 故障率 > 20% → 降级关键词匹配

🔄 LLM 故障转移

主供应商失败 → 自动切换备用供应商 → 全抖动重试

📮 死信队列（DLQ）

写入失败的任务入队，定期重试，不丢数据

⚖️ LLM-as-Judge

5% 采样审核 LLM 输出，Schema 校验

⚡ 限流器

防止 LLM API 超频，平滑请求速率

8.1 前端交互 — 异步任务进度反馈

异步任务模式

长耗时操作（需求分析/用例生成）采用异步模式：

1
POST 请求 → 立即返回 task_id
后台协程执行，不阻塞 HTTP 连接
2
前端轮询 GET /tasks/{task_id}
每 1.5 秒轮询一次，获取真实进度
3
状态变化 → UI 响应
running→进度条 / completed→跳转 / failed→红色错误框
进度阶段映射
PHASE_MAP = {
  parse: 0,      // 解析需求
  kb_search: 1,  // 检索知识库
  clarify: 2,    // 需求澄清
  regenerate: 3, // 生成最终分析
  done: 4        // 完成
}

错误展示

❌ 分析失败（红色）

task.status === 'failed'

  • 红色错误框 + 错误详情
  • "返回修改" + "重试" 按钮
  • 标题动态化（非固定"上传失败"）

⚠️ 降级警告（橙色）

result.degraded === true

  • 橙色警告框 + 降级原因
  • 展示 3 秒后继续流程
  • 用户可知数据质量有折扣

✅ 分析完成（绿色）

task.status === 'completed'

  • 无问题 → 进入影响分析
  • 有问题 → 显示澄清面板

原始文本展示（v2.19 优化）

表格 HTML 渲染

后端 _table_to_markdown 将 docx 表格转为 Markdown 语法 → 前端 ReactMarkdown 渲染为带边框、斑马纹的 HTML table，替代竖线纯文本。

图片描述折叠

多模态识别内容用 <details>/<summary> 默认折叠，点击展开。原始图片始终展示，避免描述占用过多空间。

统一两栏布局

文本块、表格块、图片块统一遵循「行号列 + 内容列」两栏布局，splitTextIntoBlocks 按顺序分块渲染，保证页面整齐对齐。

9. 部署架构 — Docker 容器化

8 个 Docker 服务

服务职责
frontendNginx + React 静态资源
backendFastAPI 主 API 服务
celery_worker异步嵌入计算、向量双写
postgresPG 16 + pgvector + zhparser
redis缓存 + Celery broker
milvus向量检索（standalone）
etcdMilvus 元数据协调
minioS3 兼容对象存储
为什么用 Docker Compose？

8 个服务有依赖关系（Milvus 依赖 etcd + minio），Compose 可以声明依赖顺序，一键启动完整环境。

网络拓扑

ai-test-gen-net (bridge 网络)
│
├── frontend (80) ──→ backend (8000)
│
├── backend ──→ postgres (5432)
│           ──→ redis (6379)
│           ──→ milvus (19530)
│           ──→ minio (9000)
│
├── celery_worker ──→ postgres
│                 ──→ redis (broker)
│                 ──→ milvus
│
├── milvus ──→ etcd (2379)
│          ──→ minio (S3)
│
└── 前端浏览器 ──→ frontend (80)
              ──→ backend (8000) [API]
健康检查

每个服务配置 healthcheck，backend 启动前等待 PG + Redis + Milvus 全部 healthy。
