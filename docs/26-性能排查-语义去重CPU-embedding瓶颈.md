# docs/26 — 自举复测轮性能排查报告：语义去重 CPU embedding 瓶颈

> 日期：2026-10-12 · 触发：v3.5.6 复验轮（v1.0-r2 / v2.0-r2）执行期间用户观察「速度慢太多，疑似系统故障」
> 结论先行：**系统无故障、无死锁**，慢的根因是 v3.4.5 新增的「跨子轮语义去重」在 CPU 上对全量用例做 bge-large embedding，单点耗时 7~35 分钟，且在编排主链路上出现三次。任务进度条在此期间停在 70% 不动（去重不更新进度消息），造成「卡死」观感。

---

## 1. 现象

复验轮执行期间观察到的时间线（均为 API 容器 UTC 时间）：

| 时间 | 事件 | 停更时长 |
|---|---|---|
| 00:23~00:59 | v1.0-r2 生成 13/13 FP 完成 | — |

| 00:59:53~01:38 | **日志静默**，任务 `running/70%` 停更 | **~35 分钟** |
| 01:38:37 | ReviewAgent 首次审核启动 | — |
| 01:44~02:01 | 补生成 14 条 → 跨子轮合并 → 第二次语义去重 | ~17 分钟 |
| 02:01~02:04 | 二次审核 → partial_block 发布 → 242 条落库 | — |
| 02:09~02:27 | v2.0-r2 生成 8/8 FP 完成 | — |

用户视角：进度条长期停在 70%，日志无新输出，疑似挂起。

## 2. 排查过程与证据

### 2.1 排除故障类原因（逐项证伪）

| 假设 | 检验方式 | 结论 |
|---|---|---|
| 进程/管线死锁 | `/proc/*/cmdline` 找脚本进程存活 + 任务 `updated_at` 持续变化 | 进程活着；恢复后正常走完 |
| LLM 调用挂起 | `docker logs` 过滤 `llm_client`，末次调用 00:59:41 正常返回 | 静默期无 LLM 在飞 |
| Celery 侧异常 | `docker logs ai-test-gen-celery --since 35m` | 无任何输出（管线不在 celery） |
| 容器/依赖故障 | milvus/pg/redis 全 healthy | 无异常 |
| py-spy 抓栈 | 容器内安装 py-spy 成功，dump 被拒（ptrace `Permission denied`，缺 `SYS_PTRACE` cap） | 未取得调用栈，改用日志+CPU 侧证 |

### 2.2 定位手段：CPU 特征 + 代码定位

- `docker stats`：静默期间 **API 容器 CPU 379%~392%**（8 核容器，占满约 4 核）——典型的本地推理特征，不是 IO 等待；
- 对照日志代码路径：`orchestrator.py:1505-1537`，`批内近重复去重` 日志行（00:59:53）之后的下一步正是：

```python
# v3.4.5（缺陷 E，对称补漏）：…补一道整例 JSON embedding 语义去重
cases, semantic_removed = await asyncio.to_thread(
    dedup_semantic, cases, embed_func=_embed_gen
)
```

- `_review_node:1815` 的 `跨子轮语义去重` 日志行出现时（01:38:37 / 02:52:12），静默立即结束——**静默窗口 = dedup_semantic 的 embedding 窗口**，证据链闭合。

### 2.3 吞吐量实测换算

| 轮次 | 用例数 | embedding 耗时 | 单条耗时 |
|---|---|---|---|
| v1.0-r2 主合并 | 526 条 | ~35 min | ~4.0 s/条 |
| v1.0-r2 子轮合并 | 280 条（266+14） | ~17 min | ~3.6 s/条 |
| v2.0-r2 主合并 | 161 条 | ~17 min* | ~6.3 s/条 |
| v2.0-r2 子轮合并 | 140 条 | ~7 min | ~3.0 s/条 |

*与首次审核等待有重叠，取估算。综合约 **3~4 秒/条**（整例 JSON 文本较长）。

## 3. 根因定性

三个因素叠加：

1. **模型过重**：`EMBEDDING_MODEL_NAME=/models/bge-large-zh-v1.5`（335M 参数），`EMBEDDING_DEVICE=cpu`（容器仅 8 核，无 GPU 直通）；
2. **全量重算**：dedup_semantic 在三个对称执行点（主生成合并 / 审核补生成合并 / 跨子轮合并）每次都**对全部在管用例重新 embedding**，无增量缓存——补生成轮明明只新增十几条，也要把 500+ 条重算一遍；
3. **串行在主链路**：embedding 是同步 CPU 调用（`asyncio.to_thread` 包装仅避免阻塞事件循环），编排管线必须等它算完才能进 review 节点；期间进度不更新（gen 节点 70% 后无阶段消息）。

**为什么此前没暴露**：该去重是 v3.4.5 才上的；此前正式轮规模较小或观察粒度粗。本轮 v1.0-r2 用例量（526 条）是历史最大，瓶颈首次显性化。

## 4. 影响面

| 维度 | 影响 |
|---|---|
| 正确性 | **无**——去重结果正确（本轮实测剔除均合理，如「大小刚好10MB的静态原型文件上传成功 ≈ 上传大小刚好10MB的文件成功」0.9721） |
| 时延 | v1.0-r2 全程 ~100 min，其中 **~60 min 为两轮语义去重等待**（占比 ~60%） |
| 体验 | 进度条停 70% 长达 30+ 分钟，无法与「挂死」区分（无心跳/无阶段消息） |
| 可扩展性 | 耗时随用例数线性增长且每轮全量重算，用例量再翻倍将逼近小时级 |

## 5. 优化方案（供拍板）

| 方案 | 改动 | 预期收益 | 成本/风险 |
|---|---|---|---|
| **A. 换小模型**（推荐先做） | `EMBEDDING_MODEL_NAME` → `bge-small-zh-v1.5`（24M）或 `bge-base-zh-v1.5`（102M），改配置即可 | 速度 5~15×；去重场景仅做 0.92 阈值粗筛，精度损失可忽略 | 需重导 base 镜像（内网更新流程）；阈值需用历史批次复标 |
| **B. 向量增量缓存** | 用例 JSON 归一化 hash → 向量的进程内/Redis 缓存；补生成轮只算新增条 | 补生成/跨子轮两处的重算几乎归零（新增仅 10~40 条） | 中等改动（`milvus_store` + `dedup_semantic`）；缓存失效策略要考虑用例被编辑的场景 |
| **C. GPU 推理** | `EMBEDDING_DEVICE=cuda` + 内网 GPU 直通 | 10~30× | 依赖部署环境有无 GPU；镜像需带 CUDA 依赖 |
| **D. 体验补丁（建议随手做）** | dedup 前后各发一条任务进度消息（如「语义去重中（526 条，预计 ~30min）」）+ 去重分批 print 进度日志 | 消除「假死」观感 | 极小，纯日志/消息改动 |

**建议组合**：D（体验）立即做；A+O（小模型 + 缓存）作为一个优化任务另立文档排期，先跑 B 的定标（用 v1.0-r2 266 条基线比对 small/base/large 三档在 0.92 阈值下的去重一致率）。

## 6. 对本轮复测的影响

- 复验轮**不中断**：性能问题不阻塞功能验证，v2.0-r2 / v3.0-r2 继续按计划跑（接受每轮 ~15-40 min 的去重等待）；
- 本报告仅记录与归因，**不改代码**——优化项（§5 A/B/C/D）待拍板后另立任务，落地后应在 docs/24 或 docs/25 的复测中回验耗时对比。
