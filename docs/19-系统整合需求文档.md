## 1. 系统概述

### 1.1 系统定位

AI 驱动的"需求 → 测试用例"自动生成平台。核心理念：将非结构化/半结构化的软件需求文档，通过 LLM 解析为结构化表示（SRR），经需求澄清闭环确保需求质量，结合历史知识库的上下文检索，自动生成高质量、可执行、可追溯、可回流的测试用例。

目标场景：中大型软件项目中的功能测试、回归测试、API 测试用例自动生成，减少手工编写工作量 60% 以上。

### 1.2 核心业务流程总览

```
新建产品 → 划分模块 → 创建项目 → 上传需求文档（md/docx/txt/html）
    → AI 解析（SRR + 功能点拆分）→ 人工澄清（≤3 轮）→ 确认需求
    → 生成测试用例（SSE 流式）→ 审核入库 → 导出（JSON/MD/Gherkin/pytest/XMind）
    → 项目归档（向量化进知识库 + CRSR 固化）→ 知识库问答 / 影响分析复用
```

需求状态机：`analyzing → draft → pending_review → confirmed → archived`。仅 `confirmed` 状态可生成用例；仅项目级归档（归档时项目下所有 confirmed 需求自动归档）。

### 1.3 系统边界（明确不做的事）

- 系统**不提供用例执行/测试运行管理**能力（无执行记录、无执行结果回填）；用例导出 pytest/Gherkin 格式仅供外部测试框架使用。
- 生成期不再进行生成中的澄清（v3.4.4 起：已确认需求强制跳过生成期 clarify 节点）；澄清只发生在需求分析阶段。
- 不存在 FAST/FULL 通道分级（v3.4.4 已删除 channel 概念）；所有生成走同一条完整流水线。
- 原型 HTML 为静态文件解析，不执行 JS，无法感知动态行为（联动显隐/异步校验/跳转逻辑）——此类信息缺失由澄清环节发问补全。

## 2. 用户角色与权限

### 2.1 角色定义

| 角色 | 能力 |
|---|---|
| 管理员（admin） | 全部能力：产品创建/修改/删除、模块管理、用户管理、角色管理、LLM 设置、提示词覆盖、知识库管理（删除条目/重向量化）、删除操作 |
| 普通用户（写权限） | 需求上传/澄清/确认、生成用例、用例编辑/反馈、项目创建、归档、KB 问答 |
| 只读用户 | 查看列表/详情/报告、KB 问答；无任何写操作 |

### 2.2 权限规则

- 基于 RBAC：角色定义 `menus` JSON 数组（菜单权限），前端按权限渲染侧边栏。
- 产品级隔离（P1-1）：产品可配置 `visible_to_user_ids`（可见用户 ID 列表）；为空表示全员可见。生成用例等写操作前校验产品可见性，不可见返回 403。
- 认证：JWT（8 小时过期）。除 `/api/health` 与 `/api/auth/login` 外，所有接口要求认证。
- 登录：用户名+密码（PBKDF2-SHA256 加盐哈希存储）；连续失败有锁定保护。登录成功返回 `data.token`。

## 3. 模块一：需求管理

### 3.1 产品管理

| 规则编号 | 规则 |
|---|---|
| PM-01 | 产品名称必填，1-128 字符，**同一系统内名称唯一**；重名创建失败（唯一约束冲突） |
| PM-02 | 产品描述选填，最长 1024 字符 |
| PM-03 | 产品 ID 可指定（≤64 字符）或留空自动生成 |
| PM-04 | 仅管理员可创建/修改/删除产品 |
| PM-05 | 删除产品前有 delete-check 预检：返回关联数据统计（项目/需求/用例数），删除为级联删除（含需求、用例、FP、向量） |
| PM-06 | 产品可配置可见用户列表（空 = 全员可见） |

### 3.2 项目管理

| 规则编号 | 规则 |
|---|---|
| PR-01 | 项目归属产品；名称必填 1-128 字符 |
| PR-02 | 项目版本号默认 "1.0"，≤32 字符，**同一产品内版本号不可重复** |
| PR-03 | 项目创建需要写权限 |
| PR-04 | 项目归档（`POST /products/projects/{proj_id}/archive`）时，项目下所有 confirmed 状态需求自动归档；触发向量化与 CRSR 固化 |
| PR-05 | 归档前置：支持 pending-archive（标记待归档）/ cancel-pending-archive（取消）/ reactivate（重新激活）流转 |
| PR-06 | 需求级归档端点已废弃（v2.45 起）：调用返回 409 并提示改用项目级归档 |
| PR-07 | 项目有 `go_live_date`（上线时间）：影响 KB 检索排序（按时间衰减/取最新）与回归基线归属；修改已归档需求的 go_live_date 需重算受影响 FP 的用例固化数据 |

### 3.3 模块管理

| 规则编号 | 规则 |
|---|---|
| MD-01 | 模块归属产品；名称必填 1-64 字符，描述 ≤512 字符 |
| MD-02 | 模块支持删除（仅管理员）、排序（position）、重命名 |
| MD-03 | 模块依赖图谱：模块间可建依赖边（source/target/relation_type 默认 depends_on/strength 默认 medium）；图谱可视化展示 |
| MD-04 | 功能点（FP）可归属一个或多个模块（多选） |

### 3.4 需求文档上传

| 规则编号 | 规则 |
|---|---|
| UP-01 | 支持格式：`.md` / `.markdown` / `.docx` / `.txt` / `.html` / `.htm`（原型，见模块六） |
| UP-02 | 单文件大小上限 **10MB**，超限拒绝 |
| UP-03 | 内容校验（魔数）：文本类解码（UTF-8 → GBK 兜底）；HTML 需前 512 字节（小写化）含 `<!doctype html`/`<html`/`<head`/`<body`/`<div`/`<script` 任一，否则 400「不是有效的 HTML 文件」 |
| UP-04 | 支持多文件同时上传（`/upload/multi`）：多文档以 `【文档：文件名】` 边界标记拼接，跨文档矛盾检测适用 |
| UP-05 | 上传即触发异步分析任务（`analysis_tasks`），前端轮询任务状态（task_id → phase/status/progress） |
| UP-06 | 上传参数：raw_text（或文件）、product_id、project_id、title、priority（P0/P1/P2…） |
| UP-07 | 系统不保存原始文档字节，只保存提取后的文本（raw_text）与图片（base64） |
| UP-08 | docx 内嵌图片走多模态识别（视觉 LLM 已配置才识别，未配置输出占位符） |

### 3.5 需求版本管理

| 规则编号 | 规则 |
|---|---|
| VH-01 | 每次重新分析（regenerate）前，当前 SRR 自动快照进 `srr_json._version_history` |
| VH-02 | 版本记录含：标题、快照时间、触发原因、补充说明 |
| VH-03 | 版本恢复（restore）：当前 SRR 先自动快照 → 目标版本覆盖；状态回 `pending_review`，需重新确认 |
| VH-04 | 需求修改乐观锁：提交带 `expected_revision`，与数据库不一致返回 409（防并发覆盖） |

## 4. 模块二：需求分析

### 4.1 需求解析（SRR 生成）

| 规则编号 | 规则 |
|---|---|
| RA-01 | 上传后 ReqAgent 调 LLM 将原始文本解析为 SRR（Software Requirement Representation）JSON：含 requirement 基本信息、flows（happy_path/alternate_flows）、business_rules、data_constraints、user_roles、non_functional 等字段 |
| RA-02 | **双 SRR 分层**（v2.0 起）：总 SRR（interaction_srr）承载跨 FP 交互规则/共享约束/契约；每个功能点（FP）有独立子 SRR（sub_srr）承载 FP 内部规则。一条规则只在一处定义 |
| RA-03 | FP 自动拆分：解析时同步提取功能点列表；FP 拆分失败不阻断主流程，但生成阶段覆盖维度会缩水（business_rules/data_constraints 只从 FP 子 SRR 抽取） |
| RA-04 | FP 去重跳过 LLM：同模块下已存在同名 FP → 直接复制到新需求，不重新调 LLM 生成 |
| RA-05 | v2.48 起 business_rules 与 data_constraints 已从总 SRR 移除、下沉到 FP 子 SRR；总 SRR 只抽 happy_path/alternate_flows/precondition/shared_rule 四类要点 |
| RA-06 | 解析结果降级标记：`_fp_extract_degraded`（FP 提取降级）等标记存在时，confirm 会被拒绝（见 RA-14） |

### 4.2 需求澄清

| 规则编号 | 规则 |
|---|---|
| CL-01 | 解析完成后状态 `draft`，系统产出澄清问题清单；澄清问题分两类来源：规则层检测（确定性）与 LLM 语义检测 |
| CL-02 | 检测维度：完整性（Checklist 规则）、歧义性、遗漏（需求模式库对比）、引用未定义（引用了文档中未定义的规则/字段）、跨节矛盾、跨文档矛盾、PRD 新建功能专项（上限处理/降级触发/风险-能力一致性/立场不一致）、原型类问题（见模块六） |
| CL-03 | **KB 自动补全优先**：语义检测出的问题先经知识库查询，KB 能答的自动补全（answered=true），答不出的才转人工问题 |
| CL-04 | 人工澄清问题**最多 5 个**/轮 |
| CL-05 | 澄清最多 **3 轮**（MAX_CLARIFY_ITERATIONS=3）；第 3 轮仍有 critical/important 问题 → 降级为 optional 强制放行，SRR 标记 `_clarify_force_passed=true`（视为需求文档结构性缺陷信号） |
| CL-06 | 澄清问题归属具体功能点（v2.8.66 起注入 FP 归属）；已回答问题不再出现在下一轮清单（去「澄清历史」查看） |
| CL-07 | 提交澄清答案（`POST /requirements/{req_id}/clarify`，answers 为 {问题ID: 答案} 映射 + extra_notes）→ 异步重新生成最终 SRR |
| CL-08 | 澄清状态快照：获取问题时返回的是上次保存快照（不重新生成），保证前后一致 |
| CL-09 | `has_unanswered_questions` 字段透出未回答状态；全部回答/无问题 → 状态 `pending_review` |

### 4.3 确认与门禁

| 规则编号 | 规则 |
|---|---|
| RA-14 | 确认（confirm）守卫：①存在降级标记（`_finalize_degraded`/`_clarify_degraded`/`_recheck_skipped`）→ 拒绝确认；②所有 FP 必须已审核通过（approved）且已分配模块；满足后状态 `pending_review → confirmed` |
| RA-15 | 确认后解锁：生成测试用例、项目归档 |
| RA-16 | regenerate（补充重新生成）：输入 extra_notes 追加到原始需求文本重新解析；当前 SRR 自动入历史版本 |

### 4.4 FP 管理

| 规则编号 | 规则 |
|---|---|
| FP-01 | FP 状态：pending_review → approved（人工逐个审核）；确认需求前必须全量 approve |
| FP-02 | FP 可编辑：名称、多模块归属、SRR 字段（逐字段编辑） |
| FP-03 | FP 重生成：输入 hint → LLM 重新生成子 SRR |
| FP-04 | FP 合并：多选多个 FP → LLM 合并为一个 |
| FP-05 | FP 依赖：跨需求 FP 依赖关系（5 种关系类型），构成依赖图谱 |
| FP-06 | 归档后 FP 锁定为只读 |

## 5. 模块三：用例生成

### 5.1 生成入口与前置守卫

| 规则编号 | 规则 |
|---|---|
| GEN-01 | 唯一入口 `POST /api/generate`（SSE 流式），请求参数：req_id（必填）、resume/resume_from_task（断点续跑，可选）；channel 参数已废弃仅兼容记录 |
| GEN-02 | **六道前置守卫**（顺序执行，任一失败即中断）：①需求存在（404）②产品可见性（403）③status=confirmed（409）④影响分析条目全部已确认（409）⑤SRR 非空（400，明确禁止回退 raw_text）⑥并发互斥（409） |
| GEN-03 | **生成并发互斥**：同一需求同一时间只允许一个生成任务；数据库 advisory lock + 唯一索引双保险；updated_at 超过 6 小时的 running 任务视为僵尸自动回收（标记 interrupted）；resume 同受互斥 |
| GEN-04 | SSE 事件统一 event 名 `message`，阶段与进度：parse 20% → select_channel(生成准备) 25% → clarify 30% → gate 40% → impact 50% → test_design 62% → generate 70% → review 90% → done 100%；FP 分片路径产出 fp_progress 细粒度进度 |
| GEN-05 | SSE 断连：三重兜底检测断连并把任务写为 aborted（防幽灵 running 任务） |
| GEN-06 | 断点续跑：从最近 interrupted/aborted/cancelled/failed 的生成任务读 checkpoint（含 fp_groups + 输入指纹）；续跑前重算指纹逐字段比对，任一不一致 409（防输入已变却套旧断点） |

### 5.2 生成流水线（LangGraph DAG，8 节点）

```
START → parse → select_channel(生成准备) → [gate] → [impact] → test_design → generate → review → END
```

| 规则编号 | 规则 |
|---|---|
| GEN-07 | parse 节点**不调 LLM**：直接复用已确认 SRR |
| GEN-08 | 生成准备节点：已确认需求强制跳过澄清；影响分析仅优化需求（存在 optimization_context）触发；多类型生成与完整审核恒开启 |
| GEN-09 | **三条生成通道**：①逐 FP 分片（主路径，FP 非空时每 FP 独立定向生成）②全量兜底（FP 为空时单次全量生成，防 0 用例）③跨 FP 集成（存在跨 FP 交互/共享规则时独立生成 integration 类型用例） |
| GEN-10 | 单 FP 生成失败不阻断（继续下一个，进度标 failed）；每 FP 完成即写 checkpoint |
| GEN-11 | **质量门禁**：质量评分阈值冷启动 0.60 / 正常 0.75；Blocker 项（SRR Schema 校验失败/关键字段空/评分低于阈值/存在未解决 Critical 问题）阻断回澄清；Warning 项（happy_path 步骤 <2、冷启动提示）放行；澄清回环最多 3 轮后强制放行并置 manual_action_required=true |
| GEN-12 | **测试设计技术**：声明 8 种（等价类/边界值/决策表/状态迁移/场景/正交/错误推测/因果图），实际有确定性触发的 6 种——范围型约束触发等价类+边界值（生成 min-1~max+1 六点）；≥2 条规则触发决策表；含状态类关键词（锁定/禁用/过期/取消/撤销/回退/超时/失败）触发状态迁移；有主备选流触发场景法；必填/长度/金额类字段触发错误推测（截断 15 条）；**正交实验法与因果图法无触发器，适用性恒为 false** |
| GEN-13 | 用例最小数量下限：按要点规模动态推导（主流程÷3 + 备选流数 + 规则数 + 数据字段数），P0/P1 优先级需求取要点数×0.6 与下限的较大者，**封顶 40 条** |
| GEN-14 | 用例编号规则：`TC-{模块}-{批次4位}-{序号4位}` |
| GEN-15 | **四级去重**：精确重复 → 语义重复（embedding）→ 子集重复 → LLM 等价判定；另有跨子轮语义去重（整例 embedding 阈值 0.92 + 数字护栏——数字集合不同的用例不合并） |
| GEN-16 | 一致性检查：与历史已完成任务比三维——用例数方差 >20%、类型分布 Jaccard <0.7、标题语义相似度均值 <0.7；数量不一致或（类型与语义同时不一致）判定不一致 |

### 5.3 用例审核与入库

| 规则编号 | 规则 |
|---|---|
| RV-01 | 多因子置信度（非 LLM 计算）：match_score×0.4 + completeness×0.3 + consistency×0.2 + 生成自评分×0.1 + 模式加分；match_score 来自同产品向量检索 Top-3 |
| RV-02 | 入库分级：confidence ≥**0.70** 且无 blocker → approved（自动入库）；0.60~0.70 → reviewed（待人工确认）；<0.60 或有 blocker → 记入错误案例库 |
| RV-03 | 补生成闭环最多 **1 次**：审核发现覆盖缺口 → 按 FP 分组定向补生成 → 二次审核；二次仍不达标标记 supplement_exhausted（不再补） |
| RV-04 | KB 回流：入库前标题级去重（同标题保留 confidence 最高一条）；逐条 savepoint 隔离（单条失败不影响其余）；**仅 approved 用例写向量**（经事务性出箱投递，至少一次幂等） |
| RV-05 | 回归复用（RTS）：优化需求生成时，受影响 FP 读取产品+FP 维度最新（按项目 go_live_date 最大）的 approved 用例作回归基线，标记 `[回归]` 前缀直接并入结果；无历史用例的 FP 由 LLM 定向补生成 |
| RV-06 | 用例类型分布：功能/边界/异常/安全四类型分类生成 + regression（回归）+ integration（集成） |
| RV-07 | 覆盖率口径：分母来自 5 类要点（主流程步骤/备选流/业务规则/数据约束/共享规则，规则与约束仅从 FP 抽取）；要点标注率 ≥30% 用真实映射口径，否则退化为数量比（该退化模式下 uncovered 为空、补生成不触发）；unknown 时不给"覆盖率"只给 observed_coverage_rate |
| RV-08 | done 事件透出：srr/cases/review_report/point_coverage/consistency_check/test_design/regression_reuse_summary/degraded_flags/manual_action_required/duration_ms 等 |

### 5.4 用例管理

| 规则编号 | 规则 |
|---|---|
| TC-01 | 用例列表支持按需求/项目/产品/类型/状态筛选；page_size ≤ **100** |
| TC-02 | 用例可编辑（写权限）、删除、批量审核（通过/驳回 + feedback） |
| TC-03 | 人工核准：reviewed 状态用例经人工确认后成为权威用例（知识库 L2 层） |
| TC-04 | 用例反馈回流：单条/批量提交 feedback |
| TC-05 | 导出格式 5 种：JSON / Markdown / Gherkin（Cucumber）/ pytest（Python）/ XMind（zip，需求→FP→用例→步骤层级）；导出必须指定 case_ids（防全量导出） |

## 6. 模块四：知识库

### 6.1 知识入库（归档链路）

| 规则编号 | 规则 |
|---|---|
| KB-01 | 归档时 SRR 写入 PG + Milvus 双存储；向量写入走**事务性出箱**（先同事务记录投递意图，后台 relay 至少一次幂等投递）；Milvus 不可用时任务积压不出错，恢复后自愈 |
| KB-02 | 嵌入模型：BAAI/bge-large-zh-v1.5（本地推理）；bge 推理为同步 CPU 计算须包线程池执行 |
| KB-03 | 向量化状态四态：null（未处理）/ processing / completed / failed；管理页双徽章展示（已归档+已向量化） |
| KB-04 | CRSR 固化：归档/知识纠错时，同名 FP 跨版本 SRR 规则式聚合（标量字段取最新版本值；数组字段按签名去重合并并集）为"最新整理版"；固化失败不阻断归档 |
| KB-05 | CRSR 向量化：固化成功同事务入出箱；向量 ID 确定性（`CRSR-` + 产品|FP名 哈希前16位），重复归档覆盖同一条不堆积；metadata 含 type=fp_crsr、status=archived、product_id、fp_name、version_count 等 |
| KB-06 | CRSR 是编译产物不是权威记录：权威永远是各版本原始 SRR；CRSR 可随时重算 |

### 6.2 检索与问答

| 规则编号 | 规则 |
|---|---|
| KQ-01 | 混合检索：向量召回（Top-K=20，相似度阈值 0.70）+ BM25 关键词（PG zhparser 中文分词）→ RRF 融合 → Cross-Encoder 重排（bge-reranker-base）→ Top-N |
| KQ-02 | 时间衰减：RRF 融合带时间衰减因子（半衰期 180 天），同功能多版本以 go_live_date 靠后为准 |
| KQ-03 | 检索范围硬过滤：product_id + status=archived；已删除内容不出现在检索结果 |
| KQ-04 | KB 问答（SSE）：按 event 名分派事件，done 事件的 data.answer_full 为最全答案；答案附带来源列表（sources），每条来源标注类型与权威层级 |
| KQ-05 | 来源权威层级：L0 需求文档 > L1 功能点/CRSR（最新整理版）> L2 人工核准用例 > L3 AI 生成用例；**fp_crsr 类型来源 = 该功能的最新整理版（跨版本聚合），与单版本记录冲突时优先采信并标注** |
| KQ-06 | KB 回答多版本问题时按最新版本回答（版本变更覆盖） |
| KQ-07 | 问答记录落库（knowledge_qa 表）；支持人工纠错：纠错内容经审核后回流知识库并触发相关 CRSR 刷新 |
| KQ-08 | reload 后 1-2 分钟窗口内问答服务暂不可用（503），属正常预热 |
| KQ-09 | CRSR 检索灰度开关 KB_CRSR_ENABLED（默认开） |

### 6.3 知识库治理（Lint 周期自检）

| 规则编号 | 规则 |
|---|---|
| KL-01 | 周期自检默认每 24 小时（KB_LINT_INTERVAL_HOURS 可配），三项检查**全部只读+报告**，不自动改数据 |
| KL-02 | L1 CRSR 漂移检测：重算聚合结果与固化行逐字段比对，不一致即漂移（固化失败/未触发等） |
| KL-03 | L2 跨版本规则矛盾检测：同名 FP 各版本业务规则同 ID 不同文本、数据约束同字段不同限制 → 矛盾清单（谁与谁冲突、各来自哪个版本） |
| KL-04 | L3 向量孤儿对账：向量库与 PG 对账，孤儿向量清单输出；修复动作需人工确认后执行 |
| KL-05 | 自检 fail-open：扫描异常不影响主业务 |

## 7. 模块五：影响分析

| 规则编号 | 规则 |
|---|---|
| IA-01 | 触发条件：需求含优化语义（optimization_context，如"优化 XX 流程"）时，生成流水线自动执行影响分析 |
| IA-02 | 分析逻辑：识别被优化需求 → 沿版本链找原始需求与历史用例 → FP 依赖图**双向 BFS** 遍历受影响的上游/下游功能点 → 产出影响范围报告与回归测试推荐 |
| IA-03 | 人工确认：影响分析结果须逐条人工确认（确认受影响/不受影响/移除）；**存在未确认条目时生成被拦截（409）** |
| IA-04 | 影响分析确认后，受影响 FP 的最新 approved 用例自动装配为回归基线（RTS） |
| IA-05 | 模块依赖图谱可视化（dependency-graph 页面）；FP 级依赖历史版本可查、可比对 diff |
| IA-06 | go_live_date 是项目级属性：修改后需同步向量库 metadata、缓存失效并重算 FP 用例固化数据，否则回归基线归属失效 |

## 8. 模块六：原型解析（HTML 原型上传）

| 规则编号 | 规则 |
|---|---|
| HT-01 | 准入：.html/.htm 白名单；≤10MB；魔数校验（见 UP-03） |
| HT-02 | 安全剥离（强制，非可选）：`<script>`/`<style>`/`<noscript>`/`<template>` 整节点移除；`on*` 事件属性过滤；`javascript:`/`data:text/html` 协议链接剔除；`<iframe>`/`<object>`/`<embed>` 剔除 URL 保留语义标记 [external]；HTML 注释剔除（注释不作为文本节点参与解析） |
| HT-03 | 产出：语义树 YAML（对齐 Playwright ariaSnapshot 格式）+ 表格转 Markdown + base64 图片走视觉识别链路 |
| HT-04 | 标签映射：h1-h6→heading；input→textbox（提取 required/maxlength/minlength/pattern/min/max/placeholder/readonly/disabled）；checkbox/radio（组内枚举全列）/fileupload/textarea/select（选项全列）/button/link（外链标 external）/table/list/dialog |
| HT-05 | 字段命名优先级：aria-label > label[for] > 嵌套 label > placeholder > title > 邻近文本（dt/dd、表格左邻）；全部无 → `(未命名字段)` 并在解析统计中计数 |
| HT-06 | 归一化：无 alt 且无邻近文本的 img 丢弃；匿名容器（无名称/无角色/无语义属性的 div/span 等）递归压平、子节点上提；**注释不计为容器自带文本**（防止深嵌套原型输出膨胀） |
| HT-07 | 预算与降级：语义树节点上限 **400**（超限截断 + 降级标记 proto_tree_truncated）；解析墙钟 **10s**（超时降级纯文本提取，proto_parse_timeout）；输出字符软上限 20,000；解析异常降级纯文本且**不阻断其他文件**（proto_parse_failed）；纯壳页面（无任何语义节点）标记 proto_no_semantics |
| HT-08 | 拼接格式：`【原型：文件名】` 边界标记，与需求文档（`【文档：文件名】`）区分来源；多文件混传时跨文档矛盾检测适用（如需求说"手机号非必填"而原型 required） |
| HT-09 | 语义树中带约束的字段进入 SRR 的 ui_rules，并纳入覆盖率统计与生成清单（ui_rules 是覆盖要点五类扩展字段之一） |
| HT-10 | 澄清联动：检测到原型来源时追加针对性问题——未命名字段补充、约束业务原因、删除类按钮二次确认、静态盲区（联动/异步校验/动态显隐原型无法体现需人工说明） |
| HT-11 | 防注入：原型内容是待分析数据不是指令，即使出现"忽略以上要求"类文字也按普通文本处理 |
| HT-12 | 落库口径：与 docx 一致——存提取后语义文本，不存原始字节；不新增表列 |
