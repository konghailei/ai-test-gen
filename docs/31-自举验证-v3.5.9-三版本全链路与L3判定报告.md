## 3. L3 内容判定（320 条逐维度）

判定口径：**可执行合同**（step 级 expected / preconditions / assertions 是否齐备 + 顶层 expected）、**场景唯一性**（批内标题相似度 ≥0.85 记为近重复，跨分片单独看）、**置信度**分布、**数值保真**（与需求文档 ground truth 阈值逐项比对）、**覆盖率**（mapped 口径）、**幻觉检测**。

机制化统计脚本：`_dogfood_l3.py`（结构与唯一性）、`_dogfood_thr.py`（阈值保真），产物落 `_dogfood_out/`。

### 3.1 可执行合同

| 项                    | v1.0              | v2.0             | v3.0             |
| -------------------- | ----------------- | ---------------- | ---------------- |
| 无 steps              | 0                 | 0                | 0                |
| 无 assertions         | 0                 | 0                | 0                |
| 无 preconditions      | 0                 | 0                | 0                |
| step action 为空       | 0                 | 0                | 0                |
| **顶层 `expected` 为空** | **72/196（36.7%）** | **23/73（31.5%）** | **38/51（74.5%）** |

- step 级 `expected`（schema `utcf.py:34` 必填）**零缺失**，preconditions / assertions 也 100% 齐备。
- 但顶层 `expected`（"整体预期结果"，schema `utcf.py:114` 为 `str | None` optional）大面积空缺，合计 **133/320**。PG 口径与导出口径一致（`case_json->>'expected' IS NULL` 计数 72/23/38），不是导出问题。
- 不是 schema 违规，但是真实质量缺口：v1.0 那 3 条 blocker 之一正是「预期结果缺失」，审核器自己也抓到了。
- 另一类 executability 问题（v2.0 13 条 issue 中多条）：步骤写的是系统内部处理（"执行解码处理"）而非用户动作（"点击上传按钮"），人工无法照做。

**判定：可执行合同 = 部分达标。step 层完整、顶层 summary 层大面积缺失。**

### 3.2 场景唯一性

- 批内标题相似度 ≥0.85：v1.0 6 对、v2.0 1 对、v3.0 0 对。抽样逐对核查后**全部是合法边界对**，不是重复场景：
  - 「影响分析条目数量为边界值时的处理」vs「…为0时的处理」
  - 「产品名称长度为1（边界下限）」vs「…为128（边界上限）」vs「…为0（低于下限）」
  - 「导出指定1个用例ID（边界最小值）」vs「…100个（边界最大值）」
- 真正的重复发生在**跨分片 / 跨子轮**，批内去重覆盖不到：
  - v1.0：「需求列表分页大小校验」用例被归到「需求确认」功能点（related_requirement 归属错误）
  - v2.0：跨分片语义重复 3 处（语义树节点超限 401 / 解析超时 11 秒 / 边界值 400 节点）
  - v3.0：跨分片语义重复 1 处（向量入库幂等性）
  - 与既往「跨子轮重复率高」的结论一致；本轮 `title_dedup`（入库前按标题去重）拦掉了同标题不同 ID 的情况。

**判定：场景唯一性 = 达标（批内），跨分片去重仍缺位。**

## 4. 缺陷台账

### F1（P1）分片审核部分失败 = fail-open + 失败标记被合并丢弃

**现象**

v3.0 生成时 ReviewAgent 走 FP 分片路径，5 片 4 成功，`REQ-1791880157029-2623`（知识库检索与问答采信规则）失败，错误为「审核引用了本批次以外的用例」。该分片 **13 条用例全部 `approved` 入库，且无一条出现在 issues 列表**。

v1.0 有同类失败（同一错误 + 分页用例归属错到「需求确认」功能点）。

**代码链路**（`backend/app/agents/review_agent.py`）

1. `_run_shard` 失败返回 `(fp_id, None, err)`（:509）；
2. `ok_shards` 只筛选成功分片，`merged_issues` 只从 `ok_shards` 累加（:592-595）——失败分片的用例**没有任何 issue**；
3. `avg_confidence` 只按 `ok_shards` 用例数加权（:601-608）——失败分片不进均值；
4. `report["review_shard_partial_failure"]=True` 与 `report["shard_review"]` 确实被设置了（:608-626），但 `_merge_review_results` 用一个**全新的字典**重建最终报告（:792-812），**这两个键没有被透传**。

**证据**：三个版本的 `run.json` 终态里 grep 不到 `review_shard_partial_failure` / `shard_review` / `failed_shards` 任何一个字符串；`outcome.degraded_flags` 也无体现（v1.0 只有 `publication_partial_block`，v2.0/v3.0 为空）。

**值得写进复盘的一点**：同一个 `_merge_review_results` 里已经为 `review_degraded` 修过完全同类的 bug，注释写得很清楚——

> ⚠️ 不能只在 `_llm_review` 的返回值里打标——该返回值只是中间结果，会被本函数合并掉。实测探针正是靠这一点发现首版补丁无效的。

**这次是同一个坑的第二次踩雷**，只是换成 `review_shard_partial_failure`。根因是这函数没有"白名单透传 llm_report 全部键"或"显式忽略清单"，而是逐个手抄——每加一个字段就要记得在这里加一行。

**建议**（按代价从小到大）

1. 最小修复：`_merge_review_results` 透传 `review_shard_partial_failure` / `shard_review`，并让它进 `outcome.degraded_flags`（代价：几行；立刻让问题可见）。
2. fail-closed：失败分片的用例默认降级为 `pending_review` 而非 `passed`（代价：会改变部分批次落库分布，需要跑回归确认 241/188/112 基线）。
3. 根治：把「中间报告 → 最终报告」改成白名单外显式透传，或让 `decide_publication` 直接吃 `shard_review`，不再依赖手工搬运。

### F2（P2）`invalid_point_references` 假阳性

**现象**：v1.0 `coverage.invalid_point_ids=["api"]`，v2.0 `=["happy_path"]`，导致发布原因里多一项 `invalid_point_references`。

**根因**（两处不同，`backend/app/utils/coverage.py`）

1. **v1.0（3 条）**：用例 notes/步骤正文里含 URL，如 `调用GET /api/impact/reports接口`、`POST /api/testcases/generate接口`。`_BARE_POINT_ID_RE` 的左边界断言是 `(?<![\w\-\[.])`，**没把 `/` 排除**，于是 `/api/...` 里的 `api` 被提取成要点 ID。
2. **v2.0（5 条）**：LLM 把裸的类型名直接写进了**标题**，如「原型解析结果落库 happy_path 验证」「需求文档与原型HTML混合上传 happy_path 验证」。「原型解析预算与降级处理 happy_path 验证」等。`extract_point_ids` 会扫 title/description/notes/步骤，于是这些裸词被当成"声称覆盖的要点"。

**影响**：本轮只是污染 reason 列表（batch 级原因，没阻断 auto-approval——v2.0 仍 73 条全 auto）。但口径是错的，且在其他配置下若升级为 case 级，会造成假阻断。类似的历史坑代码注释里已经记过一次（`precondition` 假阻断）。

**建议**：① 正则 lookbehind 加 `/`、`:`；② 标题/描述/步骤只认限定形态（`xx.happy_path.N`），裸类型名不作为声称——结构化字段与 notes 方括号标注才认。修完重跑 `_dogfood_thr.py` 或直接重算 coverage 断言 `invalid_point_ids == []`。

### F3（P1）安全类断言方向写反，13 条

**现象**：把「恶意载荷」填进 `expected_value`，而 message 说的是它应当不出现：

```json
{"type":"contains","target":"processed_html","expected_value":"<script>","message":"危险script节点已移除"}
{"type":"custom","target":"processed_answer","expected_value":"DROP TABLE","message":"系统过滤SQL注入语句"}
{"type":"custom","target":"requirement.original_text","expected_value":"<script>","message":"不保存XSS脚本"}
{"type":"custom","target":"processed_html","expected_value":"javascript:","message":"javascript:链接已剔除"}
```


**分布**：v1.0 2 条、v2.0 11 条、v3.0 0 条，合计 13 条（v2.0 的安全剥离专题全部中招）。

**后果**：若按 `case_json` 生成 pytest，会得到 `assert "<script>" in processed_html`——**安全防线失效时反而通过**。这是安全测试里的假阴性，比漏测更危险。人工执行时也会误导测试员往反方向判。

**建议**：

1. 生成 prompt 里明确写死：负向断言一律用 `not_contains` / `not_in`，**禁止把载荷本体放进 `expected_value`**；
2. 入库前加一条确定性规则校验（不调 LLM）：message 含 过滤/移除/剔除/不保存/拒绝/拦截 且 `type ∈ {contains, equals}` 且 `expected_value` 命中常见载荷模式（`<script`、`javascript:`、`DROP TABLE`、`onerror`、`<iframe`、`<style`、`<img`、`<!--`）→ 记 issue 并降级 `pending_review`；
3. 顺带把 v2.0 这 11 条 + v1.0 2 条用规则修一遍（把 `contains` 改 `not_contains`，或把 expected_value 改为"空/不含载荷"的表述）。

### F4（P2）顶层 `expected` 大面积空缺，133/320

见 §3.1。v1.0 72、v2.0 23、v3.0 38。

**建议**：二选一——要么生成 prompt 强制填顶层 `expected`（模型本来做得到，v3.0 首轮样例就填了），要么把 dimension_scores 的 completeness 口径显式区分「顶层缺失」与「step 缺失」（现在 completeness 分看不出来缺口在哪一层：v3.0 completeness 0.785 但 step 层 0 缺失）。

### F5（P3，观察）澄清收敛不稳定

- v1.0：12 问一轮收敛（✅ 符合 docs/21 验收标准"澄清一轮回答后无关键级追问"）
- v2.0：9→1→1，走满 3 轮未收敛
- v3.0：第 2 轮剩余 1 条，答案生成 **0/1** → POST 空 answers → **400「澄清答案不能为空」** → driver 按收敛处理

**说明**：剩余问题不为 0 时 LLM 偶发生成不出答案；此时不是降级为"留待人工"，而是直接 400。driver 侧也有责任（空 answers 不该提交）。建议：driver 在答案 0 条时跳过该轮并显式标记；服务端澄清提交对空 answers 返回更明确的错误语义。

### F6（P3，观察）partial_block 连坐降级

v1.0：3 条 blocker → `case_level_reasons=["review_blockers"]` → `partial_block` → 剔 3 留 193；但 `persist_to_kb` 里 `auto_allowed = not decision.get("case_level_reasons")` = False → **193 条全部 `reviewed`（待人工）**，尽管置信度 0.767~0.892 全部 ≥0.70 自动入库档。

`/tmp/dogfood`、`/tmp/dogfood_state.json`、`/tmp/_review_runs` 都在容器文件系统里。本轮中途容器重启过一次，恰好没丢（restart 而非 recreate），但这是运气不是设计。下一轮建议把 driver 产物落宿主目录或挂载卷。

4. **F2（P2）**——正则补边界 + 标题裸 ID 处理，纯确定性修复。
5. **F5/F7**——driver 与部署约定，跟着下一轮一起改。
