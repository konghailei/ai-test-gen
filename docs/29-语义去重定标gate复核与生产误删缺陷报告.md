## 3. 缺陷一（致命）：评测域 ≠ 生产域

### 3.1 事实

定标语料 = `test_cases` 表 7 个批次 **1055 条**，按 `gen_batch_id` 拉取后**汇成一张两两相似度矩阵**。但这 7 个批次来自 **6 个不同需求**：

| req_id | 条数 |
|---|---|
| REQ-1791617636644-1856 | 569（303 + 266，v1.0 两轮） |
| REQ-1791623684232-1896 | 140 |
| REQ-1791531534688-5189 | 120 |
| REQ-1791591906731-3600 | 99 |
| REQ-1791598347262-3630 | 69 |
| REQ-1791599725665-3639 | 58 |

- 总对数 `C(1055,2) = 556,285`；**同 req 对 187,316（33.7%）**，跨 req 对 **66.3%**。
- 而生产里 `dedup_semantic` **只在单次生成任务的用例集上跑**（`orchestrator.py:1542` 的 `cases`、`:1855` 的 `merged_cases`，均来自同一 `req_id`；`analysis_tasks` 还有 `uq_analysis_tasks_active_generation(req_id)` 唯一约束佐证）。
- **跨 req 对在生产中永远不会被比较。**

### 3.2 实测：gate 的证据对 90% 是跨 req

用 `_chk_samereq.py` 把证据对映射回 `req_id`：

| 证据集 | 对数 | 同 req（生产真实会比较） | 跨 req（生产中不存在） |
|---|---|---|---|
| T1 `lost_detail`（用于论证"E 漏判 469 对真重复"） | 60 | **6** | **54（90%）** |
| T2 `lost_detail`（用于论证 A 漏判） | 60 | **5** | **55（92%）** |
| T4 `divergent_pairs`（用于论证 base 误删） | 40 | **5** | **35（88%）** |

### 3.3 影响

- 「T1 漏判 469 对真重复」这条**支撑 E 否决的核心论据**，其抽样明细 90% 落在生产中不存在的比较域里；
- 我逐条读了 T1 的 60 条明细，其中**明确不是重复**的至少 8 条，例如：
  - `需求状态为待审核时可提交确认（边界测试）` ≈ `需求确认操作成功`（边界 vs 正常路径）
  - `项目名称长度为1字符（边界下限）` ≈ `创建产品成功，产品名称长度为1字符（下限）`（**项目 vs 产品**，且分属不同 req）
  - `上传9MB的.md文件成功` ≈ `上传大小9.9MB的文件成功`（**9 vs 9.9**，且分属不同 req）
  → 所以「抽样全部是真重复」这句**不成立**；
- T4 的 `ratio=0.708`、`recall=32/60`、`divergent=331` 三个判据，分母都被跨 req 对污染。

> **结论**：`E_FAIL`、`T3 FAIL`、`T4 FAIL` 三个 verdict 都不能成立。E 与 A 目前处于「未验证」状态，而非「已否决」。

## 4. 缺陷二：没有正样本标签，gate 退化成「与 T0 一致」

- 归档报告 `_calib_report.json` 里 `pos_pairs_matched = 0`——**一个真实标签都没有**（原因正当：被去重的用例不落库，removed 侧匹配不到）。
- 于是 gate 被改成「相对 T0 的结构性判定」（`_calib_dedup_embed.py:gate_verdict`）：

```python
e_ok = r_t1["extra_divergent"] == 0 and r_t1["high_conf_lost"] == 0
a_ok = (r_t2["extra_divergent"] == 0 and r_t2["high_conf_lost"] == 0
        and r_t2["missed_pos"] <= r_t0["missed_pos"] + 1)
```

问题有三：

1. **把 T0 当成金标准**。判据全是"与 T0 的差异"，T0 一旦本身误删（见 §6），gate 就会**惩罚正确行为**。它结构上不可能发现「T0 判错了」。
2. **不对称**：公式里只有 `extra_divergent` 与 `high_conf_lost`，**`lost_vs_base`（T1 丢了 469 对）根本没进公式**。也就是说，一个「几乎不判重」的方案反而更容易通过 E 判据。E 之所以 FAIL，只是因为 `extra_divergent=2`——而这 2 条里 1 条是真重复、1 条是误删（见 §5）。
3. **归档产物不可复现 verdict**：公式依赖 `high_conf_lost`，但 `_calib_report.json` 里**没有这个字段**（实测 `r["T0"]["high_conf_lost"] is None`）。归档的报告无法重算出 `E_FAIL`。

> 另：`missed_pos <= missed_pos_T0 + 1` 在 `pos_pairs_matched=0` 时恒为 `0 <= 1`，是**空洞通过**。

## 5. 缺陷三：`divergent`（标题 3-gram < 0.45）不是误删信号

`summarize()` 把「判重对里标题 3-gram 相似度 < 0.45」记为"差异显著对（疑似误删）"。这条指标被用来否决 T2（5 条）和 T4（331 条）。实测反例：

**T4 的 40 条 divergent 抽样里，同 req 的 5 条全部是真重复**：

| sim | title 3-gram | 对 |
|---|---|---|
| 0.9793 | 0.385 | 管理员查看操作日志成功 ≈ 管理员成功查看操作日志 |
| 0.9662 | 0.259 | 管理员配置大模型提供商成功，验证 API Key 加密脱敏 ≈ 管理员成功配置大模型提供商 |
| 0.9464 | 0.318 | 大模型调用异常时熔断重试切换提供商 ≈ 大模型调用异常触发熔断及重试切换 |
| 0.9415 | 0.160 | 每轮澄清问题数刚好为5个，符合规则限制 ≈ 每轮澄清问题超过5个时处理成功 |
| 0.9395 | 0.083 | 每轮人工澄清问题数为5（上限）处理成功 ≈ 每轮提交5个澄清问题不超限 |

这正是**语义去重该干的事**——抓 3-gram 抓不到的改写。把它当误删指标，等于要求语义层退化成 3-gram 层。

**T2 的 7 条 extra 里，标题级判读 6 条是真重复**，只有 1 条是真空（`上传带SQL注入的.md文件被拦截` ≈ `上传带XSS的.md文件被拦截`，我复算其 large 口径 sim=0.9141 < 0.92，即 small 的越界）。

> 结论：T2/T4 的 `extra_divergent` 判据无效；它们各自的"多判"里真正的误删只有 1/7 和 0/5。

## 6. 新发现：生产正确性缺陷——语义去重 @0.92 误删

### 6.1 证据来源

`_calib_pairs.json` 是从生产日志提取的 **32 条真实去重留痕**（`removed_title ≈ kept_title` + 当时 sim），全部发生在**单次生成内**（同 req）。sim 区间 `0.9217 ~ 0.9827`——即全部由 0.92 阈值放行。

### 6.2 标题级判读：约 25-34% 是误删

| sim | removed ≈ kept | 判读 |
|---|---|---|
| 0.9455 | 管理员**编辑**项目信息成功 ≈ 管理员**创建**项目成功（核心流程） | **误删**（不同操作） |
| 0.9274 | 创建归属产品的**模块**且名称唯一成功 ≈ 管理员创建合法名称的**产品**成功 | **误删**（不同实体） |
| 0.9273 | 管理员创建**产品**成功 ≈ 创建归属**产品**的**项目**且版本号唯一成功 | **误删**（不同实体） |
| 0.9217 | 管理员创建**产品**成功 ≈ 创建**项目**归属产品成功，输入合法名称和版本号 | **误删** |
| 0.9298 | Admin creates **product** wi… ≈ Create **project** under exi… | **误删** |
| 0.9475 | 为角色分配**空**菜单权限数组 ≈ 管理员为只读角色分配菜单权限**成功** | **误删**（边界 vs 正常） |
| 0.9223 | 质量门禁**未通过**，首次回环后仍不通过则终止 ≈ 系统校验质量门禁，**通过**则完成生成流程 | **误删**（相反分支） |
| 0.9327 | 系统正确执行跨文档矛盾检测并生成澄清问题 ≈ 用户同批上传需求文档与原型HTML成功并完成来源… | **误删**（不同场景） |
| 0.9559 | 无整理版时检索返回上线时间靠后的多版本条目 ≈ 整理版聚合版本数为边界值时的兜底规则 | **误删** |
| 0.9484 | 上传后缀为 **.docx** 的合法HTML文件成功 ≈ 上传后缀为 **.markdown** 的合法HTML文件成功 | **误删**（不同扩展名=不同边界） |
| 0.9453 | 列表字段去重合并同标识条目 ≈ 按规则聚合跨版本知识时标量取最新值列表去重 | 存疑 |
| 0.9606 | 纯图片原型无任何语义节点，系统标记**纯视觉稿** ≈ 原型无语义节点，系统标记 **proto_no_sem** | 存疑 |

**明确误删 ≥ 9 条（28%），加存疑 2-3 条 → 25-34%。** 其余 20 条判读为真重复。

### 6.3 全文复核（DB 双证）

removed 侧不落库，无法逐条读全文。改用「同形态候选对」在 DB 内复算生产判定（`_chk_fp2.py`，bge-large × 整例 JSON + 0.92 + 数字护栏）：

| 候选对 | large sim | 生产判定 | 期望 |
|---|---|---|---|
| 管理员创建产品成功，输入合法名称和描述 ≈ 创建归属产品的项目且版本号唯一成功 | 0.8877 | 不重复（保留） | 应不重复 ✅ |
| 上传带SQL注入的.md文件被拦截 ≈ 上传带XSS的.md文件被拦截 | 0.9141 | 不重复（保留） | 应不重复 ✅ |
| 解析文件内容非法…标记proto_parse_failed ≈ 同批文件中一个解析异常，其他文件正常解析 | 0.9110 | 不重复（保留） | 应不重复 ✅ |
| 管理员查看操作日志成功 ≈ 管理员成功查看操作日志 | 0.9793 | **判重复（会被删）** | 应重复 ✅ |
| 输出符合规范的YAML格式语义树 ≈ 系统输出YAML格式的语义树 | 0.8933 | 不重复（保留） | **应重复 ❌ 漏判** |

说明：**同 req 内，真重复的 sim 可以低到 0.8933（漏判），不同用例的 sim 可以高到 0.9455（误删）**——两个分布在 0.89-0.95 区间重叠。**这不是"阈值调高一点"能解决的**，这一点 docs/27 §A.2 的直觉是对的，只是它把结论下成了「口径不能瘦身」，而正确结论是**「单一余弦阈值在这个表征上分辨率不够」**。

### 6.4 连带缺陷

1. **数字护栏对小数失效**：`_numbers("9.9MB") = {"9"}`（`re.findall(r"\d+")` 吃掉小数），与 `"9MB"` 的 `{"9"}` 相同 → 护栏放行。docs/26 引以为据的「9MB vs 9.9MB」正是这一类。护栏只挡住了整数边界（4次/5次）。
2. **误删不可审计**：`semantic_dedup_removed` 只进日志与 SSE，**不落库**（`review_reports` 无该字段、无 `dedup_removed` 列）。误删一旦发生，事后无法复盘全文。这是 docs/14 治理方案里"用例库质量"的一处空洞。
3. **生产可见度为零**：日志里只在去重发生时打 3 条示例，且 `docker logs` 随容器重启丢失（当前容器仅 81 行）。生产误删率**从未被度量过**。

## 7. 收益承诺重估

| docs/27 的说法 | 复核 |
|---|---|
| 全链路语义去重 `~52min → ~3-4min（12-15×）` | **无依据**。E+A 均未验证通过，12-15× 是「E 砍 80% 计算量 × A 再快 5-15×」的乘积推演，从未实测 |
| §A.5「已落袋：~52min → ~33min（1.6×）」 | **算式不自洽**：B 只省第二轮 17min，`52-17=35` 或 `52-17+1=36`，都不是 33；且该值**未实测**（无复跑对照）。D 只改观感不改耗时 |
| §0「保底 ~3×」 | 同上是推演。**B 的真实收益是 1 轮 ~17min**（docs/26 实测数据），在 526 条场景约占 30% |
| §2.3「bge-base-zh-v1.5（102M、**1024 维**、与 KB 模型同维度更稳）」 | **事实错误**：`models/bge-base-zh-v1.5/config.json` → `hidden_size=768`（small=512，large=1024） |
| 多核服务器 `÷3~4×` | 未验证（本机无多核环境），属合理外推，标注即可 |

**实测到的真实加速比（本次复核新拿到）**：`bge-base × 整例 JSON` 在 1055 条上 **0.815 s/条 vs large 3.81 s/条 = 4.7×**（T4 日志 `embed_seconds=859.6`）。这是**口径不变、判定逻辑不变**的纯加速，比 E 的"改口径"风险低得多——但被 T4 的无效判据连带否决了。

## 8. 更好的方案

### P0（最高优先，正确性）：把误删先修掉，再谈性能

性能问题让人等 35 分钟；误删问题让人**丢掉正确的用例且事后查不到**。后者优先级更高。

改动方向（低成本、可回归）：

1. **决策规则从「单一余弦」升级为「余弦 + 结构佐证」**：`semantic_near_duplicate` 目前只用 `sim ≥ 0.92`。建议要求**语义判重 ∧ 至少一条结构佐证**（标题 3-gram ≥ 0.30 ∨ 步骤 4-gram ≥ 0.20 ∨ 实体 token 集一致）。上表 9 条误删里，`产品/项目`、`编辑/创建`、`.docx/.markdown`、`空权限/正常` 这几类的 step/实体差异都很明显，能被佐证层拦住。
2. **实体/操作护栏扩维**：现有 `_numbers` 只比数字集合。扩成 `{数字} ∪ {实体名词（产品/项目/模块/角色/需求/功能点…）} ∪ {操作动词（创建/编辑/删除/审核/归档…）} ∪ {否定词（未/不/无/空）} ∪ {文件扩展名}` 的 token 集比较，集合不同即不合并。**零 embedding 成本**。
3. **修小数护栏**：`_numbers` 用 `\d+(?:\.\d+)?` 归一后比较。
4. **留痕落库**：把 `semantic_dedup_removed` / `dedup_removed` 写进 `review_reports`（或新表 `dedup_traces`），带 removed 的完整 case_json。**没有这个，误删率永远测不出来，也无法回归验证 P0。**

回归基线：把 `_calib_pairs.json` 的 32 条留痕升格为固定用例集（9 条应保留、23 条应合并），作为 `test_case_dedup.py` 的守卫。

### P1（前置，评测重建）：先有可用的评测，再裁决口径/模型

没有这一步，E/A 的取舍只能靠猜。

1. **评测域改为 per-req**：每个 req 单独建相似度矩阵（v1.0 的 569 条是最有代表性的生产规模），只统计同 req 对。
2. **建真标签集**：正样本 = 生产留痕里人工确认的真重复；负样本 = 每 req 内随机 + 低 title-sim 高分对（易混对）分层抽样，用 LLM 判重 + 人工抽查确认。
3. **比 PR 曲线而非固定阈值**：每个方案在自己的最优阈值下比 Precision/Recall/F1。**这才是「E 是否可行」「small/base 是否可用」唯一站得住的判据**。
4. 附带产出：T0 在 per-req 域下的真实判重对数与误删率（现在这个数字是空白）。

### P2（性能，零判定风险）：不换模型也能拿到 3-5×

1. **ONNX Runtime + int8 量化，仍用 large**：同模型 → 判定几乎不变（可用 P1 的标签集验证量化前后一致率），CPU 通常 2-4×。docs/27 只在"内存超限"时提过 ONNX，没当加速手段用。
2. **把 embedding 移出关键路径**：docs/26 实测生成阶段 API 容器 CPU 仅 ~45%，**生成是 LLM-bound 的**。每生成完一个 FP 就在后台线程把该 FP 的用例 embed 进 B 的缓存 → 到合并点时去重只剩余弦计算（秒级）。这不是"缩短 35 分钟"，而是"让 35 分钟不再存在"。
3. 缓存跨进程持久化（Redis）——仅在 2 不成立时才需要。

### P3（表征层，可选，需 P1 评估）

**去各向异性（mean-centering / all-but-the-top-k）**：bge 类句向量的各向异性是"所有对的余弦都被抬高、分布挤在 0.9+"的根因，也正是 docs/27 §A.2 观察到的"结构共现抬高余弦基数"。在 embedding 出口做**减去语料均值**（或去前 k 个主成分），是标准做法，能显著拉开分布——**且对 small/base 同样有效**，可能让「小模型 + 去各向异性」拿到 docs/27 原本想要的 5-15×。改动只有几行，但**必须用 P1 的标签集评估**再定。

### 方案对照

| 方案 | 改动量 | 预期收益 | 代价/风险 | 前置 |
|---|---|---|---|---|
| P0 决策规则 + 实体护栏 + 留痕落库 | 中 | 误删 28% → 目标 0（可回归） | 需重标阈值；护栏过严会漏报 | 无 |
| P1 评测重建（per-req + 标签集 + PR） | 中（脚本为主） | 让 E/A/量化/去各向异性**可裁决** | CPU ~1-2h（大模型 embed） | 无 |
| P2-1 ONNX int8（同模型） | 小 | 2-4×，判定不变 | 需装 onnxruntime；量化掉点需 P1 验证 | P1 |
| P2-2 生成期预计算 | 中 | 去重等待 ~35min → 秒级 | 与生成并发抢 CPU；需控制并发度 | 无 |
| P3 去各向异性 + 小模型 | 小 | 潜在 5-15× | 需 P1 验证；改口径需递增版本号 | P1 |
