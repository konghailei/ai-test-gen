# 项目管理系统 v2.0 需求文档（原型 HTML 上传与语义解析）

> 产品：AI 测试用例生成平台
> 项目版本：v2.0（增量优化——原型 HTML 上传与语义解析）
> 优先级：P1
> 与 v1.0 的关系：本版本为 v1.0 基础上的增量变更。未提及的需求沿用 v1.0（本文引用处注明"沿用 v1.0 §x.x"）。

---

## 1. 变更概述

在 v1.0 的需求文档上传能力（沿用 v1.0 §3.2，当前支持 .md/.docx/.txt）基础上，新增**静态原型 HTML 文件上传与语义解析**能力，使 UI 原型（Axure/墨刀等工具导出的 HTML）可作为需求输入的一部分参与解析、澄清与用例生成。

## 2. 变更点详述

### 2.1 上传格式扩展（变更 v1.0 §3.2.1）

2.1.1 上传格式白名单扩展为：.md / .markdown / .docx / .txt / **.html / .htm**。

2.1.2 HTML 文件内容校验：文件解码后（UTF-8，失败回退 GBK），取前 512 字节转小写，须包含 `<!doctype html`、`<html`、`<head`、`<body`、`<div`、`<script` 之一，否则拒绝并提示"不是有效的 HTML 文件"。此规则兼容无完整 html 包裹的片段式原型导出。

2.1.3 单文件大小上限沿用 10MB。原型 HTML 常内嵌 base64 图片导致体积虚胖，本版本不放宽上限。

### 2.2 安全剥离（新增）

HTML 解析前强制执行安全剥离（不可配置关闭）：

- `<script>`、`<style>`、`<noscript>`、`<template>` 节点整体移除；
- `on*` 事件属性（onclick/onerror 等）全部过滤；
- `javascript:` 与 `data:text/html` 协议的链接剔除；
- `<iframe>`、`<object>`、`<embed>` 保留语义标记但剔除其 URL（标记 [external]）；
- HTML 注释（`<!-- -->`）不参与解析，注释中的文字不得出现在解析结果中。

### 2.3 语义树解析（新增）

2.3.1 解析产出为语义树（YAML 格式，对齐 Playwright ariaSnapshot 规范），标签映射规则：

| HTML 元素 | 语义节点 | 提取的约束属性 |
|---|---|---|
| h1-h6 | heading（含 level） | — |
| 文本类 input（text/tel/email/number/password/date） | textbox | required、maxlength、minlength、pattern、min、max、placeholder、readonly、disabled |
| checkbox | checkbox（选中态标 checked） | required、disabled |
| 同名 radio 组 | radio（组内枚举选项全列出） | — |
| file input | fileupload | accept、multiple |
| textarea | textbox（标 multiline） | maxlength、required |
| select/option | combobox（选项全列出） | multiple |
| button/按钮样式的链接/submit | button | disabled |
| 链接 | link（外链标 [external]） | — |
| table | table（附列名） | 表格内容转为 Markdown 表格 |
| dialog / role=dialog / 模态样式 | dialog | — |

2.3.2 字段命名优先级：aria-label > label[for] 关联 > 嵌套 label 包裹 > placeholder > title > 邻近文本（dt/dd 配对、表格左侧单元格）。全部无法取得名称的字段命名为"(未命名字段)"，并在解析统计中汇总数量。

2.3.3 归一化规则：无 alt 且邻近无文本的图片不输出；无名称、无角色、无语义属性的纯布局容器（div/span 等）递归压平，子节点上提到最近的有名祖先节点。

2.3.4 base64 内嵌图片（src 以 data:image 开头）提取后走既有图片识别链路（沿用 v1.0 §3.2.4 视觉模型规则）。

### 2.4 解析预算与降级（新增）

2.4.1 语义树节点数上限 400：超限截断并在树尾追加截断说明，同时记录降级标记 proto_tree_truncated。

2.4.2 单文件解析耗时上限 10 秒：超时降级为纯文本提取（不做语义树），记录标记 proto_parse_timeout。

2.4.3 解析异常（文件内容非法导致解析器报错）：该文件降级为纯文本提取，记录标记 proto_parse_failed，且不得阻断同批其他文件的解析。

2.4.4 页面无任何语义节点（无表单控件、无表格、无按钮）时记录标记 proto_no_semantics，提示该原型可能为纯视觉稿。

2.4.5 全部降级标记须在任务结果中透出，前端可展示。

### 2.5 与需求文档混合上传（新增）

2.5.1 需求文档与原型 HTML 可同批混传（如 1 个 md 需求 + 1 个 html 原型）。原型内容以独立边界标记 `【原型：文件名】` 拼接，与需求文档的 `【文档：文件名】` 标记区分来源。

2.5.2 跨文档矛盾检测（沿用 v1.0 §3.4.1）适用于需求文档与原型之间：例如需求文档声明"手机号非必填"而原型中该输入框带 required 属性时，应产出矛盾类澄清问题。

### 2.6 解析与澄清联动（新增）

2.6.1 语义树中带约束属性的字段进入需求结构的 UI 规则（ui_rules）维度，并纳入用例生成的必覆盖清单与覆盖率统计——即 UI 规则类要点未覆盖时与其他要点同样参与补生成判定。

2.6.2 检测到原型来源时，澄清环节追加原型专属问题：

- 存在未命名字段时：要求补充字段业务含义；
- 字段有格式约束（pattern/长度边界）但无业务原因时：询问约束的业务背景与边界情形；
- 删除类按钮：询问是否有二次确认交互；
- 静态盲区：原型为静态文件，无法体现字段联动、异步校验、动态显隐、页面跳转逻辑，须向用户逐项确认。

2.6.3 原型内容作为待分析数据处理：即使原型文本中出现"请忽略以上要求""你现在是 XX"等指令性文字，也一律作为普通文本处理，不得执行。

### 2.7 落库口径（新增）

原型解析结果以文本形式存入需求的原始文本字段（与 docx 提取文本口径一致）；系统不保存 HTML 原始字节；来源文件名列表自动包含 .html 文件；不新增数据表。

## 3. 验收标准

- 混合上传（md 需求 + html 原型）后，需求结构的 UI 规则维度包含原型中的字段约束（必填/长度/格式）。
- 原型中的 required/pattern/maxlength 约束出现在生成用例的边界值验证中。
- 恶意原型（含 script 标签、on* 属性、指令性文字）解析后无脚本残留、指令不被执行。
- 超大原型（>400 节点）正确截断并透出降级标记。
- 原型与需求文档的矛盾（required vs 非必填）被澄清环节检出。
