## 3. v1.0 项目（正式轮）

> 项目 `PROJ-565-77458-400`（v1.0 基线-系统核心功能），需求 `REQ-1791591906731-3600`，2026-10-10 执行。

### 3.1 流程缺陷（本轮实证，复现 3 次）

**DEF-1 FP 复用过滤导致新需求 FP 恒为空**：
- 现象：上传/澄清/regenerate 后 FP 均为 0 条。容器内探针实锤——`_fp_extract_from_raw` 把产品下历史 FP（冒烟轮 14 条 + 坏映射 3 条）全部列为复用候选，LLM 将其全部标记 `reuse_existing: true`，代码过滤后 `new_fps=[]`，且**复用结果不落库**（req_agent.py:1071-1074 仅过滤不登记）。
- 复现：regenerate ×3（含把历史 FP 改名为「冒烟-*」「smoke-*」降低相似度）均 0 条，说明弱匹配 0.68 相似度阈值对语义相近的系统需求（同产品自举场景）形同虚设。
- 解除阻塞：psql 删除 17 条历史 FP 后 regenerate，FP 正常拆出 9→11 条。
- 待办：复用命中应在需求下登记复用关系或允许"强制新建"开关（本轮走文档化，代码修复另立任务）。

**DEF-2 FP 删除接口 500**：`DELETE /requirements/{rid}/fp/{fp_id}` 的级联清理 SQL（`jsonb_set` 对 json 列 `::jsonb` 转型语句在 asyncpg 预编译时报 `syntax error at or near ":"`），事务中断后续 SELECT 全部 `InFailedSQLTransactionError` → 500。与 v3.1.3 P4 修复同源，转型写法仍不兼容 asyncpg 参数化。本轮改用 psql 直删。

### 5.4 多轮复测总结论

1. **生成质量稳定**：三轮 99/69/58 条用例，可执行合同满分、零重复标题、置信度 0.798~0.914 全部达标，FP 覆盖率逐轮 100%（v2.0 起）；
2. **流程正确性**：11 步流程（建项目→上传→解析→澄清→FP→审核→确认→生成→依赖检查→归档→KB 验证）全程可走通，模块挂接/门禁/发布决策均按设计工作；
3. **两个新缺陷待修**：DEF-1（FP 复用过滤导致新需求 FP 恒空 + 复用不落库）、DEF-2（FP 删除接口 jsonb 转型 SQL 在 asyncpg 下 500）；
4. **KB 累积验证受阻于两个前置**：知识固化以项目归档为前提（冷启动现象符合设计）；跨版本聚合以同名 FP 为前提（自举场景 FP 命名天然不重叠）。后续轮次应让 v2.0/v3.0 文档复用 v1.0 的 FP 命名体系，或以影响分析驱动跨版本关联。
