# 自证第四轮（修正版）· 用例质量与可执行性分析（2026-10-20）

> **本报告修正 docs/35 的方法论偏差**：docs/35 的动态部分实际是"对系统做接口冒烟"（只覆盖 4.8% 的用例），
> 本报告改为**直接分析用例这一交付物本身**：客观六维量化 + 分层抽样 LLM 评审。
> 数据：`_e2e_tmp/self_r4_quality.json`（客观指标）、`self_r4_llm_review.json`（40 条评审明细）。

## 1. 核心结论（先说结论）

1. **这批用例是"文档型用例"（human-readable），不是"可执行型用例"（machine-executable）**：无 DSL、无元素定位规范、断言 target 近半是抽象命名空间。
2. **可执行性偏低**：分层抽 40 条 → 可直接执行 **1 条（2.6%）**、需补细节才能执行 **28 条（71.8%）**、**不可执行 10 条（25.6%）**；平均 **2.79/5**。
3. **缺陷是系统性的，不是随机噪声**，集中在 5 类：入口/元素定位缺失、断言 target 不可观测、场景数据缺失、故障注入不可控、断言语义矛盾。
4. **docs/35 的"11 条用例缺陷"只是"语义可执行性"的一个子集（接口路径，覆盖 4.8%）**；真正的可执行性问题覆盖 **97.5%** 的用例面。之前"系统 0 缺陷"只对接口行为成立，不代表用例质量合格。

## 5. 根因分析（对照生成链路）

| 缺陷类型 | 根因 | 是否已有约束 |
|---|---|---|
| 入口/元素定位缺失（33% 界面步骤） | 生成 prompt 没有"每步必须可定位"的强制要求；无 UI 契约（路由/选择器）输入 | ❌ 无 |
| 断言 target 抽象/不可观测（48.9%） | 生成时没有断言命名空间规范，也未提供响应结构/UI 元素清单 | ❌ 无 |
| 场景数据缺失（账号/revision/ID） | test_data 是"字段值"级，未要求"场景前置数据"（多用户、多版本、并发基线） | ❌ 无 |
| 故障注入不可控 | 异常类用例没有"注入方式"字段（哪个开关/接口/时序） | ❌ 无 |
| 断言语义矛盾 | 生成后无一致性校验（expected 与 assertions 交叉验证） | 部分（`_path_check` 只查路径） |

**结论**：这不是"个别用例写差了"，而是**生成器的输出规格缺了"可执行性四要素"**：可定位操作对象、可观测断言目标、可驱动场景数据、可复现故障注入方式。文档型用例天然缺失这些，因为 LLM 只需"说清业务"，不必"说清怎么点"。

## 7. 改进建议（按优先级，待拍板）

> **2026-10-20 修订（重要）**：初版建议"用四要素硬约束逼出具体性"是**错的**——实测需求文档信息面：
> API 路径 44 处、**UI 页面/菜单/入口仅 7 处、元素定位 0 处、具体字段名 6 处**；
> 而用例界面型步骤占 45%。需求没给的信息，强约束只能逼模型**编造**（"项目详情页右上角按钮"），
> 比模糊更危险。故改为**分级约束**：硬约束只禁"编造"，具体性要求按信息量分级。

### 7.1 约束分两层（核心原则）

| 层级 | 约束 | 性质 |
|---|---|---|
| **硬约束（必须）** | **禁止臆造**：不得编造页面路径、元素名、字段名、错误码、接口路径；信息不足时必须显式标注缺口 | 不可妥协 |
| **软约束（有信息才要求）** | 有 API 契约 → 步骤写接口+方法；有 UI 描述 → 写页面/入口；有响应结构 → 断言写具体字段；有数字规则 → 原值出现 | 按输入信息量触发 |

### 7.2 用例三级质量分级（替代"一刀切可执行"）

| 级别 | 判定 | 处置 |
|---|---|---|
| **A 可执行** | 步骤对象可定位、断言可观测、数据齐全（信息都来自需求/契约） | 可交付自动化/人工执行 |
| **B 需补细节** | 对象明确但缺具体值（如知道"归档操作"但入口待定） | 人工补 1-2 处即可执行 |
| **C 待需求澄清** | 需求未覆盖关键信息，用例显式标 `needs_requirement_detail` + 缺口清单 | **不要求可执行**；缺口回喂 ClarifyAgent 补澄清 |

**关键**：C 级不是"失败用例"，而是**需求缺口的真实暴露**——这是产品价值，不是缺陷。

### 7.3 具体措施

| 优先级 | 措施 | 预期效果 |
|---|---|---|
| **P0** | prompt 加「禁止臆造 + 缺口显式标注」：信息不足时写"（入口待需求补充）"并登记 `_info_gaps`，**不得编造** | 把"编造的具体性"换成"诚实的缺口" |
| **P0** | **用例形态对齐信息供给**：需求给 API → 优先生成接口型用例；无 UI 描述 → 不硬拆界面步骤（当前 45% 界面步骤 vs 需求 7 处 UI 描述，是主要错配来源） | 从源头减少"无依据的界面步骤" |
| **P1** | 断言 target 规范（有响应结构时用 `response.body.data.x`；无结构时用语义断言 + 标 C 级） | 收敛抽象断言且不逼编造 |
| **P1** | 生成后分级器：自动判 A/B/C + 编造率检测（用例中的具体元素是否能在需求找到依据） | 度量从"可执行率"改为"编造率 + 分级分布" |
| **P1** | 缺口回喂 ClarifyAgent（用例缺口 → 澄清问题） | 形成"生成↔澄清"闭环 |
| **P2** | 步骤 DSL + 元素定位规范 + 执行器 | 需要 UI 契约输入，架构级 |

### 7.4 验收口径也要改

- ❌ 不追"可执行率 100%"（信息不够时不可能）
- ✅ 追两个指标：**编造率 → 0**（硬指标）+ **A 级占比随信息完备度提升**（如需求含 UI 描述时 A 级应显著提高）
- 复评时按"分级分布"看，而不是只看均分

## 8. 结论

- **用例可执行性：不合格**（2.6% 可直接执行，25.6% 不可执行，均分 2.79/5）。
- **问题性质：系统性生成规格缺失**（缺四要素），不是随机错误；与"接口路径幻觉"同源——都是**生成时缺少被测系统的契约/结构输入**。
- **对产品的含义**：当前输出适合"给测试工程师做人工用例参考"，**不适合作为自动化执行资产**；若产品定位包含"可执行用例"，这是必须补的能力缺口。
- 下一步建议：先落 P0 两项（**禁止臆造 + 缺口显式标注**、**用例形态对齐信息供给**），再抽 40 条复评。
  **验收口径改为**：① 编造率 → 0（硬指标：用例中的具体元素必须能在需求/契约中找到依据）；② 分级分布改善（A/B/C 占比），不追均分——信息不足时 A 级本就不该多。

| 口径 | A/可执行 | 说明 |

### 9.4 缺口闭环（v2.49 已落地）

**先纠正一个时序事实**：用例生成阶段**没有澄清节点**——已确认需求在
`orchestrator.select_channel` 强制 `enable_clarify=False`（`orchestrator.py:701-703`），
澄清只存在于**需求分析阶段**（`clarify_agent.py:372` 调 `_detect_prd_specific_gaps`）。
所以缺口只能在澄清期问出来（**前置**），不存在"生成后回喂澄清"。

**已实施**：`_detect_prd_specific_gaps` 新增 `_detect_executability_gaps()`，4 类检测：

| 检测 | 触发条件 | 问什么 |
|---|---|---|
| `exec_ui_entry` | 有页面/界面操作描述，但无**强入口信号**（左侧/顶部/导航栏/路由/页面路径） | 在哪个菜单/页面入口？ |
| `exec_api_response` | `api_definitions` 有 path 但 `response_body` 为空 | 该接口返回哪些字段？ |
| `exec_scene_data` | 涉及并发/多角色/多版本，但无账号或基线数据 | 需要哪些账号与基线数据？ |
| `exec_fault_inject` | 有降级/熔断/超时场景，但无**强注入信号**（模拟/注入/演练/mock） | 如何模拟该故障？ |

- **强信号判定**：初版用全文关键词共现，实测三份文档仅触发 1 条（"菜单权限控制""产品可配置"误救）；
  改为强信号后触发 1/2/3 条，与实测缺口吻合。
- **开关（两层）**：
  - 系统级 `CLARIFY_EXECUTABILITY_GAPS_ENABLED`（默认 True）——运维一键全关；
  - 需求级 `requirements.executability_clarify`（默认 True）——**上传弹窗勾选**
    「补充可执行性追问（推荐）」，用户可自主选择；生效 = 两者 AND。
- **后置分级器不设开关**：只打标记、不改流程、不影响用户，始终开启。
- **后置展示**：C 级用例的 `_executability.reasons` 已随 case_json 落库，前端可直接渲染（UI 未加）。
- **不做**：生成后自动回退状态机重新澄清（产品决策，不建议自动化）。

#### 4.x 补丁 v4.1.2（2026-10-22）：检出 → 落地的断点修复

第四节初版的四类检测**检出可靠、落地不确定**。同一份文档两次运行，规则层稳定检出
8 条，但最终澄清问题里 gap 类一次 2 条、一次 0 条——因为产出只被塞进
`completeness["important_missing"]` 当 **LLM 的参考材料**，转不转成问题由 LLM 自由裁量，
代码里没有任何确定性到达 `questions` 的路径。

**实测证据（v2.49 端到端，959 条用例）**：9 条不可执行用例归因为入口定位缺失 5、
故障注入缺失 2、接口未指明 2 —— **7/9 正好落在本检测该覆盖的范围内**，判据有效，
失效的只是最后一步交付。

**修复（三处）**：

| 位置 | 改动 |
|---|---|
