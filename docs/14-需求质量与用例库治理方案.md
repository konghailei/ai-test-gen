# 14 — 需求质量与用例库治理方案

> 编制日期：2026-09-11 ｜ 代码基线：`backend/app/VERSION` = 3.2.14
> 关联文档：`docs/13-case-generation-logic.md`（链路快照）、`docs/01-requirement-parsing.md`、`docs/02-knowledge-base.md`
> 业界参照：Meta TestGen-LLM（Assured LLMSE）、工商银行测试资产知识库、天猫 AI 用例生成、百度 RAG + 用例库实践

---

## 0. 为什么是这两个方向

用例质量的上限由两个变量决定：

```
最终用例质量 ≈ f(需求输入质量, 知识复用质量)
```

- **需求输入质量**：需求本身缺失的信息，任何生成能力都补不回来。天猫的实测结论很直白——C 端业务采纳率 85%，B 端（资金/供应链）不到 40%，**根因是 PRD 质量而非模型能力**。
- **知识复用质量**：系统已有历史用例沉淀，但"取出来用"的链路质量决定了复用价值。工行做到 59% 资产复用率，靠的是"标签过滤 + 混合召回 + reranker + 阈值"这套检索治理，不是靠模型更强。

两个方向都指向同一件事：**把不确定的 LLM 判断，换成可验证的规则信号**。

### 1.2 方向 B：用例库沉淀与使用

**沉淀侧**（`agents/review_agent.py:602-870` `persist_to_kb()`）：

| 条件 | 落库状态 |
|---|---|
| `confidence ≥ 0.70` 且非 blocker | `approved`（自动，无人工） |
| `0.60 ~ 0.70` | `reviewed` |
| `< 0.60` 或 blocker | `draft` + `error_cases` |

沉淀本身是通的（含标题级去重、savepoint 隔离、向量双写）。问题在于**准入只看生成时的 confidence**——这个分数是生成期自评 + 规则聚合，没有实战验证。

**使用侧**，三条通道各有问题：

| 通道 | 实现位置 | 问题 |
|---|---|---|
| Few-shot 参考 | `agents/gen_agent.py:115-152` | **不是语义检索**：先取该产品最近更新的 10 条 approved，再在其中按模块过滤取前 3。候选池被锁死在"最近 10 条"，用例攒多后大概率召回为空 |
| 回归基线 RTS | `core/fp_cases.py:75-95` `aggregate_latest_cases()` | 口径清晰（受影响 FP 按 `go_live_date` 最大项目取 approved），可用 |
| 模式参考 | `agents/gen_agent.py:156-190` + `db/milvus_store.py:841-850` | 只有 8 条固定种子；检索**无相似度阈值**，必返 3 条；`usage_count` / `success_rate` 零更新；无增删改接口 |

**反馈侧——完全空缺**。`db/models.py` 的 `TestCase` 表已有三个为本用途预留的字段，但全项目零引用：

```python
execution_count: Mapped[int]      # 零引用
last_pass_rate: Mapped[float]     # 零引用
weight: Mapped[float] = 1.0       # 零引用
```

这三个字段对应的正是业界闭环的核心——工行的"14 维度质量评分 + 低质量自动建议改进"、百度总结的"执行结果回流标记正负样本"、TestGen-LLM 的 `Improve` 过滤器。**字段已经建好，缺的只是把它接上。**

## 2. 方向 A：需求质量提升方案

### A1. 修正质量评分口径（P0，约 30 行）

> ⚠️ **2026-09-11 复核：本节的"问题"判断不成立，须重写目标。** 真实情况是规则公式**已经在生效**、LLM 自评是死代码。照本节原描述改将产生**零行为变化**。修正后的目标见 **§8.1 第 3 项**：改为「重设规则公式权重 + 决策是否接回 LLM 自评」。

**问题**：`_calc_quality_score()` 让 LLM 自评成为主口径。

**改法**：反转为"规则为主、LLM 为辅"。

```
新公式（建议）：
overall = structure_score × 0.35      # 结构完整度（规则，见 A2）
        + rule_completeness × 0.25    # 完整性检测（规则）
        + ambiguity_score × 0.15      # 歧义检测（规则，反向计分）
        + llm_self_score × 0.15       # LLM 自评（降权为参考）
        + clarification_score × 0.10  # 澄清收敛度（规则）
```

同时修正 `eval_answer_coverage()` 的硬编码返回：`1.0/0.8` 改为按"已回答且被判定覆盖的问题占比"计算。

**收益**：门禁的"质量评分"Blocker 从"模型自评"变成"可由人复核的规则分"，可解释、可复现。

### A2. 新增结构完整度评分（P0，约 80 行）

这是需求质量方案的核心——把"需求有没有写全"变成可量化的分。

**评估维度**（按 SRR 字段，分必填/建议两档）：

| 档位 | 字段 | 权重 |
|---|---|---|
| 必填 | `requirement.title` / `requirement.summary` / `flows.happy_path.steps` | 各 10% |
| 必填 | `flows.alternate_flows`（异常分支） | 10% |
| 必填 | `business_rules`（至少 1 条） | 10% |
| 建议 | `data_constraints`（有输入字段时） | 10% |
| 建议 | `preconditions` | 5% |
| 建议 | `non_functional`（至少一类：性能/安全/兼容/可访问） | 10% |
| 建议 | `acceptance_criteria` / 验收语义规则 | 10% |
| 建议 | `api_definitions`（涉及接口时） | 10% |
| 建议 | `user_roles`（涉及权限时） | 5% |
| 建议 | `dependencies` / `ui_rules` / `data_model` | 各 3.3% |

**实现要点**：
- 新增 `utils/requirement_quality.py`，函数 `calc_structure_score(srr) -> dict`
- 返回 `{score, filled: [...], missing: [...], applicable: {...}}`，`missing` 直接用于澄清（见 A3）
- "适用性判断"很关键：不涉及接口的需求不该因缺 `api_definitions` 扣分。用简单规则（如存在 `optimization_context` 或 `change_type=optimized` 时才要求 `api_definitions`）

> ⚠️ **2026-09-11 复核：上表有 3 个字段在顶层 SRR 根本不存在，占 30% 权重会恒判缺失。**
> `agents/req_agent.py:472-474` 已把 `business_rules` / `data_constraints` / `acceptance_criteria` 从顶层 `srr.pop()` 掉（v2.40 迁移：`business_rules`→`cross_fp_interactions.shared_business_rules`；`data_constraints`/`acceptance_criteria`→`assumptions`），它们**只存在于 FP 子 SRR**。
> 因此签名应改为 `calc_structure_score(total_srr, fp_srrs: list) -> dict`：总 SRR 评结构性字段、FP 子 SRR 评业务规则类字段。顶层实测字段清单与逐项可用性见 **§8.2 缺陷 1、2**。

**收益**：产出可展示的"需求完整度报告"，并让门禁有据可依。

### A3. 澄清从"问题驱动"改为"缺口驱动"（P1）

**现状**：ClarifyAgent 生成问题（LLM + KB 检索辅助），收敛靠 LLM 判定答案是否覆盖问题。

**改法**：A2 的 `structure_score.missing` 直接作为澄清问题的种子来源，与 LLM 生成的问题合并：

```
澄清问题池 = structure_gaps（规则，优先）
           ∪ llm_questions（LLM 生成，补充）
           ∪ kb_gaps（KB 比对发现的缺失维度）
```

优先级：结构缺口 > KB 缺口 > LLM 自由生成。这样澄清有明确的"补全目标"，而不是等 LLM 发挥。

**收益**：澄清轮次收敛更快、更可预期；结构缺口是确定性的，不受 LLM 波动影响。

### A4. 门禁纳入结构完整度（P1）

在 `core/quality_gate.py` 的检查项中新增：

| 类型 | 条件 | 建议阈值 |
|---|---|---|
| Blocker | `structure_score < 0.35` 且非冷启动 | 需求过于简略，强制打回 |
| Warning | `structure_score < 0.60` | 提示"建议补充 X / Y / Z" |
| Warning | 冷启动模式 | 保留现有提示，但附带结构缺口清单 |

注意：**门槛要保守**。结构分低不等于需求不能用，Blocker 阈值定得过严会重演冷启动死锁（v3.5 的教训）。建议先用 Warning 跑一段时间，观察分布后再决定是否升级为 Blocker。

### A5. 需求质量报表（P2）

在需求详情页展示：
- 结构完整度分 + 缺口清单（可点击跳转到对应编辑入口）
- 质量分构成拆解（结构/完整性/歧义/LLM 自评/澄清度 各占多少）
- 澄清轮次与收敛原因

作用：让"需求写得好不好"对用户可见——**没有度量就没有改进动力**（这也是 `docs/13 §4.4` 的同类问题）。

## 3. 方向 B：用例库沉淀与使用方案

### B1. 沉淀标准：分级准入 + 来源标记

**保留现有三级**（approved / reviewed / draft），但做两处增强：

**① 增加"核准来源"标记**

现在 `confidence ≥ 0.70` 直接自动 approved，没有人工环节。v3.5 把阈值从 0.85 降到 0.70 是为了解决冷启动死循环（合理），但代价是 approved 里混着"未经人看的自动核准"。

建议：保留自动 approved，但用 `source` 字段区分（现已有 `ai_generated` / `reused`，扩展为）：

> ⚠️ **2026-09-11 复核更正**：`reused` **未落到 DB 列**。DB 列 `TestCase.source`（`db/models.py:106`）实际只写 `ai_generated`（`agents/review_agent.py:727/748/768`）与 `manual`（`api/testcases.py:303`）；`reused` 只存在于 `case_json.source`（`core/orchestrator.py:851`）。本节分级方案依赖 DB 列，**需先补齐 `reused` 的列写入**。详见 **§8.2 缺陷 3**。

| `source` | 含义 | 检索权重 |
|---|---|---|
| `human_approved` | 人工复核通过 | 1.0 |
| `ai_approved` | confidence ≥ 0.70 自动核准 | 0.7 |
| `reused` | 回归复用基线 | 1.0（本身已是历史基线） |
| `imported` | 外部导入 | 按导入时标注 |

**② 补充结构完整性校验**

落库前校验 UTCF 必填字段（`title` / `steps` / `assertions` / `related_fp` / `notes` 要点标注）齐备。缺字段的降级到 `reviewed`，不直接 approved。

### B2. 使用规则：三条通道统一"阈值 + 限量 + 可追溯"

**统一原则**（对应工行的检索治理）：

1. 任何注入 prompt 的知识都必须过**相似度阈值**
2. 必须有**数量上限**
3. 必须**可追溯**（记录注入了哪些知识源，便于事后归因）

| 通道 | 取数规则（建议） | 数量 | 阈值 | 改造位置 |
|---|---|---|---|---|
| **Few-shot 参考** | 向量语义检索（`search_similar_cases`，按 `product_id` 过滤）+ 模块/类型二次筛选 | 3–5 | cos ≥ 0.75 | `agents/gen_agent.py:115-152` |
| **回归基线 RTS** | 保持不变（受影响 FP 的 `go_live_date` 最新版 approved，全量复用） | 全量 | 不设（本身即基线） | `core/fp_cases.py` |
| **模式参考** | 向量检索 + score 过滤 | ≤ 3 | cos ≥ 0.75 | `db/milvus_store.py:841` + `gen_agent.py:156` |

**Few-shot 改造是最高优先级**——系统里 `vector_store.search_similar_cases(query, top_k, product_id)` 已经存在（ReviewAgent 用它算 `match_score`），GenAgent 却走了一个 `order_by(updated_at.desc()).limit(10)` 的近似。改动量约 20 行，复用已有能力。

### B3. 反馈闭环：激活三个死字段（核心）

这是让用例库"越用越准"的机制，也是与业界差距最大的一环。

**字段激活方案**：

| 字段 | 何时更新 | 更新规则 |
|---|---|---|
| `execution_count` | 用例被检索命中并注入 prompt 时 | `+= 1`（记录"被使用过"） |
| `last_pass_rate` | 有执行结果回流时（CI/CD 对接或人工标记"此用例有效"） | 移动平均，如 `0.7×old + 0.3×new` |
| `weight` | 定期重算（见下） | 综合质量权重 |

**`weight` 计算建议**：

```
weight = 0.35 × 人工采纳率        # feedback.accepted 的比例
       + 0.25 × 质量分            # 6 维度 dimension_scores 的 completeness/coverage
       + 0.20 × 使用频率归一化      # execution_count 的 log 归一化
       + 0.20 × 通过率             # last_pass_rate（无数据时取中性值 0.5）
```

**闭环流程**：

```
生成 → 审核（人工/自动）→ 沉淀（approved，标记 source）
  → 检索使用（few-shot / RTS，execution_count += 1）
  → 人工反馈（api/testcases.py 的 /feedback：accepted/rejected）
  → 定期重算 weight
  → 影响下次检索排序（见 B4）
```

**检索排序接入**：

```
rank_score = 0.6 × semantic_similarity
           + 0.3 × weight
           + 0.1 × recency
```

这样"人工认可、用过且有效的用例"会排在前面，而不是"最近更新的"。

### B4. 用例治理：定期扫描与淘汰（P2）

对应工行的"14 维度质量评分 + 低质量自动建议改进"：

- **定期任务**（建议每周）：扫描 `weight < 0.3` 且 `execution_count = 0` 的 approved 用例 → 标记为"待复核"，降权处理
- **长期未命中**：`execution_count = 0` 且入库超过 N 个月 → 建议归档（写入 `archived_at`）
- **冲突检测**：语义相似度 > 0.9 的用例对 → 提示合并（现在是标题级去重，跨批次的语义重复仍会入库）

### B5. 用例库质量报表（P2）

在知识库管理页增加：
- approved / reviewed / draft 三级占比
- 复用率（被检索命中的用例数 / approved 总数）—— 对标工行的 59%
- weight 分布直方图
- Top-N 被复用最多的用例、Top-N 从未被复用的用例

## 6. 风险与注意事项

1. **阈值不要照搬**。业界用的 0.75 是在 bge-large-zh + reranker 的管线上调出来的。本项目用的嵌入模型不同，建议先用"不设阈值但记录 score 分布"，跑一批真实数据后再定阈值，而不是直接照抄。
2. **结构分先做 Warning 不做 Blocker**（见 A4）。冷启动死锁的教训（v3.5）说明：门槛定错会让流程卡死而不是变好。
3. **weight 需要冷启动数据**。初期人工反馈少，`weight` 会集中在中性值附近，排序效果有限。可以先用 `source` 分级（人工 approved 优先）作为过渡，等反馈积累够了再上 weight。
4. **`execution_count` 的语义要定清楚**。"被检索命中"和"被实际执行"是两回事，建议分别记录（前者 `execution_count`，后者新增 `run_count`），避免语义混淆。
5. **改动要分批验证**。第一期 6 项都是低风险改动，建议一项一 commit，每项跑 phase2/3/4/5 回归。第二期涉及门禁口径变更，需要先拿历史需求做分布分析。

### 8.5 一期实施结果与阈值标定（2026-09-11 已落地）

**① 阈值标定：业界 0.75 在本系统会过滤掉 100% 结果（实证）**

用与生产**完全一致**的 query 构造（`" / ".join(modules) + " " + fp_name`）实测（bge-large-zh-v1.5 / COSINE / 真实 Milvus）：

| 情形 | 分布 | 中位 |
|---|---|---|
| S 信号（本产品内检索） | 0.545 – 0.588 | 0.570 |
| N 无关（同 query 检索另一产品） | 0.359 – 0.458 | 0.406 |

阈值敏感性：**0.50 → 保留信号 100%、误放无关 0%**（0.45 会误放 20% 无关；0.60 则信号全丢）。故取 `FEW_SHOT_MIN_SIMILARITY = 0.50`、`PATTERN_MIN_SIMILARITY = 0.45`（模式为通用骨架、全局共享无产品归属问题，宽松一档）。

> ⚠️ **标定教训（重要）**：**必须用生产真实 query 构造标定**。本轮先用 `requirement.title` 当 query 测，得出信号区间 0.485~0.531、噪声 0.280~0.402，据此把阈值定为 0.45——**口径错了**。生产 query 含模块名与功能点名，信息量更大，相似度整体上移约 **0.10**，阈值需相应提高。这也解释了为什么"用标题测出的阈值"在真实链路上完全不生效（实测 15 个候选全部过阈值）。标定工具已固化为 `scripts/calibrate_retrieval_threshold.py`，可复现。

**② 一个被证伪的方案假设：`search_similar_cases` 的 `modules` 参数对用例不可用**

§7 复用关系表称"检索结果打分 + 模块过滤"可直接复用。实测：**`test_cases` 的向量 metadata 从未写入 `modules` 字段**（`add_test_case` 只写 `req_id` / `product_id` / `case_type` / `confidence` / `gen_batch_id`，实测 metadata_keys 已核），故传 `modules` 会被 `search_similar_cases` 的内存过滤**清成 0 条**。

| KB 答案主要依据 **AI 生成的测试用例** 而非需求文档 | B2 答案自述「需求文档中并未直接说明上限为 50…是通过测试用例推断得出的」；B3 注明「信息来源于知识库中的测试用例文档」 |
| 三问的 requirement 来源**恒为 V1.0 旧需求** | `blog_qa_v11.json` 三问 `source_ids_sample` 首项均为 `REQ-1788244895551-8397`（V1.0），其后 3 条全是 `TC-编辑器-*` |
| **V1.1 需求完全缺席** | 检索实测：以「手动标记版本最多保留多少个？」「素材库个人总量配额是多少？」检索，V1.1 `REQ-1788322894962-6696` **均未进 top-10** |

### 9.2 根因链（四条环环相扣，非单一"权威倒挂"）

```
① Milvus 堆积孤儿向量（删除的需求未清理）
        ↓ 占满 top-K 名额
② 孤儿过滤后真实文档所剩无几（代码中 _build_qa_prompt 的孤儿过滤是「后过滤」）
        ↓ 池中只剩 V1.0 需求 + 测试用例
③ V1.1 无 go_live_date → prompt 的「以上线日期靠后为准」规则对它不生效
        ↓ 既进不了 top-K，进了也赢不了
④ prompt 无「按来源类型的权威规则」→ LLM 把测试用例与需求文档等权采信
        ↓
   答案依据 AI 生成用例 = 循环权威
```

**逐条证据**：

| 环 | 证据 |
|---|---|
| ① 孤儿向量 | 以产品过滤检索 10 条，**9 条的 REQ ID 在 `requirements` 表（共 34 条）中不存在**，也不是功能点 ID |
| ② 后过滤 | `api/knowledge_qa.py:116`「用 enriched_sources 的 id 集合过滤 kb_results，去除孤儿向量」——**先召回后过滤**，名额已被占掉 |
| ③ go_live_date 缺失 | V1.1 `REQ-1788322894962-6696`：`vectorization_status=completed` 但 **`go_live_date=None`**；V1.0 为 `2026-09-01`。prompt 第 4 条「多个版本同时出现时，以上线日期靠后的最新版本为准」**对无上线日期的 V1.1 无效** |
| ④ 无类型权威 | `_build_qa_prompt`（:146-166）只给了 4 条规则：安全隔离 / 仅用文档 / 不编造 ID / **多版本取最新**。**没有任何一条规定「需求文档优先于测试用例」** |

> ⚠️ **这修正了对 N1 的原有理解**：主因不是"模型偏爱用例"，而是
> **召回池被孤儿向量挤压 + 最新版本根本没有可比对的日期字段**。
> 只加"权威提示词"而不解决 ①②③，等于在垃圾池上做排序。

### 9.3 治理目标（可验收）

1. **最新版需求必须能被召回**：V1.1 类需求在版本相关问答中进入 top-8
2. **权威层级可执行**：答案若引用测试用例推断业务规则，必须显式标注「推断自用例，需求文档未明确」
3. **孤儿向量不占名额**：召回阶段即排除，而非后过滤
4. **可追溯**：每个答案的关键结论可指到「权威层级 + 来源 ID + 版本」

**明确不做**：不删除历史版本的向量（版本演进对比需要）；不禁止引用测试用例
（用例在"边界行为/历史口径"上有价值）——目标是**分层与标注**，不是一刀切剔除。

### 9.4 设计方案 B6：知识权威分级（分四层落地）

#### B6-1 权威层级定义（对齐 B1 的 `source` 权重，向上扩展到文档类型）

| 层级 | 来源类型 | 说明 | 检索权重 |
|---|---|---|---|
| **L0** | 需求文档（requirement，已确认/已归档） | 业务规则的唯一权威 | 1.0 |
| **L1** | 功能点 SRR / CRSR（functional_point） | 需求的结构化分解，次权威 | 0.9 |
| **L2** | 人工核准用例（`source=human_approved` / `reused`） | 可作**行为**佐证，不作**规则**依据 | 0.6 |
| **L3** | AI 生成用例（`source=ai_generated`） | 仅作参考，**不得**作为业务规则依据 | 0.4 |

> 与 B1 的关系：B1 定义了用例**内部**的 `source` 权重；B6 把它**向上扩展**到
> 需求/FP/用例**之间**的类型权威。二者共用一套权重常量，避免各写一份。

#### B6-2 召回层：孤儿向量前置清除（P0，成本最低、收益最直接）

现状是「先召回 top-K 再按 PG 存在性过滤」。改为**两级**：

1. **入库侧即删**：需求/FP/用例删除时同步删向量（现在只删 PG，Milvus 留残）
   —— 需先核对现有删除路径是否漏了向量清理
2. **定期 GC**：新增清扫任务，扫描 Milvus 全部 `id`，与 PG 对账，删掉不存在的
   （实测孤儿占比高，本次 11 条里 9 条）
3. **检索侧兜底**：`search_similar_requirements` 等检索方法支持传入 `valid_ids`，
   或在扩大召回（`top_k × 3`）后再过滤并截断回 `top_k`

> 建议**先做 2（GC）**，因为它对存量孤儿立即生效，且不改检索语义、风险最低。

#### B6-3 排序层：版本新鲜度可比较（P0）

1. **补齐 `go_live_date`**：归档流程应对该版本下所有需求写入 `go_live_date`
   （V1.1 现为 `None`，需查明是归档未覆盖还是该需求未参与归档）
2. **缺失兜底**：`go_live_date` 为空时，用 `archived_at → updated_at → created_at` 依次兜底，
   **不允许出现"无日期"导致无法比较**
3. **新鲜度加权**：最终分 = `similarity × 类型权重 × 新鲜度系数`，
   新鲜度系数按版本日期做温和加权（如近一版 1.0、上上一版 0.95），
   **不搞硬性置顶**，避免弱相关的新文档挤掉强相关的旧文档

#### B6-4 Prompt 层：权威规则显式化（P1，约 20 行）

在 `_build_qa_prompt` 的规则列表中补两条（放在第 4 条"多版本取最新"之后）：

```
5) 资料按权威层级采信：需求文档 > 功能点说明 > 测试用例。
   测试用例可用于说明「系统实际做了什么」，但**不能**作为「规则应当是什么」的依据。
6) 若某条规则只在测试用例中出现、需求文档未明确，必须显式说明
   「该值推断自测试用例，需求文档未直接说明」，不得陈述为确定结论。
```

> 这一条直接对应 B2 答案的问题——**模型其实已经知道自己在推断**（它写明了"是通过测试用例
> 推断得出的"），缺的是**统一的、强制的表达规范**，让下游与用户能识别推断。

#### B6-5 可追溯：答案标注权威层级（P2）

`reference_sources` 每条目增加 `authority_level`（L0/L1/L2/L3）与 `go_live_date`，
前端 KB 问答页按层级着色。使"这条答案的规则依据够不够硬"一眼可见。

### 9.7 风险与注意事项

1. **孤儿 GC 要可回滚**：先 dry-run 输出待删 ID 清单，人工确认后再执行；
   且**只删在 PG 中确认不存在的**，不做模糊匹配
2. **新鲜度加权不能盖过相关性**：采用温和系数而非硬置顶，避免"新但无关"的文档霸占上下文
3. **`go_live_date` 补齐要区分语义**：它表示"上线时间"，归档时写入；
   未归档需求的兜底值**不得写回该字段**，只在排序时临时计算，避免污染语义
4. **与 N3/N4 无耦合**：本节改动集中在 KB 检索与问答路径，不涉及澄清去重与任务调度

### 9.9 ⚠️ 2026-09-14 二次分析：**根因修正**（§9.2 的环①③判断有误）

本节用**生产同款检索链路**复核 §9.2 的四条根因，结论：**①③ 判断错误，真正的头两条根因当时没找到。**

#### 复核方法与关键数据

按生产实际调用方式检索（`knowledge_qa.py:488`）：

```python
hybrid_searcher.search_requirements(query=question, product_id=product_id,
                                    modules=modules, top_k=5,
                                    status="archived", session=session)   # ← 硬过滤
```

| 检验 | 结果 |
|---|---|
| `status='archived'`（**生产用法**） | 5 条：`V1.0` + 4 条 FP 向量，**无 V1.1** |
| `status=None`（不过滤） | top-5 **全是孤儿 ID** → 说明孤儿**只在不过滤时**才占位 |
| `req_id == V1.1` / `requirement_id == V1.1` / `id == V1.1` | **三种键均 0 条** → **V1.1 根本没有向量** |
| `req_id == V1.0` | 1 条（V1.0 向量存在） |
| requirement 型向量的 status 分布 | `archived 11 / draft 86` |
| PG `requirements` status 分布 | `draft 16 / archived 12 / confirmed 5 / pending_review 1` |

#### 修正后的根因（按证据强度排序）

**① V1.1 压根没有向量【新增，主因】**
PG 里 `REQ-1788322894962-6696.vectorization_status = 'completed'`，
但 Milvus 中按 `req_id` / `requirement_id` / `id` 三种键查询**全部为 0 条**。
→ 最新版需求在设计上就**无法被召回**，与相似度、排序、日期都无关。
→ **顺带暴露一个独立缺陷**：`vectorization_status` 字段与实际向量状态**不一致**（谎报 completed）。
> 注：向量为何缺失（被删未重建 / 重建失败但状态未回滚）**尚未定位**，本次只确认"不存在"这一事实。

**② 功能点（L1）向量被误标为 requirement 后被当孤儿静默丢弃【新增，主因】**
- `knowledge_qa.py:493`：对 `search_requirements` 的**全部**结果无条件 `r["type"] = "requirement"`
- `_enrich_sources`：只按 **`requirements` 表**校验存在性，`not found and type == "requirement"` → `continue`（丢弃）
- 而功能点向量主键是 `"FP-" + functional_points.id`，在 `requirements` 表里当然查不到
→ **整个 L1 权威层在 KB 问答中被静默丢弃**。

实测证据：B1 检索中 `FP-REQ-1788251057736-1226` 的相似度 **0.6064 高于 V1.0 的 0.5712**
（是最高分文档），却在最终 `reference_sources` 中消失；最终 `types` 只剩
`['requirement', 'test_case']`，**从未出现 `functional_point`**。

**③ 需求检索硬过滤 `status="archived"`【新增，设计层面】**
V1.1 是 `confirmed` → **即便有向量也会被排除**。这是"只信已归档需求"的设计决策，
但与「B 时点应采纳最新版本」的目标直接冲突：**最新版本恰恰最可能尚未归档**。

**④ 孤儿向量【修正：§9.2 环① 判断过重】**
实测 87 条孤儿中 **86 条是 `draft` 状态**，而生产检索硬过滤 `status='archived'`
→ **它们进不了生产检索窗口**。上一轮用 `vector_store.search_similar_requirements`
（未带 status 过滤）测出"9/11 是孤儿"，**属于用了非生产口径**，结论被放大。
→ 孤儿向量仍是**卫生问题**（应清理），但**不是 N1 的成因**。

**⑤ `go_live_date` 缺失【修正：§9.2 环③ 判断过重】**
V1.1 `go_live_date=None` 属实，但前提是 V1.1 能被召回——而它**连向量都没有**。
→ 该字段是**潜在**问题（B6-3 的兜底仍有价值），但**不是当前成因**。

#### 修正后的因果链

```
① V1.1 无向量                      ┐
② FP（L1）被误标后当孤儿丢弃        ├─→ KB 上下文只剩 1 条旧需求(V1.0) + 5 条用例
③ status="archived" 排除未归档最新版 ┘        ↓
                                    答案只能依据 AI 生成的用例
                                            ↓
                                    表现为「循环权威」（N1 的表象）
```

**结论**：N1 的表象是"权威倒挂"，**实质是"上下文供给不足"**——
可用的权威文档被三种机制各自砍掉一部分，最后只剩用例可依。
因此治理的**优先级应当调整**：先修 ①②③（让权威文档能被召回），
再谈权威分层与提示词（B6-1/B6-4/B6-5 已落地，属于"标注"而非"补供"）。

#### 对 B6 方案的修订建议

| 项 | 原优先级 | 修订后 | 理由 |
|---|---|---|---|
| 修 `vectorization_status` 与实际不一致 + V1.1 向量缺失 | 未列入 | **P0（新增）** | 向量不存在，后面全部治理都是空谈 |
| 修 FP 被误标/误丢（`knowledge_qa.py:493` + `_enrich_sources`） | 未列入 | **P0（新增）** | 一行类型覆盖导致整层 L1 失效 |
| `status="archived"` 过滤策略 | 未列入 | **P0（新增）** | 最新版本天然未归档，与"采纳最新"目标冲突 |
| B6-2 孤儿向量 GC | P0 | **P2（降级）** | 卫生问题，非成因 |
| B6-3 新鲜度兜底 | P0 | P1（保留） | 潜在问题，待 ①②③ 修完才需要 |
| B6-1 / B6-4 / B6-5 权威分层 | P1/P2 | P1（已落地） | 价值在"标注不确定性"，非"补供给" |

### 9.20 知识库维护周期任务：N5-c 根治（2026-09-14）

#### 为什么做这一项

N5 追查确认了三个机制缺陷，其中 **N5-c（无「PG 状态 vs Milvus 实际」对账机制）**
是"这类不一致能潜伏至今"的**根本原因**：

```
N5-a 归档派发 Celery 向量化任务后无终态保证（有需求长期停留 pending）
N5-b KB 纠错「删旧向量 → 重新嵌入」非原子，中断则永久丢向量且状态不回滚
N5-c 无对账机制 → 上述不一致无法被自动发现   ← 本次解决
```

`kb_vector_reconcile` 已提供修复能力，但**之前只能手动跑**。
本次把它变成周期任务，使系统**自愈**，而不是等人发现。

#### 实现

| 文件 | 内容 |
|---|---|
| `app/core/kb_vector_reconcile.py` | **核心逻辑**（从脚本抽出）：`reconcile_requirements()` + `scan_orphan_vectors()` |
| `app/core/kb_maintenance.py` | 周期循环 `_maintenance_loop()` + `start/stop_kb_maintenance()` |

| `app/config.py` | `KB_MAINTENANCE_ENABLED=True` / `KB_MAINTENANCE_INTERVAL=3600` |
| `scripts/kb_vector_reconcile.py`、`scripts/kb_orphan_gc.py` | 改为**薄 CLI 封装**，共用同一套核心逻辑 |

**为什么抽到 `app/core`**：同一套逻辑有两个消费方（周期任务 + CLI），
放一起避免**两份实现漂移**——尤其孤儿判定这种"判错就误删"的逻辑，绝不能有两份。

#### 做什么 / 不做什么（安全边界）

- ✅ **自动修复**：补写缺失向量、修正"卡住"的状态（**只新增/改状态，不删任何数据**）
- ✅ **只报告孤儿**：扫描结果写日志（含样例与占比），**不自动删除**

### 9.24 二期 10/11 落地：`weight` 计算、排序接入、反馈闭环（2026-09-15）

#### ⚠️ 实现前实测：公式的 4 个输入里 **2 个是近似常量**

| 输入 | 实测（1704 条用例） |
|---|---|
| `feedback.accepted` | **None 1287 / true 416 / false 1** |
| `confidence`（质量分） | 分布良好：1.0(440) / 0.9(549) / 0.8(150) / 0.7(436) / 0.6(127) |
| `execution_count` | **>0 的仅 5 条** |
| `last_pass_rate` | **>0 的 0 条**（从未写入——无执行结果回流） |
| `weight` 现值 | **全部 1.0**（默认值，从未重算过） |

按公式计算：**min 0.225 / max 0.822 / mean 0.528 / std 仅 0.058**，
分布 `{0.2:1, 0.4:152, 0.5:1133, 0.6:410, 0.7:6, 0.8:2}` ——
**66% 挤在 0.5 桶，区分度甚至低于 `confidence` 单独使用**。

→ 若直接算 `0.6×sim + 0.3×weight`，weight 项只会给排序带来**噪声级扰动**，
同时把相似度权重稀释到 0.6。**这正是设计文档警告的"改完等于没改"。**

#### 解法：候选集内归一化 + **方差守卫**

```python
w_norm = (w - min) / (max - min)   # 仅当 max-min >= MIN_WEIGHT_SPREAD(0.10)
       = 0.5                        # 否则视为无有效差异，不影响排序
rank   = 0.6 × sim + 0.3 × w_norm + 0.1 × recency
```

**为什么必须有方差守卫**（这是实现中发现的坑）：
min-max 是**线性拉伸**，拉伸倍数 = 1/极差。候选集常常是**同质的**
（同一需求的用例置信度相近），此时极差可能只有 0.02，
归一化会把 0.01 的噪声差异放大 **50 倍**成满量程 → **噪声主导排序**。

- 实测全局极差 0.597 → 拉伸仅 1.68×，可接受
- 但同质候选集极差可能 <0.05 → **必须抑制**

`MIN_WEIGHT_SPREAD = 0.10` 的取值依据：公式中人工反馈翻转（最明确信号）带来 0.35 差异，
置信度跨一档（0.6→1.0）带来 0.10 差异 —— 即 0.10 ≈ "一个可辨识的信号档"。

**验证**：

```
同质集(极差0.02) → [0.5, 0.5, 0.5]   ✅ 抑制
同质集(极差0.05) → [0.5, 0.5, 0.5]   ✅ 抑制
有差异(极差0.30) → [0.0, 1.0, 1.0]   ✅ 生效
同质集下 rank(sim=0.9)=0.74 > rank(sim=0.8)=0.68  ✅ 顺序仍由相似度决定
```

#### 另一处修正：使用频率归一化改用**固定饱和基准**

原设计未明确分母。若用"批次内最大值"，会导致**同一条用例的 weight 随别人变化而变化**
（单条重算与批量重算结果不一致，权重不可比较）。
改为固定基准 `USAGE_SATURATION = 50`（命中 50 次即视为充分使用），
使 weight 成为**用例自身的属性**，任何时刻算都相同。

> ⚠️ 50 是**初始标定**——实测目前 `execution_count>0` 仅 5 条（最高个位数），
> 尚无分布可依。待使用量积累后应按 §8.5 的方法（取分布分位数）重新标定。
