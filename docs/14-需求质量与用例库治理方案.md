# 14 — 需求质量与用例库治理方案

> 编制日期：2026-09-11 ｜ 代码基线：`backend/app/VERSION` = 3.2.14
> 关联文档：`docs/13-case-generation-logic.md`（链路快照）、`docs/01-requirement-parsing.md`、`docs/02-knowledge-base.md`
> 业界参照：Meta TestGen-LLM（Assured LLMSE）、工商银行测试资产知识库、天猫 AI 用例生成、百度 RAG + 用例库实践

---

## 0. 为什么是这两个方向

用例质量的上限由两个变量决定：

```
最终用例质量 ≈ f(需求输入质量, 知识复用质量)
```

- **需求输入质量**：需求本身缺失的信息，任何生成能力都补不回来。天猫的实测结论很直白——C 端业务采纳率 85%，B 端（资金/供应链）不到 40%，**根因是 PRD 质量而非模型能力**。
- **知识复用质量**：系统已有历史用例沉淀，但"取出来用"的链路质量决定了复用价值。工行做到 59% 资产复用率，靠的是"标签过滤 + 混合召回 + reranker + 阈值"这套检索治理，不是靠模型更强。

两个方向都指向同一件事：**把不确定的 LLM 判断，换成可验证的规则信号**。

## 1. 现状诊断

### 1.2 方向 B：用例库沉淀与使用

**沉淀侧**（`agents/review_agent.py:602-870` `persist_to_kb()`）：

| 条件 | 落库状态 |
|---|---|
| `confidence ≥ 0.70` 且非 blocker | `approved`（自动，无人工） |
| `0.60 ~ 0.70` | `reviewed` |
| `< 0.60` 或 blocker | `draft` + `error_cases` |

沉淀本身是通的（含标题级去重、savepoint 隔离、向量双写）。问题在于**准入只看生成时的 confidence**——这个分数是生成期自评 + 规则聚合，没有实战验证。

**使用侧**，三条通道各有问题：

| 通道 | 实现位置 | 问题 |
|---|---|---|
| Few-shot 参考 | `agents/gen_agent.py:115-152` | **不是语义检索**：先取该产品最近更新的 10 条 approved，再在其中按模块过滤取前 3。候选池被锁死在"最近 10 条"，用例攒多后大概率召回为空 |
| 回归基线 RTS | `core/fp_cases.py:75-95` `aggregate_latest_cases()` | 口径清晰（受影响 FP 按 `go_live_date` 最大项目取 approved），可用 |
| 模式参考 | `agents/gen_agent.py:156-190` + `db/milvus_store.py:841-850` | 只有 8 条固定种子；检索**无相似度阈值**，必返 3 条；`usage_count` / `success_rate` 零更新；无增删改接口 |

**反馈侧——完全空缺**。`db/models.py` 的 `TestCase` 表已有三个为本用途预留的字段，但全项目零引用：

```python
execution_count: Mapped[int]      # 零引用
last_pass_rate: Mapped[float]     # 零引用
weight: Mapped[float] = 1.0       # 零引用
```

这三个字段对应的正是业界闭环的核心——工行的"14 维度质量评分 + 低质量自动建议改进"、百度总结的"执行结果回流标记正负样本"、TestGen-LLM 的 `Improve` 过滤器。**字段已经建好，缺的只是把它接上。**

## 2. 方向 A：需求质量提升方案

### A1. 修正质量评分口径（P0，约 30 行）

> ⚠️ **2026-09-11 复核：本节的"问题"判断不成立，须重写目标。** 真实情况是规则公式**已经在生效**、LLM 自评是死代码。照本节原描述改将产生**零行为变化**。修正后的目标见 **§8.1 第 3 项**：改为「重设规则公式权重 + 决策是否接回 LLM 自评」。

**问题**：`_calc_quality_score()` 让 LLM 自评成为主口径。

**改法**：反转为"规则为主、LLM 为辅"。

```
新公式（建议）：
overall = structure_score × 0.35      # 结构完整度（规则，见 A2）
        + rule_completeness × 0.25    # 完整性检测（规则）
        + ambiguity_score × 0.15      # 歧义检测（规则，反向计分）
        + llm_self_score × 0.15       # LLM 自评（降权为参考）
        + clarification_score × 0.10  # 澄清收敛度（规则）
```

同时修正 `eval_answer_coverage()` 的硬编码返回：`1.0/0.8` 改为按"已回答且被判定覆盖的问题占比"计算。

**收益**：门禁的"质量评分"Blocker 从"模型自评"变成"可由人复核的规则分"，可解释、可复现。

### A2. 新增结构完整度评分（P0，约 80 行）

这是需求质量方案的核心——把"需求有没有写全"变成可量化的分。

**评估维度**（按 SRR 字段，分必填/建议两档）：

| 档位 | 字段 | 权重 |
|---|---|---|
| 必填 | `requirement.title` / `requirement.summary` / `flows.happy_path.steps` | 各 10% |
| 必填 | `flows.alternate_flows`（异常分支） | 10% |
| 必填 | `business_rules`（至少 1 条） | 10% |
| 建议 | `data_constraints`（有输入字段时） | 10% |
| 建议 | `preconditions` | 5% |
| 建议 | `non_functional`（至少一类：性能/安全/兼容/可访问） | 10% |
| 建议 | `acceptance_criteria` / 验收语义规则 | 10% |
| 建议 | `api_definitions`（涉及接口时） | 10% |
| 建议 | `user_roles`（涉及权限时） | 5% |
| 建议 | `dependencies` / `ui_rules` / `data_model` | 各 3.3% |

**实现要点**：
- 新增 `utils/requirement_quality.py`，函数 `calc_structure_score(srr) -> dict`
- 返回 `{score, filled: [...], missing: [...], applicable: {...}}`，`missing` 直接用于澄清（见 A3）
- "适用性判断"很关键：不涉及接口的需求不该因缺 `api_definitions` 扣分。用简单规则（如存在 `optimization_context` 或 `change_type=optimized` 时才要求 `api_definitions`）

> ⚠️ **2026-09-11 复核：上表有 3 个字段在顶层 SRR 根本不存在，占 30% 权重会恒判缺失。**
> `agents/req_agent.py:472-474` 已把 `business_rules` / `data_constraints` / `acceptance_criteria` 从顶层 `srr.pop()` 掉（v2.40 迁移：`business_rules`→`cross_fp_interactions.shared_business_rules`；`data_constraints`/`acceptance_criteria`→`assumptions`），它们**只存在于 FP 子 SRR**。
> 因此签名应改为 `calc_structure_score(total_srr, fp_srrs: list) -> dict`：总 SRR 评结构性字段、FP 子 SRR 评业务规则类字段。顶层实测字段清单与逐项可用性见 **§8.2 缺陷 1、2**。

**收益**：产出可展示的"需求完整度报告"，并让门禁有据可依。

### A3. 澄清从"问题驱动"改为"缺口驱动"（P1）

**现状**：ClarifyAgent 生成问题（LLM + KB 检索辅助），收敛靠 LLM 判定答案是否覆盖问题。

**改法**：A2 的 `structure_score.missing` 直接作为澄清问题的种子来源，与 LLM 生成的问题合并：

```
澄清问题池 = structure_gaps（规则，优先）
           ∪ llm_questions（LLM 生成，补充）
           ∪ kb_gaps（KB 比对发现的缺失维度）
```

优先级：结构缺口 > KB 缺口 > LLM 自由生成。这样澄清有明确的"补全目标"，而不是等 LLM 发挥。

**收益**：澄清轮次收敛更快、更可预期；结构缺口是确定性的，不受 LLM 波动影响。

### A4. 门禁纳入结构完整度（P1）

在 `core/quality_gate.py` 的检查项中新增：

| 类型 | 条件 | 建议阈值 |
|---|---|---|
| Blocker | `structure_score < 0.35` 且非冷启动 | 需求过于简略，强制打回 |
| Warning | `structure_score < 0.60` | 提示"建议补充 X / Y / Z" |
| Warning | 冷启动模式 | 保留现有提示，但附带结构缺口清单 |

注意：**门槛要保守**。结构分低不等于需求不能用，Blocker 阈值定得过严会重演冷启动死锁（v3.5 的教训）。建议先用 Warning 跑一段时间，观察分布后再决定是否升级为 Blocker。

### A5. 需求质量报表（P2）

在需求详情页展示：
- 结构完整度分 + 缺口清单（可点击跳转到对应编辑入口）
- 质量分构成拆解（结构/完整性/歧义/LLM 自评/澄清度 各占多少）
- 澄清轮次与收敛原因

作用：让"需求写得好不好"对用户可见——**没有度量就没有改进动力**（这也是 `docs/13 §4.4` 的同类问题）。

## 3. 方向 B：用例库沉淀与使用方案

### B1. 沉淀标准：分级准入 + 来源标记

**保留现有三级**（approved / reviewed / draft），但做两处增强：

**① 增加"核准来源"标记**

现在 `confidence ≥ 0.70` 直接自动 approved，没有人工环节。v3.5 把阈值从 0.85 降到 0.70 是为了解决冷启动死循环（合理），但代价是 approved 里混着"未经人看的自动核准"。

建议：保留自动 approved，但用 `source` 字段区分（现已有 `ai_generated` / `reused`，扩展为）：

> ⚠️ **2026-09-11 复核更正**：`reused` **未落到 DB 列**。DB 列 `TestCase.source`（`db/models.py:106`）实际只写 `ai_generated`（`agents/review_agent.py:727/748/768`）与 `manual`（`api/testcases.py:303`）；`reused` 只存在于 `case_json.source`（`core/orchestrator.py:851`）。本节分级方案依赖 DB 列，**需先补齐 `reused` 的列写入**。详见 **§8.2 缺陷 3**。

| `source` | 含义 | 检索权重 |
|---|---|---|
| `human_approved` | 人工复核通过 | 1.0 |
| `ai_approved` | confidence ≥ 0.70 自动核准 | 0.7 |
| `reused` | 回归复用基线 | 1.0（本身已是历史基线） |
| `imported` | 外部导入 | 按导入时标注 |

**② 补充结构完整性校验**

落库前校验 UTCF 必填字段（`title` / `steps` / `assertions` / `related_fp` / `notes` 要点标注）齐备。缺字段的降级到 `reviewed`，不直接 approved。

### B2. 使用规则：三条通道统一"阈值 + 限量 + 可追溯"

**统一原则**（对应工行的检索治理）：

1. 任何注入 prompt 的知识都必须过**相似度阈值**
2. 必须有**数量上限**
3. 必须**可追溯**（记录注入了哪些知识源，便于事后归因）

| 通道 | 取数规则（建议） | 数量 | 阈值 | 改造位置 |
|---|---|---|---|---|
| **Few-shot 参考** | 向量语义检索（`search_similar_cases`，按 `product_id` 过滤）+ 模块/类型二次筛选 | 3–5 | cos ≥ 0.75 | `agents/gen_agent.py:115-152` |
| **回归基线 RTS** | 保持不变（受影响 FP 的 `go_live_date` 最新版 approved，全量复用） | 全量 | 不设（本身即基线） | `core/fp_cases.py` |
| **模式参考** | 向量检索 + score 过滤 | ≤ 3 | cos ≥ 0.75 | `db/milvus_store.py:841` + `gen_agent.py:156` |

**Few-shot 改造是最高优先级**——系统里 `vector_store.search_similar_cases(query, top_k, product_id)` 已经存在（ReviewAgent 用它算 `match_score`），GenAgent 却走了一个 `order_by(updated_at.desc()).limit(10)` 的近似。改动量约 20 行，复用已有能力。

### B3. 反馈闭环：激活三个死字段（核心）

这是让用例库"越用越准"的机制，也是与业界差距最大的一环。

**字段激活方案**：

| 字段 | 何时更新 | 更新规则 |
|---|---|---|
| `execution_count` | 用例被检索命中并注入 prompt 时 | `+= 1`（记录"被使用过"） |
| `last_pass_rate` | 有执行结果回流时（CI/CD 对接或人工标记"此用例有效"） | 移动平均，如 `0.7×old + 0.3×new` |
| `weight` | 定期重算（见下） | 综合质量权重 |

**`weight` 计算建议**：

```
weight = 0.35 × 人工采纳率        # feedback.accepted 的比例
       + 0.25 × 质量分            # 6 维度 dimension_scores 的 completeness/coverage
       + 0.20 × 使用频率归一化      # execution_count 的 log 归一化
       + 0.20 × 通过率             # last_pass_rate（无数据时取中性值 0.5）
```

**闭环流程**：

```
生成 → 审核（人工/自动）→ 沉淀（approved，标记 source）
  → 检索使用（few-shot / RTS，execution_count += 1）
  → 人工反馈（api/testcases.py 的 /feedback：accepted/rejected）
  → 定期重算 weight
  → 影响下次检索排序（见 B4）
```

**检索排序接入**：

```
rank_score = 0.6 × semantic_similarity
           + 0.3 × weight
           + 0.1 × recency
```

这样"人工认可、用过且有效的用例"会排在前面，而不是"最近更新的"。

### B4. 用例治理：定期扫描与淘汰（P2）

对应工行的"14 维度质量评分 + 低质量自动建议改进"：

- **定期任务**（建议每周）：扫描 `weight < 0.3` 且 `execution_count = 0` 的 approved 用例 → 标记为"待复核"，降权处理
- **长期未命中**：`execution_count = 0` 且入库超过 N 个月 → 建议归档（写入 `archived_at`）
- **冲突检测**：语义相似度 > 0.9 的用例对 → 提示合并（现在是标题级去重，跨批次的语义重复仍会入库）

### B5. 用例库质量报表（P2）

在知识库管理页增加：
- approved / reviewed / draft 三级占比
- 复用率（被检索命中的用例数 / approved 总数）—— 对标工行的 59%
- weight 分布直方图
- Top-N 被复用最多的用例、Top-N 从未被复用的用例

## 6. 风险与注意事项

1. **阈值不要照搬**。业界用的 0.75 是在 bge-large-zh + reranker 的管线上调出来的。本项目用的嵌入模型不同，建议先用"不设阈值但记录 score 分布"，跑一批真实数据后再定阈值，而不是直接照抄。
2. **结构分先做 Warning 不做 Blocker**（见 A4）。冷启动死锁的教训（v3.5）说明：门槛定错会让流程卡死而不是变好。
3. **weight 需要冷启动数据**。初期人工反馈少，`weight` 会集中在中性值附近，排序效果有限。可以先用 `source` 分级（人工 approved 优先）作为过渡，等反馈积累够了再上 weight。
4. **`execution_count` 的语义要定清楚**。"被检索命中"和"被实际执行"是两回事，建议分别记录（前者 `execution_count`，后者新增 `run_count`），避免语义混淆。
5. **改动要分批验证**。第一期 6 项都是低风险改动，建议一项一 commit，每项跑 phase2/3/4/5 回归。第二期涉及门禁口径变更，需要先拿历史需求做分布分析。

## 8. 一期方案可行性核验（2026-09-11 代码复核）

> 复核方式：逐条对照 `backend/app` 真实代码，验证方案假设的「函数/字段/调用链」是否成立。结论分四档：✅ 可直接落地 ｜ ⚠️ 可落地但收益/成本与描述不符 ｜ ❌ 伪问题（照做等于白做）。

### 8.1 一期 6 项逐条结论

| # | 任务 | 结论 | 代码依据 |

### 8.2 必须修正的方案缺陷（影响二期）

**缺陷 1：A2 的字段清单有 3 个字段在顶层 SRR 根本不存在。**

`agents/req_agent.py:472-474` 明确把四个字段从顶层 SRR 中 `pop` 掉（v2.40 迁移）：

```python
_legacy_bc = srr.pop("boundary_conditions", None) or []
_legacy_dc = srr.pop("data_constraints", None) or []
_legacy_ac = srr.pop("acceptance_criteria", None) or []
_legacy_br = srr.pop("business_rules", None) or []
```

迁移去向：`business_rules` → `cross_fp_interactions.shared_business_rules`；`boundary_conditions` → `cross_fp_interactions.global_constraints`；`data_constraints` / `acceptance_criteria` → `assumptions`（带类型标注）。

而 A2 的维度表把 `business_rules`（10%）、`data_constraints`（10%）、`acceptance_criteria`（10%）列为评分项 —— **合计 30% 权重会恒判为"缺失"**，并因此产生虚假澄清缺口。

**修正**：`calc_structure_score(srr)` 必须**先明确评哪一层 SRR**。这三个字段只存在于 **FP 子 SRR**（`docs/13 §4.4` 已证：`business_rules`/`data_constraints` 仅从 FP 子 SRR 抽取）。建议签名改为 `calc_structure_score(total_srr, fp_srrs: list) -> dict`，总 SRR 评结构性字段、FP 子 SRR 评业务规则类字段。

**缺陷 2：顶层 SRR 实测字段清单（供 A2 校准）。**

取自真实产物 `backend/_e2e_tmp/artifacts/blog_v1_clarify.json`（`srr_keys_count=22`）：

```
srr_version / requirement / fp_summary / preconditions / flows / non_functional /
relationships / api_definitions / user_roles / dependencies / ui_rules / data_model /
assumptions / cross_fp_interactions / legacy_data_impact
```

对照 A2 维度表：`requirement.title` / `requirement.summary` / `flows.happy_path.steps` / `flows.alternate_flows` / `preconditions` / `non_functional` / `api_definitions` / `user_roles` / `dependencies` / `ui_rules` / `data_model` —— **均存在，可用**；仅上述 3 个字段需改口径。

**缺陷 3：B1 对 `source` 现状的描述不准确。**

方案称"现已有 `ai_generated` / `reused`"。实际 **DB 列** `TestCase.source`（`db/models.py:106`）写入值只有 `ai_generated`（`agents/review_agent.py:727/748/768`）与 `manual`（`api/testcases.py:303`）；`reused` **只存在于 `case_json.source`**（`core/orchestrator.py:851`），未落到 DB 列。B1 若要靠 `source` 做检索权重分级，**需先补齐 DB 列写入**。

### 8.3 二期前置条件（复核后新增）

| 前置项 | 原因 |
|---|---|
| 先修 A2 字段口径（缺陷 1） | 否则结构分 30% 权重恒缺失，澄清缺口驱动会问出一堆伪问题 |
| 先定 `calc_structure_score` 的 SRR 层级 | 决定 A3 澄清缺口来源是总 SRR 还是 FP 子 SRR |
| 先补 `TestCase.source` DB 列写入（缺陷 3） | B1 的 `human_approved`/`ai_approved` 分级依赖它 |
| 先决策质量分是否真正进门禁 | 当前 `quality_report` 在**生成链路**确实进 `QualityGate` Blocker（`core/orchestrator.py:579` → `quality_gate.py:188-193`），但在**需求分析链路**只做 0.4 温和警告（`requirement_tasks.py:1179/1537/1857`）——两条链路口径不一致，需统一后再谈"门禁可信度" |

### 8.4 复核结论一句话

**一期方案整体真实可用，第 1/2/5 项可立即动手；但方案对 A1 的根因判断（"门禁建立在 LLM 自评分上"）与代码事实相反——规则公式才是实际口径、LLM 自评是死代码，第 3 项必须重写目标，否则会做出一个"改完等于没改"的提交。**
