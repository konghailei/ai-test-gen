## 1. 根因实证

### 1.1 DEF-2：`:fp_id::text` 语法地雷（已容器内复现）

**代码位置**：`backend/app/api/requirements.py:4103-4121`（fp_delete 的级联清理 SQL），关键行 4119：
```sql
jsonb_build_array(jsonb_build_object('fp_id', :fp_id::text))
```

**复现实验**（容器内，ai-test-gen-api，2026-10-10）：

| 实验 | 结果 |
|---|---|
| psql `PREPARE` + `$1::text`（纯 PG 参数化） | ✅ 正常 |
| asyncpg 原生 `conn.execute(SQL, "FP-TEST")` + `$1::text` | ✅ `UPDATE 0` 正常 |
| SQLAlchemy `text()` + `:fp_id::text`（与线上代码同构） | ❌ `PostgresSyntaxError: syntax error at or near ":"` |
| SQLAlchemy `text()` + `CAST(:fp_id AS text)` | ✅ 正常 |
| SQLAlchemy `text()` + `:fp_id :: text`（空格分隔） | ✅ 正常 |
| SQLAlchemy `text()` + `jsonb_build_object('k', :x)`（无转型） | ❌ `IndeterminateDatatypeError`（asyncpg 无法推断参数类型） |

**官方依据**（SQLAlchemy 文档 `sqlelement.html`，`text()` 说明，联网核对）：
> "A name that is immediately followed by another colon, such as `:this:that` or `:value::int`, is currently not interpreted as a bound parameter and is rendered as literal text; whitespace may be used to separate the name from the colon, e.g. `:value ::int`."

即 `:fp_id::text` 被 SQLAlchemy 原样透传成字面 `:fp_id::text`，PG 解析到裸 `:` 报语法错误。**`::jsonb` 列转型本身无罪**（v3.1.3 P4 加的转型是对的），罪魁是第 4119 行那个绑定参数后紧跟的 `::text`。

**事务中毒链**（与 docs/24 描述吻合）：
1. cleanup_stmt 抛 `PostgresSyntaxError` → 被 4127 行 except 捕获（仅打日志，**未 rollback**）→ 事务进入 aborted 状态；
2. Traceability 清理（4143 行）在中毒事务上执行 → `InFailedSQLTransactionError` → 被 4149 行捕获；
3. FPDependency 查询（4154 行）→ 同样失败 → **未被捕获** → 500。

**全库扫描**：`:\w+::` 模式全代码库仅此 1 处（grep 实证），hybrid_search.py:185 已用正确的 `CAST(:module_filter AS VARCHAR)` 写法。

**列类型事实**：`requirements.srr_json` 为 `json`（information_schema 实证），这是 `::jsonb` 转型存在的原因（见 P2-C）。

### 1.2 DEF-1：强候选查询 OR 退化 + 模块名/ID 类型错配（双 bug）

**代码位置**：`backend/app/agents/req_agent.py:899-928`：
```python
where_clauses_strong = []
if product_id:
    where_clauses_strong.append(_ReqModel.product_id == product_id)   # ← bug①
if modules:
    where_clauses_strong.append(FunctionalPoint.module_id.in_(modules))  # ← bug②
    for _m in modules:
        where_clauses_strong.append(func.jsonb(FunctionalPoint.modules).op("@>")(func.jsonb(f'["{_m}"]')))
...
.where(_sa_or(*where_clauses_strong) if where_clauses_strong else False)  # ← OR！
```

**Bug ①（OR 退化）**：`product_id` 条件单独出现在 OR 列表里 → 只要产品相同，**产品下全部 FP 都成为"强匹配（module_hard）"候选**，与模块无关。docs/24 场景中三轮需求的 `requirements.modules` 均为 `[]`（DB 实证），OR 列表只剩产品条件 → 17 条历史 FP 全部命中强匹配。

**Bug ②（类型错配死子句）**：`FunctionalPoint.module_id.in_(modules)` 中 `modules` 是上传表单传入的**模块名称**（如"知识库"），而 `module_id` 列存的是 **MOD-565-xxx 形式的 ID**（DB 实证：FP.module_id=MOD-565-99322-690，modules JSON=["MOD-565-99322-690"]）。名称比对 ID 恒不命中；`@> ["模块名"]` 同理——**整个模块子句是死代码**。这也意味着：即使 OR 写对了，强匹配永远为空。

**误导链闭环**：强匹配 → 提示词（1026-1037 行）输出「以下功能点已存在数据库中——请勿重新生成」+「**硬性约束**：以上【强匹配】功能点名称，禁止重新生成内部 sub_srr」→ LLM 遵守指令把全部 FP 标 `reuse_existing: true` → 1071-1074 行过滤后 `new_fps=[]` → 4 个保存点（requirement_tasks.py:1228/1405/1867/2273，均 `if captured_fps:` 前置）全部跳过 → **需求 FP 恒为 0**。

**"弱匹配 0.68 形同虚设"的修正**：docs/24 把改名后仍 0 条归因于弱匹配阈值——实际强路径不看名称相似度，改名对抗无效。弱匹配是次要问题（子串捷径 `kw in name → 0.82` 在中文场景偏宽，如"知识库"⊂"知识库编译化功能"，另行收敛）。

**`/fp/reuse` 端点对照**（requirements.py:3975-4071）：手动复用要求源 FP `status == "archived"`、同产品、req 内查重，复制 name/fp_type/srr_json/atomicity_check/test_hints + 继承模块，新 FP `pending_review`。自动复用应复用同一套规则。

### 1.3 O-6：依赖图谱——结论修正 + 三个真问题

**docs/24 结论修正（实测）**：
- DB 现存 21 条边：v1.0 需求 5 条（803-807，01:40:15 由澄清重解析落库）、v2.0 需求 10 条（808-812 @02:14:15 + 813-817 @02:17:09）、v3.0 需求 5 条（818-822）；
- 端到端实测 `/api/requirements/{rid}/fp/dependencies`（ASGITransport + default_token）：**v1.0=5 / v2.0=10 / v3.0=5，全部 200**；
- docs/24 §3.4/§5.3 的"0 条"是**检查时机早于边落库**（v1.0 边 01:40:15 创建，检查发生在流程中途）。代码路径 `_run_clarify_reparse` → `_save_fp_dependencies`（requirement_tasks.py:1868）与 regenerate 路径（2274 行）均在登记依赖，"依赖未随拆分登记"不成立。

**真问题 ①：对偶边（4 组）**。v2.0 的两组边来源不同、方向相反：

| 02:14:15 LLM dependencies 数组 | 02:17:09 confirm 时 cross_fp_flows 补建 |
|---|---|
| 808 安全剥离 → 静态上传 | 813 静态上传 → 安全剥离 |
| 809 语义树解析 → 安全剥离 | 815 安全剥离 → 语义树解析 |
| 812 原型落库 → 语义树解析 | 816 语义树解析 → 原型落库 |
| 811 混合检测 → 静态上传 | 817 静态上传 → 混合检测 |

根因在 confirm 补建（requirements.py:2694-2711）：flow 的 `source_fp→target_fp` 是**数据/顺序流方向**（上游→下游），却默认映射成 `depends_on`（依赖方向：依赖方→被依赖方），语义颠倒。LLM 依赖数组方向是正确的（如"安全剥离 depends_on 静态上传"），flow 补建反向成对出现 → 图谱出现环，影响分析 BFS 互相到达、范围虚增。

**真问题 ②：跨需求边为 0**。`sf.requirement_id != tf.requirement_id` 查询 0 行——v2.0/v3.0 的 FP 不引用 v1.0 已归档 FP。而 `_save_fp_dependencies` 的跨需求解析层（v3.1.3，requirement_tasks.py:652-708）早已支持"归一化名匹配已归档 FP"，缺的只是 LLM 没被引导去引用历史基线。

**真问题 ③：验证时序**。依赖图谱检查应放在 confirm + FP 落库之后（与 docs/24 §2 的 11 步顺序一致，但 §3.4 实际检查提前了）。

### 1.4 O-7：跨版本聚合无输入（功能域漂移）

- DB 实证：三轮 21 个 FP 名称零重叠（v1.0 系统核心 11 个 / v2.0 原型解析 6 个 / v3.0 KB 编译 4 个）——本就是三个功能域，不是命名不规范；
- `functional_point_crsr` 表 17 行（v1.0 的 11 + v2.0 的 6），每行 `version_refs` 仅 1——`aggregate_crsr` 按 `(product_id, fp_name)` 精确同名聚合（fp_crsr.py:232-235），无输入是必然；
- Q5"命中但整理版内容为空"同源：CRSR 行 version_count=1，聚合从未发生。
- **与 DEF-1 的联动**：复用机制修复后（P1-A），新需求复用已归档同名 FP 会在新需求下产生同名 FP 副本 → CRSR 聚合自然获得跨版本输入。**复用与聚合是同一问题的两条路径**。

### 1.5 Q6：KB 固化时序 + 清基线副作用

时间线（DB 实证）：v1.0 项目归档 03:00:09 → CRSR 固化 03:00:14 → v2.0 归档 03:00:29 → CRSR 固化 03:00:30；`vector_outbox` 中 fp_crsr 37 条全部 done（relay 正常工作）。未命中的两个成分：
1. **异步窗口**：归档 → 固化（同步）→ 出箱 → relay（异步）→ Milvus 可检索，查询落在窗口内即 miss（含 Milvus reload 后 1-2 分钟 503 窗口，既有已知事实）；
2. **清基线副作用**：docs/24 §0 声明的"13 个旧测试产品全部清除"把 10-08 轮 Q6 曾命中的历史归档数据一并清掉——"回退"不纯是时序问题。docs/24 §5.3 只记了时序，漏了清理副作用。

### 1.6 O-1/O-2：数值保真无合同

- 注入机制存在且正确：gen_agent.py:641-672 把 `cross_fp_interactions.shared_business_rules` 注入 fp_section，并附"覆盖要求：若某条共享规则 applied_fps 涉及 ≥2 个 FP，应生成一个跨 FP 集成用例"；
- 缺口 ①：这是**弱要求**（"应生成一个集成用例"），没有"数值必须在用例断言中原值出现"的合同，LLM 可用间接表述绕过（docs/24 两轮实证：令牌 8h、锁定 30min、40 条封顶仅间接出现）；
- 缺口 ②：生成后**无命中率校验**——publication_policy 查覆盖缺口，不查数值命中；
- 缺口 ③：**无透出指标**——done 事件/result_json 没有 shared_value_coverage，数值丢失对用户不可见。
- O-2（FP 粒度致 SBR 分散）与 DEF-1 同源（FP 拆分路径不稳），保持观察，P0-B 后复验。

## 2. 修复方案

### 2.1 P0-A：DEF-2 修复（最小改动，立即可验）

**改动点 1（requirements.py:4119）**——`:fp_id::text` → `CAST(:fp_id AS text)`：
```sql
WHERE COALESCE((srr_json->'impact_analysis')::jsonb, '[]'::jsonb) @>
      jsonb_build_array(jsonb_build_object('fp_id', CAST(:fp_id AS text)))
```
其余 `::jsonb` 转型保留（列类型是 json，转型必要且已验证无害）。已实测 CAST 写法通过。

**改动点 2（requirements.py:4127-4131，except 分支加固）**——按"补丁必须检查 except 分支"纪律：
```python
except Exception as e:
    logger.warning("[FP-Delete] 级联清理失败: fp={} error={}", fp_id, str(e)[:200])
    await session.rollback()                      # 解除事务中毒
    fp = await session.get(FunctionalPoint, fp_id)     # rollback 后实例过期，重新加载
    req = await _load_active_requirement(req_id, session)
```
（async SQLAlchemy 下 rollback 会使 ORM 实例过期，属性访问抛 MissingGreenlet，必须重新 get。）

**验收标准**：
1. 构造双需求夹具：需求 A 含 FP X（挂模块），需求 B 的 srr_json.impact_analysis 引用 X 的 fp_id → `DELETE /requirements/A/fp/X` 返回 200；
2. B 的 srr_json.impact_analysis 中 X 条目被清除（跨需求级联生效）；
3. A 自身 impact_analysis、Traceability、fp_dependencies 关联行全部清理；
4. 重复删除返回 404；
5. **注入异常验证失败路径**：mock cleanup_stmt 抛错 → 接口仍能完成 FP 删除（rollback 生效，不 500）。

**回归设计**：新增 `test_phase7_fp_delete.py`（或并入既有 phase 序列），上述 5 断言；随后按纪律全量跑 phase2-6（改的是 requirements.py，属共享 API 层）。

### 2.2 P0-B：DEF-1 强候选查询修正

**改动点（req_agent.py:899-928 重写强候选查询）**：
```python
# 强匹配 = 同产品 AND 同模块（模块名 → 模块 ID 解析）AND 源已归档
# 产品条件单独不再构成强匹配（DEF-1 根因）
where_strong: list = []
if product_id:
    where_strong.append(_ReqModel.product_id == product_id)
    where_strong.append(_ReqModel.status == "archived")          # 对齐 /fp/reuse 的基线语义
    where_strong.append(FunctionalPoint.status == "archived")
if modules:
    # 模块名 → ID（与 _save_fps_to_db 的 name→id 解析对称，消除类型错配死子句）
    mod_rows = await s.execute(
        select(Module.id).where(
            Module.product_id == product_id,
            Module.name.in_([m.strip() for m in modules if m.strip()]),
        )
    )
    mod_ids = [r[0] for r in mod_rows.all()]
    if mod_ids:
        where_strong.append(_sa_or(
            FunctionalPoint.module_id.in_(mod_ids),
            *[_sa.func.jsonb(FunctionalPoint.modules).op("@>")(_sa.func.jsonb(f'["{_mid}"]'))
              for _mid in mod_ids],
        ))
q_strong = (...).where(_sa_and(*where_strong) if where_strong else False)
```
要点：
1. **OR → AND**：产品是过滤前提，模块是匹配条件，二者是交集不是并集；
2. **名称→ID 解析**：消掉死子句，与 `_save_fps_to_db`（requirement_tasks.py:345-374）的解析逻辑对称；
3. **archived 双重过滤**：与 `/fp/reuse` 的"源必须归档"语义对齐（复用 = 从基线拷贝；未归档需求不构成复用候选，避免把进行中的分析当基线）；
4. 弱匹配路径保留（LLM 判断语义），子串捷径收敛：`kw in name` 命中要求长度比 ≥0.6 且不再直接给 0.82 分（与相似度 0.68 同权），中文短词（≤3 字）子串不单独构成弱候选。

**提示词同步收敛（fp_agent.py FP_INTEGRATED_USER_PROMPT + req_agent.py:1026-1037）**：
- 「强匹配（同模块）」文案改为「同模块已归档基线功能点」；
- 硬性约束软化为：「仅当当前需求与该功能点**语义完全一致**（非版本迭代、非内容变化）才标记 reuse_existing=true；同功能的新版本迭代应正常新建功能点（其内容可能已变化）」——删除"禁止重新生成"的绝对表述；
- 新增一句引导跨版本依赖（服务 P1-B）：「若列出的已归档功能点与本需求功能点存在业务依赖，可在 dependencies 数组中以其名称建立跨需求依赖边」。

**验收标准（夹具按"对齐真实产物"纪律构造）**：
- F1（强匹配需真同模块）：产品 P 下归档需求 A（FP X 挂模块 M）；上传需求 B（同产品、表单 modules=模块 M 的**名称**、文档语义与 X 一致）→ 日志可见强候选仅 [X]（不再是产品全量）；
- F2（不吞新 FP）：同产品上传需求 C（不同模块、不同功能域）→ 强候选为空，FP 正常新建 ≥1；
- F3（docs/24 复现条件回归）：历史 FP 改名「冒烟-*」后 regenerate → 需求 FP 数 > 0（不变量断言，不断言 LLM 具体选择）；
- 现网自举场景复跑：v1.0 重复上传不再 0 FP。

**影响面**：req_agent.py 是所有需求分析路径的共享模块（upload/clarify/regenerate/refine）→ **必须全量回归 phase2-6 + 真实端到端验收**（回归全绿 ≠ 功能可用，docs/24 教训）。

### 2.3 P1-A：复用落库 + FP 空结果保护

**改动点 1：`_fp_extract_from_raw` 返回结构扩展**（req_agent.py:1071-1074）：

`_resolve_reused` 规则：
- 仅提示词清单内出现的名称有复用资格（LLM 不得复用未展示的名称，未在清单内的 reuse 标记按新建处理并告警）；
- 同名多候选（跨需求同名）：优先 archived + 需求版本号最大者；仍歧义 → 降级为新建并告警；
- 源 FP 状态非 archived → 降级为新建并告警（对齐 /fp/reuse）。

**改动点 2：新增 `_register_reused_fps(session, req_id, reused_fps, priority, product_id)`**（放 `app/core/requirement_tasks.py`，与 `_save_fps_to_db` 并列）：
- 逐条按 `/fp/reuse` 等价语义复制：`FunctionalPoint(id=新, requirement_id=req_id, module_id=src.module_id, modules=src.modules, name/fp_type/atomicity_check/test_hints 继承, priority=需求优先级, srr_json={**src.srr_json, "_reuse_source": {"fp_id": src.id, "req_id": src.requirement_id, "req_title": src_req.title, "archived_at": ...}}, status="pending_review")`；
- req 内同名查重：与新建 FP 撞名时**复用副本优先**，丢弃同名的 LLM 新建项并告警；
- 同时建追溯边：`FPDependency(source=新FP, target=源FP, relation_type="depends_on", description="跨版本复用基线（{源需求标题}）")`——新 FP 为 source ∈ 本需求，confirm 时既有自动审核机制会将其置 approved，天然参与影响分析（改基线 → 波及复用方），同时给 CRSR 聚合制造同名输入（O-7 联动）。

**改动点 3：4 个保存点同步**（全量 grep 调用方纪律）：

**改动点 4：FP 空结果保护（任务级，fail-closed 落终态）**：

**验收标准**：

### 2.8 P2-C：json → jsonb 列迁移（根治项）

**动机**：DEF-2 与 v3.1.3 P4 同源的土壤是 `requirements.srr_json`（及 functional_points.modules/srr_json 等）为 `json` 列。迁到 `jsonb` 后：所有 `::jsonb` 转型成为无害恒等操作、可建 GIN 索引、读取不再逐次重解析（PG 社区共识：除需字节级保序外一律 jsonb）。
**范围**：information_schema 扫描全部 json 列 → 逐表 `ALTER TABLE ... ALTER COLUMN ... TYPE jsonb USING col::jsonb`（表重写 + 锁，需停写窗口；本部署数据量小，窗口分钟级）。
**步骤**：pg_dump 备份 → 迁移 → models.py 列类型改 `sqlalchemy.dialects.postgresql.JSONB` → 全量回归（重点：JSON 序列化行为、`@>` 查询、hybrid_search、出箱 payload）。
**前置**：P0-A 落地并稳定一个迭代后再做，避免两个变量叠加。
