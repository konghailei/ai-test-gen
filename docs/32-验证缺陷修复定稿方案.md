## 1. F6 连坐：历史脉络与残留形态（拍板依据）

大哥记忆正确——"坏的剔除、好的保留"在 v3.5.2 / v3.5.4 已经修过**两层**，但还剩第三层没修完。三层演进（代码注释实证，`review_agent.py:1144-1155` / `publication_policy.py` 文档头）：

| 层 | 形态 | 修复 |
|---|---|---|
| 第一层 | 内容级缺陷整批判死 blocked，一条不落库 | ✅ v3.5.2 方案 B：`decide_publication` 产出 `partial_block`，坏条剔除进 `error_cases`，好条进 `reviewed_cases` |
| 第二层 | 批次级信号（quality_gate_forced / human_review）连坐取消全部 auto | ✅ v3.5.4 D-3 终版：`auto_allowed` 由"决策类型白名单"改为"内容级缺陷判定" |
| **第三层（残留）** | **partial_block 时 `case_level_reasons` 非空 → `auto_allowed=False` → 好条全部降 `reviewed`** | ❌ 本方案 B-1 |

**本轮实证**（docs/31 F6）：v1.0 三条 blocker 剔除后，193 条好条（置信度 0.767~0.892，全部 ≥0.70 auto 档）全部落 `reviewed` 待人工。代码注释自称"有意防线"，但这与大哥两次拍板的方向（v3.5.2 剔坏留好、v3.5.4 D-3）矛盾——**它是前两次修复不彻底的残留，不是独立设计**。

**防线分析（为什么修掉它不破坏安全性）**：
1. 坏条已在 persist 前剔除（`error_cases` 留档 + draft 占位），不进好条集合；
2. `is_blocked`（blocker issue 命中的 case_id）在 auto 分支已有独立拦截（`review_agent.py:1275` `not is_blocked`），漏剔的 blocker 条也不可能 auto；
3. 批次曾 partial_block 的事实已持久化在每条 `case_json["publication"]` 里，审阅台可筛可查；
4. 置信度 <0.70 的条目仍走 `reviewed`，分级逻辑不变。

## 2. Bug 修复方案（定稿）

### B-1 partial_block 好条恢复 auto 资格（F6 终版）

**改动点**：`backend/app/agents/review_agent.py:1155`

```python
# 现状
auto_allowed = not decision.get("case_level_reasons")
# 改为：内容级缺陷只剔除坏条（已在上文 purged 处理），
# 不再取消好条的 auto 资格；blocker 条由 is_blocked 独立拦截。
auto_allowed = True
```

同时更新 :1144-1154 注释块，记录第三层连坐的关闭（引用本文档）。

**消费点核查**（全量 grep 已做）：`auto_allowed` 共 4 处消费（:1155 定义；:1275 auto 分支；:1329/:1409/:1412 中置信度与更新分支）。改 True 后：
- :1275 `auto_allowed and confidence >= 0.70 and not is_blocked` → 好条 approved（**新增 approved→出箱向量化**，见风险）；
- :1329 `elif not auto_allowed or ...` → 退化为纯置信度判定，`<0.70` 仍 reviewed，行为正确；
- :1409/:1412 同型。

**对流程时长的影响（大哥 2026-10-14 追问，结论：不影响生成主链路，只影响后台消化）**：

1. **生成主链路（SSE 流程）零增加**——persist 落库是同步路径上毫秒级的 DB 写入（每条一个 savepoint insert + 出箱 insert，v1.0 实测 196 条全量落库 ~秒级），出箱**入队**只写一行 PG 记录，不等 Milvus；
2. **向量化转移到了后台 relay**（celery_worker，并发 2，~13-17s/条）——这批工作量**现在也存在**：`reviewed` 条被人工 approve 时走 `testcases.py:651` 出箱（实测 v2.0/v3.0 全 reviewed → 全靠人工 approve 后入箱）。B-1 只是把"人工点完才排队"变成"生成完自动排队"，**总工作量不变，完成时间从人工审批后挪到了生成后**；
3. **净变化**：v1.0 场景 193 条提前 ~人工审批时长（通常数小时~数天）进入检索可用状态；relay 消化 193 条约 25-40 分钟（并发 2），期间 `kb_search` 检索命中逐步增多、无 503 风险（出箱是队列不是同步写）；dev 机 DEDUP_EMBED_WORKERS 默认串行、relay 不受影响；
4. **唯一真实新增负载**：`/knowledge-qa/ask` 的检索结果会在生成后 ~40 分钟窗口内逐步变化（新向量流入），无功能风险。

**验收标准**：
1. 重放 v1.0 场景（3 blocker + 193 好条，置信度全 ≥0.70）：坏条 3 条进 error_cases；好条 193 条 `approved`（不再 reviewed）；
2. 单测新增：partial_block + 高置信好条 → approved；partial_block + blocker 漏剔条 → 仍不 auto；
3. 回归：unit 全量（落库分布相关断言同步更新）+ phase4/phase5。

**风险与对策**：
- **落库分布变化**（reviewed → approved）：预期行为，但 phase4/5 断言基线（188/112）需要核对用例状态分布的断言；
- **approved 才进出箱**（:1327 `_enqueue_outbox` 仅 auto 分支）：修复后好条将新增向量化。v1.0 场景约 +190 条出箱，relay 并发 2、~13-17s/条，约 20-25 分钟消化，需确认 relay 重试/对账能扛（既有机制，预期可扛，验收时观察 pending 归零）；
- 需要人工抽查的场景保留：审阅台按 `case_json->publication->decision = 'partial_block'` 过滤即可。

### B-2 F1 分片审核失败：标记透传 + fail-closed（两步一个批次）

**第一步（最小修复，可见性）**

改动点 1：`backend/app/agents/review_agent.py` `_merge_review_results`（:727 起，返回 dict :792-812）新增两键透传：

```python
"shard_review": llm_report.get("shard_review"),
```

改动点 2：部分失败时 `review_status` 由恒 `"complete"` 改为 `"partial"`——`publication_policy.decide_publication` 已有 `review_status != "complete" → reasons.append("review_not_verified")`，**零改动复用既有判定**，批次自动落入 `human_review`。

改动点 3：`orchestrator.py` done 事件组装处，`review_shard_partial_failure=True` 时追加进 `degraded_flags`（与 `publication_partial_block` 同型），SSE 前端红条可见。

**第二步（fail-closed，防未审先批）**

```python
unreviewed_fp_ids = {
    f.get("fp_id") for f in (report.get("shard_review") or {}).get("failed_shards", [])

```

循环内 auto 分支条件追加：`and str(case.get("related_fp", "")) not in unreviewed_fp_ids`——失败分片的用例**不进 auto**，按置信度落 `reviewed`（待人工），修复 docs/31 F1 "13 条未审用例全部 approved" 的 fail-open。

**验收标准**：
1. 单测：注入 1 个分片 `_run_shard` 异常 → 最终 report 含 `shard_review.failed_shards`、`review_shard_partial_failure=True`、`review_status="partial"`、`degraded_flags` 含该标记；失败分片用例落 `reviewed` 而非 `approved`（用结构字段断言，不匹配 LLM 文本）；

3. 回归：落库分布变化（失败分片条 approved→reviewed），unit + phase4/5 基线同步；
4. 真实验收：复跑一轮带分片失败的生成（或注入异常），确认 done 事件 grep 得到 `shard_review`。

**与 B-1 的交互**：两者都改 persist 分支条件。B-1 放开 `auto_allowed`，B-2 收紧失败分片——合并实施时先落 B-2 的 `unreviewed_fp_ids` 拦截，再放 B-1 的 `auto_allowed=True`，单测覆盖两个条件叠加（好条 approved / 失败分片条 reviewed / blocker 条不 auto）三种形态。

### B-3 F3 安全断言方向写反（13 条存量 + 生成端）

三件事，前两件沿用 docs/31 方案：

1. **生成端 prompt 硬约束**（`gen_agent` 提示词）：负向断言一律 `not_contains` / `not_in`，禁止把载荷本体放进 `expected_value`；
2. **入库前确定性校验**：挂 `validation_issues()`（纯函数，已被 `_merge_review_results` 与 `publication_policy` 双消费）——message 含 过滤/移除/剔除/不保存/拒绝/拦截 之一 且 `type ∈ {contains, equals}` 且 `expected_value` 命中载荷模式（`<script`、`javascript:`、`DROP TABLE`、`onerror`、`<iframe`、`<style`、`<img`、`<!--`）→ 产出 `cases[N].assertions` 内容错误。**产出走既有 `invalid_case_content → partial_block → 剔坏留好` 链路**，与 B-1 修复后的语义自洽：坏条剔除、好条不受连坐（微调点：docs/31 原建议"降级 pending_review"，定稿改为走 validation_issues 剔除——理由：方向反的安全断言执行即假阴性，属于坏条，剔除比降级更符合"剔坏留好"）；
3. **存量 13 条修复**（v1.0 ×2 + v2.0 ×11）：DB 脚本批量 `contains → not_contains`（保留 expected_value 载荷本体作为"不得出现"的对照），修复后逐条人工过目抽样 3 条。

**防误伤**：双条件（message 负向词 ∧ 载荷模式）缺一不判；合法正向断言（如"响应包含 Content-Security-Policy 头"）不含载荷模式，不受影响。单测覆盖正反各 3 例。

### B-6 语义去重误删修复（docs/29 P0，与 B-1/B-2 解耦先行）

沿用 docs/29 §建议路线 P0，四件套：

1. **决策规则升级**：`余弦 ≥0.92` → `余弦 ≥0.92 ∧ 结构佐证`（佐证 = 标题 3-gram 相似度达标 或 步骤序列高度一致）；
2. **四类护栏**（命中任一即不合并）：实体词不一致（产品/项目/模块）、操作词不一致（创建/编辑/删除）、否定/分支词相反（通过/未通过、成功/失败）、扩展名/单位不同（.docx/.markdown）；
3. **小数护栏**：`re.findall(r"\d+")` → `r"\d+(?:\.\d+)?"`（`9.9MB` 不再被吃成 `{"9"}`）；
4. **误删留痕落库**：`semantic_dedup_removed` 从日志/SSE 升级为持久化（进 `review_reports` 或独立表），事后可审计。

**⑤ 角色变体护栏（2026-10-14 探针实证新增，大哥提出）**：

多角色同功能用例（管理员/普通用户/访客/只读成员…，功能相同、部分功能点不同）是去重误删的高危形态。容器内真实 bge-large-zh-v1.5 探针（`_probe_role_dedup.py`）实测：

| 变体形态 | 批内 3-gram（0.55/0.45+0.25） | 跨分片语义（整例 JSON，0.92） | GenAgent L2（标题，0.95） |
|---|---|---|---|
| 角色在短标题（"管理员创建项目成功" vs "普通用户…"） | ✅ 0.364 保留 | ⚠️ **0.9543 删** | ✅ 0.69 保留 |
| 角色在长标题（"管理员导出月度统计报表并验证文件完整性" vs "访客…"） | ⚠️ **0.737 删** | ⚠️ **0.9745 删** | ✅ 0.83 保留 |
| 同标题、角色只在步骤里（登录身份不同） | ⚠️ **1.000 删** | ⚠️ **0.9885 删** | ⚠️ **同标题=1.0 删** |
| 对照组：真重复 | ⚠️ 删（正确） | ⚠️ 0.9663 删（正确） | — |
| 对照组：不同场景 | ✅ 保留（正确） | ✅ 0.8142 保留（正确） | — |

结论：**角色词在整例 JSON 中占比过小，embedding 分辨不出角色差异——语义层三种形态全命中（0.95-0.99 vs 阈值 0.92），数字护栏完全无效（角色不是数字）**。与 docs/29 生产留痕的"产品 vs 项目 0.927 误删"是同一家族（实体维度差异被向量淹没）。本轮 320 条中 v1.0 有 24 条角色用例但无同骨架变体对（未实际触发）；但系统 09-22 起 `collect_points` 已提取 `role.N` 要点并要求分角色覆盖——若角色变体被去重，role 要点永远补不上，且会诱发"补生成→再被删→再补"的死循环（本轮"补生成未收敛"的潜在成因之一）。

**⑤-b 角色误删的治本设计：分层闸门（2026-10-14 追加，大哥追问"怎么办比较好"）**

先说清为什么不能只调阈值：探针数据里**真重复 0.9663 与角色变体 0.9745/0.9885 在向量空间犬牙交错**——降阈值救不了变体（变体比真重复还像），升阈值挡不住变体（0.9885 同标题形态）。阈值手段在此结构性失效，这与 docs/29 "0.89-0.95 区间误删/漏判分布重叠"是同一结论。所以治本靠**分层闸门**，每层职责单一：

```
命中"疑似重复"（向量 ≥0.92 或 3-gram 达标）
        │
        ▼
┌─ 闸门1：确定性护栏（纯文本比对，零成本，确定性优先）────────────┐
│  两例的角色词集合不一致 → 保留（不合并）                        │
│  实体词 / 操作词 / 否定分支词 / 扩展名 / 小数护栏 —— 同结构并入       │
│  角色词表 = SRR user_roles 动态收集（coverage.py 已有提取逻辑）      │
│            + 静态兜底词表（管理员/普通用户/访客/只读/作者/审批人…）   │
└──────────────┬──────────────────────────────────┘
               │ 护栏全过（两侧角色词一致或都无角色词）
               ▼
┌─ 闸门2：LLM 裁决（只在"护栏全过 + 相似度极高"的窄带内触发）────────┐
│  sim ≥ 0.92 且护栏全过 → 单次轻量 LLM 判定：                     │
│  "这两条用例是否为同一测试场景？若角色/实体/操作不同则不是重复"      │
│  ├─ 不是重复 → 保留，留痕（reason=llm_distinct）                │
│  └─ 是重复 → 合并，留痕（reason=llm_duplicate:sim）             │
│  成本控制：只对"即将删除的对"触发（每批通常 0-5 对，非全量比对）；    │
│  LLM 失败 → fail-open 保留（宁可漏删不可误删——去重是优化不是正确性） │
└──────────────┬──────────────────────────────────┘
               │ 判定删除
               ▼
┌─ 闸门3：留痕可审计 + 一键复活 ──────────────────────────────┐
│  removed 记录已含 removed/kept/title/reason 四要素；             │
│  B-6 第 4 件套（留痕落库）让它可查；                             │
│  新增：审阅台"去重留痕"视图，误删条目支持一键恢复（错误案例已先例）   │
└──────────────────────────────────────────────────────┘
```

**设计原则与取舍**：

1. **确定性优先**（闸门1）：纯文本比对不花钱、可解释、可单测——能用确定性手段拦的绝不进 LLM。这与 MEMORY 纪律"规则层产出必须确定性到达"一致：护栏函数是纯函数，进单测锁死（探针 5 组 + docs/29 留痕 9 保留/23 合并 + 320 条 7 对边界对全部过闸门）；
2. **LLM 只裁窄带**（闸门2）：护栏解决"已知家族"（角色/实体/操作/否定/扩展名），但词表永远有盲区（下个需求文档写"超级管理员/协作者"）——LLM 裁决兜住"未知家族"。触发面 = "即将删除的对"，每批 0-5 次 LLM 调用，成本可控（对比：生成一个 FP 分片本身就要几十次调用）；**fail-open 方向刻意选保留**——漏删几条真重复的代价（多几条用例、审阅台能看见）远小于误删的代价（角色覆盖永久缺口、不可逆、还诱发补生成死循环）；
3. **可复活是最后防线**（闸门3）：既然 0.89-0.95 区间分布重叠是结构性的，任何判定都可能有残余误差——留痕 + 一键恢复把"误删"从不可逆事故降级为可纠错操作。错误案例机制（error_cases 复活）已有先例，复用同型 UI；
4. **为什么不单靠词表**：词表是黑名单思路，天然滞后（新角色名、英文角色、拼音缩写都会漏）；为什么不单靠 LLM：全量对都问 LLM 成本高且引入不稳定。分层 = 确定性拦大头 + LLM 兜窄带 + 留痕收残余。

**改动落点**：

## 4. 评估重建（docs/29 P1）：定稿建议 = 暂缓

**它是什么**（大哥问的"不太清楚"项）：语义去重**定标 gate 的评测体系重建**——docs/29 发现原 gate 三处方法学缺陷（评测域 ≠ 生产域：定标语料 66% 是跨 req 对，而生产只在单任务内去重；无正样本标签：gate 退化成"与 T0 一致"，结构上发现不了 T0 自己判错；divergent 不是误删信号）。所以当年"E/A 方案否决"的结论**不成立**，只是"未验证"。

**它和 B-6 的区别**：B-6 是**修生产 bug**（0.92 阈值正在误删真实用例，不可逆）；评估重建是**建考试**（未来想换模型/改口径/调阈值之前，先有一套可信的考卷证明新配置不劣化）。

**暂缓理由**：
1. 当前定稿路线不换模型、不改口径、不动阈值（B-6 只在余弦判定外**加**护栏，收紧方向单调安全）——考试服务的决策近期不存在；
2. B-6 护栏的验证用现成材料即可：docs/29 的 32 条留痕 + docs/31 的 320 条（含 7 对合法边界对）就是小规模考卷，不需要完整重建；
3. 完整重建成本高（per-req 语料重组 + LLM 判重标签 + 人工抽查三轮），预期收益在"未来优化"而非"当前正确性"。

**重启条件**（满足其一即重启）：B-6 落地后误删率抽检仍 >5%；或未来要评估 bge-base/ONNX 量化等表征层变更；或阈值需要重定标。
