## 5.3 根因追查：这是系统真实缺陷，不是测试方法问题（2026-10-20 补充）

> 结合前后端与生成链路逐层追查后，**修正 §5.1 的粗粒度归因**：11 条用例缺陷不是"LLM 随机幻觉"，而是系统三层缺陷的必然产物。

### 5.3.1 缺陷链路（证据）

| 层 | 组件 | 缺陷 | 证据 |
|---|---|---|---|
| **① 解析层** | ReqAgent | `api_definitions` 提取**召回低 + 精确低** | R1 提取 4 条、R3 提取 4 条（需求文档明确路径 ≥8 个）；R3 的 4 条中 **2 条是臆造**（`/api/llm/fallback`、`/api/retrieval/status` 在 OpenAPI 中不存在） |
| **② 生成层** | GenAgent | 无 api 要点覆盖时**自行发明路径** | 6 个不存在路径不在任何 SRR 的 `api_definitions` 中（`/api/v1/requirements`、`/api/task/{id}`、`/api/admin/product/list`、`/api/knowledge-base/status`、`/api/llm/provider/{id}`、`/api/metrics/event_loop`） |
| **③ 校验层** | 全链路 | **无接口真实性校验** | 解析后不校验、生成后不校验、落库前不校验 → 幻觉直达产物 |

**关键实证**：R3 的 `srr_json.api_definitions` 实际内容包含

```json
{"path": "/api/llm/fallback", "method": "POST", "summary": "LLM提供商熔断处理接口，禁用失败提供商600秒"}
{"path": "/api/retrieval/status", "method": "GET", "summary": "检索状态接口，透出Milvus可用性与降级状态"}
```

而需求文档原文只有**能力描述**（v1.0 §3.12.3 熔断机制、检索降级），**从未给出这两个路径**。ReqAgent 把"能力"臆造成了"HTTP 接口"，GenAgent 忠实使用，用例因此不可执行。

### 5.3.2 为什么这算系统缺陷（而非测试方法问题）

1. **产品定位决定**：AI-Test-Gen 的核心产出就是"可执行用例"。输出不可执行 = 核心能力缺陷，不能归因为"测试脚本写得不对"。
2. **链路可定位**：缺陷在解析/生成/校验三层的具体代码，不是数据问题、不是环境问题。
3. **不是随机性**：8 个坏路径中 7 个能映射到"需求里有能力描述但无路径"或"跨模块命名习惯推断"——**系统性偏差，可复现、可修**。

### 5.3.3 前后端契约是自洽的（排除前端问题）

- 前端 `client.ts` 仅有 `health()` 封装，无 `/api/v1/*`、`/api/task/*`、`/api/llm/fallback` → **前端从未使用这些路径**，问题不在契约漂移，而在"生成用例时未参考既有契约"。
- 后端 OpenAPI 130 条路径与前端调用面一致（抽样核对通过）。
- `coverage.py:100` 把 api 要点渲染为 `"{method} {path}"` 送入生成 prompt → **只要 `api_definitions` 正确，生成器就能拿到正确路径**；故根因在 ① 而非 ② 的"看不到契约"。

### 5.3.4 另外 2 处需求-实现契约不一致（文档缺陷，非实现 Bug）

| 项 | 需求原文 | 实现 | 定性 |
|---|---|---|---|
| 分页超限 | v1.0 §4.1「超出**按 100 截断**」 | `Query(le=100)` → **422 拒绝**；代码注释（v3.4.1 L-5）明确"避免静默截断导致回显值失真" | **实现有意偏离且更合理，需求文档未同步** → 文档缺陷 |
| 未授权状态码 | v1.0 §1「未授权访问受控接口返回 **403**」 | 未携带/无效 token → **401**；权限不足 → 403（`auth.py:288/310`） | **实现符合 HTTP 语义，需求表述笼统** → 文档缺陷 |

### 5.3.5 1 个安全加固点（非实现缺陷）

`/api/health` 未鉴权且返回 `llm_provider`、`db_type`、`vector_store`、`event_loop` 内部参数、`generation_load` 等。需求 §2.1.1/2.1.2 要求这些指标"经 health 透出"，但**未规定鉴权级别**；`main.py` 注释表明"health 公开"是刻意设计。→ **生产部署建议分级**：公开 `/api/health` 只返回 `{status, version}`，详细指标走鉴权端点（需求需同步调整契约）。

### 5.3.6 责任划分：需求文档 vs 系统生成（量化比对）

对三份需求文档做路径抽取，与 OpenAPI 130 条逐条比对：

| 指标 | 结果 |
|---|---|
| 需求文档中明确出现的路径 | **38 个** |
| 其中真实存在（含自动补 `/api` 前缀后存在） | **37 个 → 正确率 97.4%** |
| 唯一 MISS | `/impact-analysis/confirm`（v2.0 §2.2.2 缩写，完整路径 `/api/requirements/{req_id}/impact-analysis/confirm` 存在） |
| **8 个坏路径在需求文档中的出现次数** | **0 次（全部零提及）** |

**结论：主责在系统生成，需求文档不是主因。**

- **系统侧（主责）**：8 个坏路径 100% 由系统产生——2 个来自解析层臆造（把「能力描述」变成 HTTP 接口）、6 个来自生成层自创（无契约时自由发挥）；且全链路无真实性校验。
- **关键行为不一致**：解析层对**文档中写了的路径**是忠实照抄的（哪怕缺 `/api` 前缀也照抄，如 R1 的 `/requirements/upload`），对**文档中没写的路径**则**凭空编造**。正确策略应是：没有路径就留空，而不是发明。
- **需求文档侧（次要瑕疵，不构成主因）**：
  1. 5 个路径缺 `/api` 前缀（`/requirements/tasks/{task_id}/cancel`、`/requirements/{req_id}/fp/dependencies`、`/requirements/{req_id}/fp/merge`、`/requirements/{req_id}/impact-analysis`、`/impact-analysis/confirm`）——前缀不统一，会诱导解析层抄出不完整路径；
  2. 1 处缩写（`/impact-analysis/confirm` 缺父路径）；
  3. 2 处表述与实现不一致（分页「截断」vs 422、未授权 403 vs 401）；
  4. 「熔断」「检索状态」等能力只描述机制、未声明"是否暴露接口"，留下推断空间。

**必须强调的边界**：需求文档"没给路径"**不能成为系统臆造接口的理由**。需求未给契约时，系统的正确行为是「不生成 API 调用步骤 / 标记契约缺失」，而不是编一个路径——这是生成策略问题，主责在系统。
