ai-test-gen · Harness 工程亮点

围绕「非确定性 LLM 流水线」搭建的判定、执行与证据基础设施

仓库 konghailei/ai-test-gen · 整理于 2026-09-16 · 全部条目均经代码实读核实

一句话结论：这个项目最值钱的 harness 设计不是某个脚本，而是 「脚本只判结构与机制，内容判定回传给 AI」的分层原则，以及与之配套的 服务端证据链——任何"上线/发布/跳过"的决定都必须引用可复现证据，而不是调用方的声明。

三层结构总览

判定层决定什么叫合格；执行层兜住跑不完、跑错了；证据层回答"凭什么信它"。

1三层测试计划执行器

把"验证 LLM 流水线"拆成机器可判 / 人（或 AI）可判的两类问题。

脚本只判结构与机制，内容判定回传 AI

核心设计

L1 机制层用探针 + 回归脚本断言不变量（互斥、幂等、状态守卫、指纹）；L2 流程层跑真实 API， 零内容断言，只判状态码、终态合法性、字段齐全、计数一致；L3 内容层把生成内容原样打包成 ai-review/ 证据包 + AI-REVIEW-TASK.md 任务书（判什么、按什么标准、交付什么）， 交 AI 逐条判定后经落地脚本写库。

  • backend/scripts/run_test_plan.py — step_mechanism() / step_unit() / _structural_checks() / write_ai_task()
  • L1 覆盖清单在 PROBES 与 REGRESSION 常量里，改测试计划只改这两处
  • 输出：/app/_review_runs/plan-<ts>/plan-results.json（三层结果汇总）
# 只跑 L1 机制层（秒级，不烧额度）
docker exec ai-test-gen-api python /app/scripts/run_test_plan.py --only mechanism

# 完整三层：需求分析 → 生成 → 结构断言 → 打包给 AI 判定
docker exec ai-test-gen-api python /app/scripts/run_test_plan.py

为什么值得迁移：用脚本断言 LLM 的输出内容必然误判。把"机器可判的不变量"和 "需要判断力的内容"分开，前者交给脚本（客观、可重复、秒级），后者回传给模型并保留证据包。

240 个故障注入探针

不等故障自然发生，而是按验收口径主动制造故障点。

把非确定性问题拆成可确定复现的断言

确定性验证

backend/_probe_*.py 共 40 个，命名即验收点。全部跑在容器内、不调用 LLM， 用真实 PG/Milvus + 桩 Agent，秒级出结果。典型手法是在关键边界注入崩溃，然后断言"最终收敛且不重复"。 本次实跑 _probe_outbox.py 为 13 项通过 / 0 项失败， 三个崩溃点分别是：PG commit 前崩溃（事务回滚）、投递失败后退避重试、Milvus 成功后 ack 前崩溃（重复投递幂等）。

  • backend/_probe_outbox.py — 出箱三崩溃点收敛
  • backend/_probe_concurrency.py — 并发互斥 + SSE 隔离
  • backend/_probe_durable.py — 断点续跑 + 输入指纹
  • backend/_probe_revision_lock.py / _probe_selfheal.py / _probe_first_response.py …
# 单个探针（示例：出箱）
docker exec ai-test-gen-api python /app/_probe_outbox.py

# 查看权威清单（PROBES 常量）
docker exec ai-test-gen-api python /app/scripts/run_test_plan.py --only mechanism

为什么值得迁移：失败路径的验证用注入而不用等待——确定性、秒级、不烧额度。 项目里多次用"换桩 + 断言降级标记"的方式验证 LLM 失败路径。

3服务端评测门禁

"提示词能不能上线"从调用方声明，改成服务端可复现证据。

prompt_hash 逐字绑定 + 基线不劣化

证据链

原本激活候选提示词只校验客户端提交的 confirmed_eval: bool——等于自证清白。 现在激活接口必须引用一条服务器端 passed 的评估运行，且通过 6 项校验：运行存在 → 状态为 passed → target 一致 → 数据集 hash 非空 → 口径版本一致 → prompt_hash 逐字匹配； 另外必须有基线对比记录，证明"不比线上更差"。候选文本改一个字，旧评估立即作废。

  • backend/app/core/evaluation.py — validate_prompt_activation()（纯函数，便于单测）
  • backend/scripts/eval_prompt_candidate.py — 候选 vs 线上基线 A/B
  • backend/scripts/eval_retrieval.py — 检索质量 recall@5/10/20 + MRR
  • mark_evaluation_run_consumed() 记录"这条提示词凭什么上线"
# 冷启动冒烟（1 条样本，省额度）
docker exec ai-test-gen-api python /app/scripts/eval_prompt_candidate.py \
  --integration-id PI-xxx --limit 1

# 检索质量（依赖 backend/eval/retrieval_evalset.jsonl 的人工标注）
docker exec ai-test-gen-api python /app/scripts/eval_retrieval.py --top-k 20

为什么值得迁移：LLM 资产（提示词、检索配置、模型路由）的每次变更都应有 版本化数据集 + 可复现评估记录 + 内容 hash 绑定三件套，否则"评估过"只是一句口头承诺。

4fail-closed 发布决策

合格与否是纯函数算出来的三态，不是抛异常。

Unknown is not success：未知一律降级为人工复核

门禁

decide_publication() 只认正向证据：没有用例、内容合同错误 → blocked； 其余缺失（覆盖口径未知、审核降级、质量门未过、子任务失败、任一降级标记）→ human_review； 全部通过才 auto_approve。原因码可枚举（coverage_unknown、 review_llm_failed、invalid_point_references…），前端可直接展示。 与之配套的 quality_outcome() 产出 done 事件的 completion_status （completed / awaiting_human_review / failed）。

  • backend/app/core/publication_policy.py — decide_publication() / quality_outcome()
  • backend/app/utils/case_validation.py — 用例可执行合同（断言 type/target/expected_value、steps）
  • 合同校验与覆盖未知只记录、不抛异常，处置权留在策略层
# 纯离线单测，无需任何服务
python -m pytest backend/tests/test_publication_policy.py -q

关键教训：把"不合格"写成 raise → 节点异常 → 流水线中途终止 → 连 done 事件都不会发出，终态与原因全无从上报。正确形态是「不写副作用 + 终态可见 + 前端可判定」， 验收断言要检查 done 事件本身，而不只是"没写库"。

5判定器自身的可信度

评分器、Judge、A/B 对比各有一套护栏。

确定性评分优先，Judge 必须过金标校准，对比必须过显著性检验

元验证

① 评分不用 LLM。score_sample() 用 must_cover 要点命中率打分 （KEYPOINT_MIN_RATIO = 0.6），注释写明理由：让 LLM 再打一次分不可复现、且成本翻倍。 没有期望要点的样本保守判为不达标——不能白送分。

② 用 Judge 必须先校准。calibrate_judge.py 强制在金标集上算 Cohen's kappa > 0.7 才允许启用 LLM-as-Judge（MIN_SAMPLES = 30）， 退出码即结论：0 可用 / 1 不可用 / 2 数据不足；换模型或改 rubric 必须重校。

③ A/B 对比要过统计。eval_stats.py 提供配对 McNemar 精确检验、Wilson 置信区间 与 pass^k 稳定性口径——两个配置比分数不是裸比命中率。

  • backend/app/core/evaluation.py — score_sample() / score_dataset()
  • backend/scripts/calibrate_judge.py — KAPPA_THRESHOLD = 0.7
  • backend/scripts/eval_stats.py + backend/app/core/eval_stats.py
# Judge 金标校准
docker exec ai-test-gen-api python /app/scripts/calibrate_judge.py \
  --report-id RR-xxxx --golden /app/eval/golden/review_golden.jsonl

# 两个配置的配对显著性检验
docker exec ai-test-gen-api python /app/scripts/eval_stats.py pair run_a.jsonl run_b.jsonl

为什么值得迁移：自动化判定的可信度本身必须被度量，否则"评估通过"只是另一个黑盒。 kappa 门槛 + 显著性检验是让评测结论站得住的最小成本做法。

6指纹断点续跑与启动自愈

续跑的前提是"输入没变"，宁可不续，不乱续。

8 字段输入指纹 + 保守自愈策略

执行可靠性

checkpoint 里记录 req_id / product_id / revision / srr_sha256 / fp_set_sha256 / prompt_version / model / schema_version，续跑前全部离线复算比对，任一不一致返回 409（只有显式 fallback_to_restart=true 才允许从头）。指纹校验必须在占用并发槽位之前—— 放在原子占用之后会把 running 任务留在库里，造成槽位泄漏。

API 启动时另有自愈：扫描近 24h 内 interrupted 且有 checkpoint.fp_groups 的生成任务自动续跑，但规则极保守——每个需求最多续一个、需求状态非 confirmed 跳过、 指纹校验不过就跳过并保留 interrupted 交人工。文件里的原话是"自愈绝不把旧产物拼到新输入上"。

  • backend/app/core/pipeline_fingerprint.py — compare_fingerprints() / load_current_fingerprint()
  • backend/app/core/task_selfheal.py — SELFHEAL_WINDOW_HOURS = 24 / SELFHEAL_MAX_TASKS = 5
# 断点续跑 + 指纹校验
docker exec ai-test-gen-api python /app/_probe_durable.py

# 启动自愈调度
docker exec ai-test-gen-api python /app/_probe_selfheal.py

为什么值得迁移：长耗时 LLM 任务必然被中断。要能安全续跑，就得把 "输入指纹"显式化成可复算的数据结构，并且给自动化一个保守的默认动作（跳过而非猜测）。

7并发互斥与事务性出箱

两个最容易出现"看不见的脏数据"的地方，各有一层专门机制。

三层互斥 + 失败必须分类

一致性

reserve_generation_slot() 在同一事务内按 hashtext(req_id || ':generate') 取 advisory 锁 → 回收僵尸 → 检查活动任务 → 插入；DB 层再有一个 partial unique index 兜底 （仅约束 status IN ('pending','running') 的生成类任务）。resume=True 不绕过互斥。

最有价值的是错误分类：最初实现把任何插入异常都返回 conflict，导致外键错误被读成 "已有任务在跑"，排查方向全错。现在只把唯一索引冲突当 conflict，其余照抛 500。

  • backend/app/core/task_guard.py — reserve_generation_slot()
  • backend/app/db/database.py — init_db 里的 partial unique index
# 20 并发同 req_id，断言只有 1 个成功
docker exec ai-test-gen-api python /app/_probe_concurrency.py

判据：错误分类错了，比不报错更贵。

跨库写入走"出箱"（outbox）

一致性

PG 与 Milvus 无法同事务，项目里禁止在业务事务外直写向量：业务行与出箱意图同事务提交， relay 用 FOR UPDATE SKIP LOCKED 认领、幂等 upsert、5→300s 指数退避、超 8 次转 failed 等对账处理。向量 metadata 带 revision 与 content_hash 用于识别陈旧数据；删除类判定只有一份实现。

  • backend/app/core/vector_outbox.py — enqueue() / relay
  • backend/app/core/kb_vector_reconcile.py — 对账（周期任务与 CLI 共用同一实现）
# 三个崩溃点：commit 前 / 投递失败 / ack 前
docker exec ai-test-gen-api python /app/_probe_outbox.py

# 出箱单测
python -m pytest backend/tests/test_vector_outbox.py -q

为什么值得迁移：凡是"两个存储要一致"的地方，出箱模式几乎是唯一能在崩溃语义下 说清楚"最终会发生什么"的方案。

8静默降级扫描与真实数据定标

让"能力静默缺失"这类最隐蔽的缺陷可机械发现。

AST 扫描"捕获不标记"，输出待判定清单而非缺陷清单

可观测性

判定规则很明确：捕获块类型为 Exception/BaseException + 块体内没有 raise + 块体内有 logger.warning/error，再按是否出现 降级标记关键字（degraded/skip_reason）分档。实测有 40 处静默捕获、36 处无降级标记。工具刻意把自己定位为"待判定清单"——很多命中是合理兜底， 需按「是否让产出质量看起来正常而实际缺失」逐条判定。

与之呼应的还有阈值定标：RetrievalThreshold.FEW_SHOT_MIN_SIMILARITY = 0.50 来自真实 分布实测（信号 0.413~0.588 / 噪声 0.345~0.458），代码注释明确写着 "不是照搬业界 0.75"——照搬会把 100% 的候选过滤掉。模式检索阈值 0.45，因为它误注入代价更低。

  • scripts/scan_silent_degradation.py — AST 扫描器（含 HOT_FILES 优先清单）
  • backend/app/core/constants.py — RetrievalThreshold（含实测分布注释）
  • backend/app/core/task_watchdog.py — 每 120s 回收超 60 分钟的任务，置 interrupted
  • backend/app/orchestrator.py 组装 degraded_flags，前端可直接展示
# 扫描 app 全量
python scripts/scan_silent_degradation.py --all

# 去重阈值单测（真实数据标定后的边界用例）
python -m pytest backend/tests/test_case_dedup.py backend/tests/test_coverage_evidence.py -q

为什么值得迁移："失败但看起来成功"是 LLM 系统最贵的缺陷类型。 两个可迁移动作：① 任何降级都要打可观测标记并复用现有的标记通道； ② 阈值一律先在真实数据上定标，再写进常量并留下实测分布注释。

9人机闭环与失败回流

内容判定的人工环节也要有产物、有快照、有回流。

审阅台 → 判定落地 → 评估集回流

闭环

审阅台：真实跑一次生成，把 done 事件、落库状态、覆盖口径渲染成单文件 HTML， 供人逐条判定。关键约束是"展示事实的工具必须复用系统同一套口径"——覆盖标注直接 import 后端 extract_point_ids，不自己实现一套，否则会把 54 条有标注的用例全标成"未标注"。 产物写容器内 /tmp，因为往 /app 写会触发 reload 杀掉在飞任务。

判定落地：apply_verdicts.py 默认干跑，--execute 才写库； 符合→批量 approve（同步写向量），不符→批量 reject，存疑→不动，并自动快照执行前状态以便回溯。

失败回流：reflux_failures.py 把生产 failed/error 任务脱敏后导出到 backend/eval/failure_cases.jsonl，按 task_id 幂等，让评估集成为活资产。

CI 门禁：backend/tests/conftest.py 用 AITG_RUN_INTEGRATION=1 决定是否收集脚本式集成套件，使 unit 层无需 PG/Redis 即可跑（91 passed / 1 skipped）； CI 里的 continue-on-error 已移除，pytest 失败即红灯。

  • backend/scripts/review_generation_run.py — 审阅台（--req-id 真跑 / --task-id 重建 / --from-run 重渲染）
  • backend/scripts/apply_verdicts.py — 判定落地
  • backend/scripts/reflux_failures.py — 失败轨迹回流
  • backend/tests/conftest.py + .github/workflows/test.yml
# 生成 + 收集证据 + 出审阅台（约 25 分钟，消耗额度）
docker exec ai-test-gen-api python /app/scripts/review_generation_run.py \
  --req-id REQ-xxx --note "口径修复后的复测"

# 落地判定（默认干跑，加 --execute 才写库）
docker exec ai-test-gen-api python /app/scripts/apply_verdicts.py \
  --run-dir /app/_review_runs/20260916-xxxxxx

# 失败回流到评估集
docker exec ai-test-gen-api python /app/scripts/reflux_failures.py --limit 20 --days 30

# CI 同款 unit 层（无需 PG/Redis）
python -m pytest backend/tests -q

为什么值得迁移：人工判定如果不能落库、不能回流、不能复现系统口径， 就只是"看过一遍"。三件套（证据包 / 干跑默认 / 幂等回流）让它变成可累积的资产。

可迁移的方法论

换到任何 LLM 应用都成立的五条。

  1. 脚本判结构与不变量，内容判定回传模型。不要写断言去判 LLM 生成文本好不好。
  2. 任何"上线 / 激活 / 跳过"的决定都要引用服务端可复现证据，并用内容 hash 逐字绑定； 调用方的自我声明一律不算。
  3. 合格判定写成纯函数返回三态，不要抛异常。异常会吃掉终态，前端只剩空白； 未知应当 fail-closed 到人工复核。
  4. 失败路径用注入验证，不要等它自然发生。换桩 + 断言降级标记，确定性、秒级、不烧额度； 同时要确认标记真的到达了消费方，中间层返回值不等于最终输出。
  5. 阈值与合同先用真实数据定标，再谈调参。项目里反复验证：判定键选错了，调阈值零收益。

边界与未做项

避免把这份清单读成"已经完美"。

  1. 生成任务仍跑在 API 进程内。完整持久任务队列（迁出进程）是架构级改造，目前 40% 的价值 靠启动自愈续跑顶住；API 重启仍会杀掉在飞任务，只是能被自动续跑捡回来。
  2. 集成层尚未进 CI。脚本式套件（test_phaseN_*.py）需真实 PG/Redis/Milvus， 要等迁成标准 pytest + service containers 后才能进 CI 门禁；目前 CI 只跑 unit 层。
  3. 探针是本地资产。backend/_probe_*.py 被 gitignore，40 个探针在仓库里不可见， 新环境需要按 run_test_plan.py 的 PROBES 清单重建。
  4. 覆盖率仍有盲区。要点采集只覆盖 5 类要点，FP 为空时 business_rules 与 data_constraints 两个维度会消失；标注率低于 30% 时补生成不会触发。这是当前 最高优先级的已知风险。
