需求管理设计：
为什么我们这么设计？

把"我们系统"的需求管理，和业界 4 种常见做法摆在一起比优劣，用生活中的例子，给完全不懂的你讲清楚。
📄 基线：docs/11 系统 vs 业界 🎯 仅需求管理设计（不含测试用例生成） 🗓️ 2026-07-29

先讲人话：什么是"需求管理设计" 0

开奶茶店前，得先想清楚：卖哪些口味、杯子多大、会员怎么算、停电了怎么办……

把这些"要想清楚的事"想周全、记清楚、还能随时改和查，叫需求管理。
"需求管理设计"讨论的是：用什么"架子"去装这些需求，才不容易乱、不容易漏、改了还能追溯？

🧋 本文主角：我们自研的 AI 测试平台（ai-test-gen），它在"需求管理"这一层有一套自己的设计。

A 散文/纯文档式

长什么样：像你给合伙人发的微信——"明天把菜单定一下，奶茶甜度客户说要可调，顺便看看隔壁会员卡怎么弄。"信息有，但散、乱、没结构。

  • ✅ 上手零门槛，5 分钟能写
  • ✅ 早期灵感记录很顺手
  • ❌ 无法精确定位（"那条安全需求是哪条？"答不上）
  • ❌ 难以统计、容易遗漏、难追溯
  • ❌ 模糊需求不会被自动发现
📱 微信例子：
"登录要支持账号密码和验证码。密码要能隐藏。为了安全最好输错5次锁账号。界面要好看，按钮用蓝色。"
——三句话混了功能/安全/界面，没编号没优先级，开发得自己拆。
🌐 网络案例 1：Atlassian 把"写清晰需求"列为敏捷第一实践，要求用 INVEST 准则消除"快/友好"这类模糊词。散文式恰恰相反——既不结构化，也没澄清机制。

B 重型需求工具式（DOORS / Polarion）

长什么样：造航母时，每个螺丝钉都要能查到装在哪、谁供的、改了影响哪根管道。靠一张"需求追踪矩阵(RTM)"大表实现双向追溯。

  • ✅ 追溯极强、合规无忧（航空/医疗/汽车强制）
  • ✅ 改一条需求，自动标红"牵连 30 处"
  • ❌ 重：要培训，普通人一周未必上手
  • ❌ 贵：授权费动辄几十万
  • ❌ 慢：写一条需求要走流程
🌐 网络案例 2/3：RTM 被比作"QA 的安全带"——平时无感，出事时庆幸它在。但同一资料提醒："追溯成本要和风险成正比，不是每个项目都需要正式 RTM。" 中小项目用 DOORS 是杀鸡用牛刀——这也是我们没选它的核心原因。

C 敏捷看板式（Jira / 禅道 / TAPD）

长什么样：你家的"家务便利贴看板"——一张贴纸写"买菜"，贴「待办」；做了移「进行中」；做完移「完成」。Jira 把贴纸叫 User Story，三列叫看板，再配每 2 周一轮的迭代。

  • ✅ 协作强、进度可视、特别适配迭代
  • ✅ 开发/测试/产品同一张看板，沟通成本低
  • ❌ 需求易碎片化（一条一卡，全局靠人拼）
  • ❌ 跨模块共享规则 / 非功能需求没处放
  • ❌ 卡片里仍是散文，缺"规则不重复"硬约束
🌐 网络案例 1/4：Atlassian 自己都要求"把非功能需求（性能/安全）跟着每个功能一起写"；可现实里 Story 最容易把"跨模块共享规则"漏掉——它不属于任何一张便利贴。aqua 也指出纯看板在跨团队/合规上弱，所以才有 Jama/Polarion 补位。这正是看板的结构性短板。

D 学术歧义澄清式（ClarifyGPT · FSE'24）

长什么样：你写的需求模糊，它先试着写代码，发现代码里"这里也对、那里也对、自相矛盾"，于是反过来问你："你这句到底是 A 还是 B 意思？"

  • ✅ 歧义发现非常精准，直戳"需求想不清"痛点
  • ✅ 硬核数据：GPT-4 一次写对率 70.96% → 80.80%（被引 130+）
  • ❌ 依赖"先写代码"——需求阶段还没代码时失效
  • ❌ 不治"规则重复/分层/版本/追溯"等工程管理
  • ❌ 工程化重，不是开箱即用
🌐 网络案例 5：ClarifyGPT（中科院/北航，FSE'24 顶会）核心动机："用户常常无法准确表达需求，现有 LLM 不懂主动澄清，直接按模糊需求生成，结果跑偏。"思路值得借鉴——但前提是已有代码可写。我们系统是需求阶段就澄清，所以改用"知识库+结构化检测"更早更轻地达成同类目标。

E 我们系统：借各家优点，避开各自的坑

🟢 吸收了谁
  • ClarifyGPT 的"先澄清再动手"共识
  • BDD 的"把模糊变具体（用例子）
  • DOORS 的"基线 / 影响分析"思想
  • RTM 的"可追溯是安全带"理念
🔵 我们怎么落地（轻量版）
  • 双 SRR 分层 → 规则不重复
  • FP 子系统 → 可复用/去重/影响分析
  • 状态机+版本 → 可回滚（不买重型工具）
  • KB 澄清 → 用 2026 生产级 RAG 实现
🎯 一句话：我们没闭门造车，而是用轻量方式，把业界验证过的优点"拼"成最适合中小产品、快速迭代、且人人能读懂的一套。

E① 双 SRR 分层：分开放的规则柜

铁律：单功能规则 → 放 sub_srr；跨功能共享 → 放 interaction_srr；禁止重复写。

doc11 实证：旧架构每条规则出现 2 次，新架构降到 0 次。

🧋 例子："杯子要耐热"是全店通用 → 只在通用柜写一次；"奶茶糖度可调"只属奶茶 → 放奶茶柜。绝不在每个小食单上都抄一遍"杯子耐热"。
🌐 网络案例 6：BDD 用"具体例子"把模糊变具体（如"消费100元→金牌8折"），目标一致；但我们多了层级职责分离，避免 BDD 在大型系统里"例子散落、互相重复"。

E② FP 功能点：可拼装的乐高模块

每个 FP 是独立可管单元：

  • 🔁 去重跳过 LLM：同模块已有同名 → 直接复制，省调用费
  • 📦 模块多选：一个 FP 可挂多个模块
  • 🕸️ 依赖图谱 / BFS 影响分析：改一处知道牵连谁
  • ✅ 审核流：pending → approved（店长签字才用）
🧋 例子：总店做过"会员打折"，分店也要——系统发现同名 FP 已存在，直接复用，不重新设计，两家规则还一致。
🌐 网络案例 1：业界共识"渐进细化"——别一次写全，让需求分层在临近实现时再细化。我们的 FP 把这件事工程化了，还加了业界面少见的"去重跳过 LLM"降本优化；依赖影响分析则是 DOORS"影响分析"的轻量版。

E③ 状态机 + 版本：带时光机的公文

状态机：draft → pending_review → confirmed → archived，任意态可"补充重新生成"。

版本快照：每次改动前自动存一份，能回到任意历史版本（restoreVersion）。

🧋 例子：新菜单先"草稿"，店长审过变"已确认"上线。两周后想改糖度，系统先自动存"当前版快照"，改坏了能一键回到改之前那版。
🌐 网络案例 3：DOORS 的"基线（冻结快照）"思想我们取其精华做轻量版——不强制走变更委员会，但每次改动前自动快照，保留"可回滚"核心收益，又没官僚成本。资料还建议"把版本控制作为 Definition of Done 的一部分"。

E④ 需求侧 KB 澄清：记性超好的老员工

需求模糊/不全时，系统自动查"知识库"帮你补全、发现遗漏：

🔍 检索组合（doc11 称"生产级"）：
向量(bge-large-zh) + BM25(中文分词)
→ RRF 融合(k=60) → Cross-Encoder 重排
→ 模块过滤(防跨模块误匹配) → 冷启动降级
🧋 例子：你写"会员等级按消费金额分"。系统查档案发现上次定义过"铜/银/金，门槛 1000/5000/20000"，于是问你："这次也用这三档吗？"——把模糊点自动揪出。
🌐 网络案例 5/7/8：澄清必要性被 ClarifyGPT 证明，但我们不靠写代码反推，改用知识库在更早阶段澄清。更关键：我们的检索是 2026 生产级 RAG（混合检索+重排），不是朴素 RAG——2026 共识"朴素 RAG 已死，生产级=混合检索+重排，Top-K 精度再提 15–30%"。RAG 还能"减少幻觉、答案可溯源"，契合我们"可追溯"基调。

E⑤ 全链路可追溯：快递单号一路查

实现：related_fp → Traceability → XMind 分组 → FP 覆盖率矩阵。每条需求能一路追到影响的功能点，再追到下游产物。

🧋 例子：看到"会员打折"功能，能反查：源自需求第几节 → 影响了哪些 FP → 在 XMind 归到哪组。像用快递单号查包裹全程。
🌐 网络案例 2/1：可追溯是行业刚需——RTM 被比作"QA 的安全带"，Atlassian 也把它列为六实践之一防范围蔓延。我们的差异点是做到 FP 级追溯（不止"需求↔用例"两级）：比看板靠人脑拼可靠，又比 DOORS 全链路强追溯轻得多。

AI① 需求分析不是一个人干：一组 AI 员工接力

系统把"读懂需求"拆给多个专职 AI（Agent）接力完成，而不是一个模型包打天下：

  • 📥 ReqAgent：像"需求分析师"，把人话文档读成结构化双 SRR + 拆成 FP
  • 🔍 ClarifyAgent：像"爱挑刺的同事"，查知识库补全模糊点、问你问题
  • 🚧 QualityGate：像"质检员"，不合格打回重来
  • 🕸️ ImpactAnalysis：像"风险员"，改一处算出牵连哪些 FP
🧋 例子：开分店时，ReqAgent 把"老板口述"写成标准菜单；ClarifyAgent 发现"中杯"没定义，回头问；QualityGate 检查菜单齐不齐；ImpactAnalysis 算出"改糖度"会牵连奶茶和会员两个模块。
🌐 网络案例 4/7：多 Agent 协作（创建/视觉/编排/可观测）已成行业趋势（如 Pcloudy Qpilot）；我们用 Req→Clarify→Quality→Impact 的小队，把"需求分析"这一段做专、做稳，再交给下游。

AI② AI 怎么把"人话"变成"结构化需求"

  • 读文档→结构化：ReqAgent 调 LLM，一次产出 双 SRR（通用/专属规则分开放）+ 自动把需求拆成 FP（功能点积木）
  • 向量化入库：需求被中文嵌入模型（bge-large-zh，1024 维）转成"向量"，存进 Milvus 向量库 + PostgreSQL，供以后检索
  • 去重跳过 LLM：同模块已有同名 FP → 直接复制，不重复花钱调模型（doc11：显著降本）
🧋 例子：老板口述"登录加验证码"，ReqAgent 立刻整理成：通用规则（60秒倒计时）+ 奶茶店专属规则（短信通道），并拆成"获取验证码/校验"两个 FP；同时把这份菜单向量化存进"档案柜"，下次别家店能搜到。
🌐 网络案例 7/8：把需求向量化进向量库正是 RAG 的基础步骤——2026 共识"先 Embedding 再存向量库"，我们的 bge-large-zh + Milvus 就是这套标准做法，保证后续澄清/检索"可溯源、不幻觉"。

AI③ AI 怎么"澄清 + 把关 + 闭环"

  • 澄清：ClarifyAgent 做完整性/歧义/遗漏检测，调 hybrid_search（向量+BM25+RRF+CrossEncoder 重排+模块过滤）查知识库，自动补全或追问；还能 LLM 二次校验答案
  • 把关：QualityGate 当"质检员"，不达标打回；ImpactAnalysis 用 BFS 算出"改一处牵连哪些 FP"
  • 闭环：确认后的需求写入 Milvus + PostgreSQL，打版本快照（restoreVersion）；related_fp → Traceability 让每条需求可一路反查
🧋 例子：ClarifyAgent 发现"会员等级"没说门槛，查档案问你；你答完，QualityGate 检查菜单齐了放行；ImpactAnalysis 标出"这改动了会员和优惠两个模块"；最终菜单存入档案柜并拍了张"快照"，以后改坏能找回。
🌐 网络案例 5/7/8：澄清逻辑与 ClarifyGPT 同源（但我们用知识库而非写代码）；检索是 2026 生产级 RAG；落库用向量库使答案"可追溯、减幻觉"——三个环节都有业界前沿依据。
